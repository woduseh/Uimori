## 0. 확인 범위와 자료 사용법

- GitHub 연결로 기본 브랜치·SHA, `web/main.tsx`, `style.css`, `product.css`, `SourceReader.tsx`, `LibraryPanel.tsx`, `ProfileEditor.tsx`, `core/product.ts`, `core/types.ts`, `package.json`, `project-plan/CURRENT.md`, `tests/product-browser.spec.ts`의 앞 120줄과 테스트 파일 목록을 읽었다. 전체 저장소 감사나 모든 테스트의 검토는 아니다.
- 현재 앱은 이 환경에서 실행하지 않았다. 저장소 clone은 네트워크 이름 해석 제한으로 실패했고, 이 환경의 Node는 22.16.0인 반면 저장소는 >=24.14.0 <25를 요구한다. GitHub 연결을 통한 소스 읽기는 성공했다. 미실행을 제품 오류라고 판단하지 않는다.
- CURRENT에 기록된 M1-local/M0 통과는 작성자가 남긴 검증 기록이며 이번 작업에서 재실행한 결과가 아니다. live 연결, 실제 폰, 원격 배포의 완료 근거로 확장하지 않는다.
- 공개 제품 문서에서 확인한 화면/동작 패턴을 참고했다. 이 작업에서 타 서비스에 로그인해 모든 현재 UI를 조작한 것은 아니다. 문서의 설명과 Uimori에 대한 제안을 구분한다.
- `uimori-ui-prototype.html`과 PNG들은 **새 설계의 독립 모형**이다. 현재 Uimori의 실행 화면·수정 결과가 아니다. 사용자의 소설·봇 에셋·키는 포함하지 않았다. 데이터는 합성이고 API 호출은 없다.
- `prototype-checks.json`은 독립 HTML의 제한된 브라우저 검증이다. UI-01 이후의 제품 수용 시나리오는 아직 미실행이다.
- 적용 순서: 이 문서 → `CODEX_UI_TASK.ko.md` → 현재 저장소의 AGENTS/CURRENT/ARCHITECTURE. 기존 핵심 데이터 계약과 충돌하면 조용히 바꾸지 말고 최소 변경안을 명시한다. 이후 코드가 달라졌으면 baseline 차이를 먼저 확인한다.

## 1. 설계 당시 화면의 구체적인 문제

| ID | 코드에서 확인한 사항 | 사용자 경험상 문제라는 판단 | 개편 |
|---|---|---|---|
| A01 | main의 LibraryPanel·ArchivePanel이 항상 채팅 원고보다 앞에 배치된다. SettingsEditor·ProfileEditor·AssetEditor도 원고 위에 있다. 접이식 본문은 기본 닫힘이다. | 모든 폼이 늘 펼쳐진 것은 아니지만, 관리 영역의 헤더가 일상 경로를 먼저 차지한다. | 서재·앱 설정으로 분리하고 이야기별 설정만 드로어에 둔다. |
| A02 | reader 다음에 runs 전체 목록과 AttemptInspector를 넣고 그 뒤에 composer를 렌더한다. CSS에 composer를 뷰포트 하단에 두는 레이아웃이 없다. | 긴 원고 뒤에서 다음 요청 입력과 중단·후보 작업을 찾기 어렵다. | 고정 높이 앱 셸, 독립 reader 스크롤, 하단 composer. 실행 목록은 작업 패널. |
| A03 | 모바일 CSS는 sidebar를 위로 옮기고 채팅을 가로 줄로 나열한다. 새 이야기 이름 폼도 위에 남는다. | 모바일에서 탐색·생성 폼을 지나야 읽을 수 있다. | 기본 화면은 한 열. 왼쪽 탐색은 메뉴, 설정은 sheet/dialog. |
| A04 | SourceReader는 원문/번역 문자열을 React span에 넣고 CSS pre-wrap으로 표시한다. | Markdown 제목·강조·목록·인용·링크가 의미 구조로 렌더링되지 않는다. | 원문을 보존하면서 안전한 표시 파이프라인과 Typography를 둔다. |
| A05 | 원고 아래마다 job cards, 번역 chunk 목록, 재시도·revision·source/hash 연결 정보가 섞인다. | 작품의 흐름과 운영 정보의 시각적 우선순위가 같다. | 한 줄 진행 요약 → 작업 패널 → 실행 상세의 3단계 공개. |
| A06 | story 생성은 제목 필수 입력부터 시작한다. 봇/페르소나/로어는 한 attachment checkbox 목록에서 선택한다. | 사용자가 생각하는 '봇 → 페르소나 → 프리셋 → 장면 요청'과 다르다. | 봇 중심 시작 화면, 역할별 선택기. 내부 콘텐츠 통일은 유지. |
| A07 | LibraryPanel은 자료 편집·프리셋 편집·연결 등록을 같은 접이식 패널에서 제공하며 관련 자료 ID를 직접 입력한다. | 탐색 UI 대신 DB 관리 폼처럼 느껴진다. | 검색 가능한 카드/리스트, 상세 편집, 관련 자료 선택기. ID는 상세 진단으로. |
| A08 | Settings.preset(calm/vivid)와 ChatProfile.creative.style 및 프리셋 UI가 별도로 있다. | 사용자는 어떤 '서술 프리셋'이 적용되는지 혼동하기 쉽다. | fixture 실행 제어를 개발자 메뉴로. 제품용 창작 제어의 유효값을 하나의 사용자 진입점에 표시. 내부 필드는 함부로 삭제하지 않는다. |
| A09 | onmessage마다 `/chats/:id` refresh로 전체 ChatDetail을 읽고 목록·본문을 다시 구성한다. | 긴 채팅 스트림에서 전송·조립·렌더 비용이 커질 수 있는 경로다. 실제 지연은 이번에 측정하지 않았다. | 선택된 실행 이벤트를 병합/배치하고 필요할 때 해당 리소스 재조회. 우선 계측하고 작은 개선부터 한다. |
| A10 | Source에는 runId가 있고 Run에는 request/sourceRevision이 있지만 기본 reader는 source만 순회한다. | 사용자의 어떤 지시로 장면이 만들어졌는지 원고와 가까이 확인하기 어렵다. | source-run 연결로 '작가 요청 → 원고 → 후보/파생물'의 논리 턴을 만든다. |

기존 검사에는 콘텐츠 revision 고정, 프리셋 교체, 모델 경로, API 결과와 DOM 상태를 비교하는 유용한 내용이 있다. 그것을 없애는 것이 아니라 사용 흐름과 시각적 완성도를 검증하는 별도 항목을 더한다. aria-label/옛 버튼명에 결합된 테스트는 새 접근 가능한 UI로 갱신하되 불변 조건 assertion은 유지한다.

## 3. 정보 구조

### 주요 목적지

1. **이야기**: 현재 이야기와 최근/고정 이야기. 앱 진입 시 마지막으로 읽은 위치 또는 최근 목록.
2. **서재**: 봇, 페르소나, 로어, 작가 설정, 창작 프리셋, 스킬, 명칭집. 처음에는 주로 쓰는 탭 4–5개와 나머지 분류 선택으로 시작한다.
3. **설정**: 화면/읽기, 모델/연결, 기본 보조 역할, 데이터/백업, 접근 보안, 개발자 도구.

작업 현황은 독립 관리 대시보드가 아니라 sidebar의 작은 진입점으로 연다. 현재 이야기의 핵심 실패는 본문 옆에도 표시한다. 모든 실패를 toast나 숨긴 패널에만 넣지 않는다.

### 앱 설정과 이야기 설정

- 앱 설정: 재사용할 모델 연결·비밀키 참조, 전체 기본값, 테마·기본 읽기 언어, 데이터/백업.
- 이야기 설정: 장착한 봇/페르소나/로어/모듈, 선택된 창작 프리셋과 override, 본문/번역/상태/이미지 모델 경로, 역할별 자동 실행.
- 원고/응답 설정: 해당 응답의 번역 버전, 다른 후보, 요청 불일치 표시, 실행 상세.
- 화면 상태: 현재 기기의 읽기 언어·커서·열린 패널. 서버의 정사·branch head와 별개.

내부에서 모듈/Content로 통일한 것은 UI에 'type=persona인 row를 장착하세요'라고 노출하라는 의미가 아니다.

## 4. 화면 규격 — 제안값, 측정 후 조절 가능

### 데스크톱

- 앱 전체는 `100dvh`를 사용하고, 가로 페이지 스크롤이 발생하지 않는다.
- 좌측 sidebar 약 240–260px: Uimori, 새 이야기, 검색, 서재, 최근/고정 목록, 작업 현황, 설정.
- 중앙 header 약 56–60px: 제목, 작은 봇/세계 맥락, 다른 전개·읽기·이야기 설정.
- 기본 화면의 상시 오른쪽 열은 없다. 설정/분기는 요청 시 약 360–400px drawer/dialog로 연다. 도킹·리사이즈는 초기 필수 아님.
- reader와 composer는 같은 중앙 열에 속하지만 reader만 스크롤된다. 읽기 너비는 약 700–780px 안에서 조절한다.
- 하단 composer: 기본 2–3줄, 입력에 따라 제한된 높이까지 확장. 창작 프리셋·페르소나·본문 모델의 작은 선택기. 주 동작은 보내기 하나이며 현재 작업 실행 중에는 해당 작업 중단.
- 단계·build hash·NARRATIVE RUNTIME·M1 fixture 같은 개발 문구는 기본 제목으로 쓰지 않는다. 실제 demo/미연결 상태는 연결 선택기·설정·작업 배지로 정직하게 표시한다.

### 모바일

- 폭 360/390px부터 설계한다. sidebar를 페이지 위로 쌓지 않는다.
- header는 메뉴·제목·2–3개 중요 동작. 덜 쓰는 읽기 설정은 더보기 또는 이야기 설정에 둔다.
- 본문은 대략 16–20px(사용자 조정), 1.75–1.95 줄간격, 좌우 16–20px 여백. 한국어 어절 보존과 긴 URL 줄바꿈을 함께 처리한다.
- composer는 시각적 뷰포트의 하단, OS safe area와 가상 키보드를 고려한다. `100dvh` 하나만으로 모든 키보드/IME를 검증했다고 하지 않는다.
- 기본 주 동작은 44px 수준의 터치 영역을 목표로 한다. 조밀한 행의 아이콘과 텍스트 간격도 시험한다. WCAG 2.2 AA 최소 target은 예외와 함께 24 CSS px인 별도 기준이며, 44px는 제품 목표다.
- 짧은 후보/프리셋 선택은 bottom sheet, 긴 콘텐츠 편집·모델 연결 폼은 fullscreen page/dialog를 우선한다. 모바일에서 많은 중첩 sheet를 열지 않는다.
- 집중 읽기는 composer와 탐색을 숨기는 표시 옵션이다. 모델 작업 모드나 프롬프트를 바꾸지 않는다. 나가는 버튼은 항상 찾을 수 있어야 한다.

### 시각 언어

- 기본 제안: 저채도 차콜 + 작은 세이지 그린 강조. 밝은 테마도 token으로 지원. 첫 방문은 OS 테마를 따르고 명시적 선택을 기억한다. 시안은 비교를 위해 dark로 시작한다.
- UI는 시스템 sans, 본문은 sans 기본과 선택 가능한 serif. 글꼴 파일을 이 자료에 포함하지 않는다.
- 큰 카드·녹색 배경·테두리는 자료 선택/설정처럼 경계가 필요한 곳에만. 원고는 카드 안의 카드로 감싸지 않는다.
- 원고 제목은 원문에 실제 제목이 있을 때만 렌더한다. 시안의 합성 원고 제목을 모든 응답의 자동 제목 규칙으로 복제하지 않는다.
- 과한 유리효과·그라데이션·거대한 hero·토큰마다 타자기 효과·지속적인 그림자 애니메이션을 피한다.

## 5. 핵심 상호작용

### 5.1 시작과 전환

- '새 이야기' → 봇 검색/카드 → 페르소나(없음 허용)·최근 창작 프리셋 확인 → 시작.
- 이름은 봇 이름 기반 기본값으로 자동 채운다. 사용자가 제목을 먼저 지어야 진행되는 필수 관문을 없앤다. 제목 변경에 LLM 호출을 요구하지 않는다.
- 빈 이야기를 먼저 만들고 profile을 후속 API로 저장해야 한다면 실패를 복구 가능하게 표시하고 재시도에서 새 채팅을 중복 생성하지 않는다. 프로필 저장 완료 전 미적용 상태로 첫 원고를 보내지 않는다.
- 봇 정보의 편집과 봇으로 새 이야기를 시작하는 동작을 구분한다. 라이브러리 업데이트는 기존 이야기의 pinned revision을 몰래 바꾸지 않는다.
- 현재 확인한 Content에는 썸네일 참조가 없고 Asset은 chatId에 연결된다. 봇 카드 이미지는 우선 이름/문자 대체 표현을 사용한다. 실제 라이브러리 표지를 넣으려면 최소한의 안전한 참조 모델/API 확장을 별도 구현한다. 현재 chat asset을 전역 bot 표지라고 추정하지 않는다.
- 이야기/분기별 draft·읽기 위치는 보존한다. 브라우저 뒤로/앞으로와 기존 `?chat=…&branch=…&source=…` 진입을 깨뜨리지 않는다.

### 5.2 요청과 원고

- `Source.runId` ↔ `Run.id/request`로 요청과 원고를 붙인다. 사용자 요청은 작은 메시지 surface, 긴 원고는 전체 읽기 폭의 prose.
- 요청이 길면 표시만 접는다. '전체 보기'로 복원할 수 있고 실제 API 입력은 축약하지 않는다.
- 소설 모드에서는 '장면 요청'으로 입력 의미를 설명한다. `(OOC: …)`를 별도의 관리/분석 모드로 자동 전환하지 않는다.
- 문서 제목·강조·인용·목록·ruby 등은 지원 정책에 맞게 안전하게 렌더한다. 임의 HTML·script·이벤트 handler를 그대로 실행하지 않는다. 원문 hash/revision은 렌더 결과로 재계산하지 않는다.
- main 모델의 도구 활동은 작은 작업 요약으로 표시한다. 항상 별도 플래너나 로어 수동 선택 팝업을 강요하지 않는다.
- streaming 중 partial text는 원고 자리에서 볼 수 있게 하고 최종 결과와 구분한다. 재연결 중이면 서버가 계속 생성한다고 단정하는 대신 '연결을 다시 확인하는 중'이라고 표시한다.
- 생성 중 다른 채팅을 열어도 전역 busy나 구독 종료가 원격 run을 취소하지 않는다. 현재 분기에서 이중 제출이 생기지 않도록 기존 idempotency와 version 계약을 유지한다.

### 5.3 보내기·취소·키보드

- 소설 기본: Enter는 줄바꿈, Ctrl/Cmd+Enter는 보내기. 짧은 RP는 사용자 선택으로 Enter 보내기/Shift+Enter 줄바꿈을 허용한다. 모드 변화가 예고 없이 키 의미를 바꾸지 않는다.
- 한글 composition 중 보내지 않는다. desktop 단축키는 보조이며 터치 보내기 버튼은 항상 존재한다.
- 서버가 요청 수락을 확인하면 draft를 비우되 실패/전송 결과 불명확이면 복구한다. 주 버튼과 composer 주변에서 수락 상태를 확인할 수 있게 한다.
- 본문 생성 중단, 번역만 중단, 전체 후속 작업 중단을 구분한다. 화면을 닫는 것은 생성 취소가 아니다.
- Esc는 열린 메뉴/dialog를 닫는다. 원격 유료 작업을 Esc 한 번으로 무조건 중단하는 전역 shortcut은 기본값으로 만들지 않는다.

### 5.4 번역 우선 독서

- 기본 표시 언어는 한국어 번역. 현재 SourceReader의 원문 기본값과 구분해서 device preference로 관리한다.
- 번역이 준비되지 않았으면 원문을 읽을 수 있는 명시적 동작과 번역 상태를 보여준다. 사용자가 원문을 읽기 시작했다면 번역 도착으로 읽기 위치를 강제로 바꾸지 않는다.
- 번역/원문 전환은 표시 선택이며 과금 동작이 아니다. '다시 번역'과 '다른 응답 생성'은 분명히 다른 동작이다.
- 재번역 버전은 필요할 때 메뉴에서 고르고, 원문과 번역을 동시에 비교하는 기능은 선택적으로 연다. 모든 응답에 영문+한글을 상시 두 번 펼치지 않는다.
- 번역 실패 시 원문 보존 + 작은 오류 + 번역만 재시도. chunk 상세는 문제를 조사할 때만 펼친다.
- 보호 구문·원문 블록·원문↔번역 앵커 매핑을 지킨다. DOM을 나중에 뒤져 HTML을 API에 되먹이지 않는다.

### 5.5 다른 전개

- 각 응답 아래에 `이전 / 1·2 / 다음`, '다른 응답', '여기서 이어가기' 등의 작은 동작을 제공한다.
- header의 '다른 전개'는 현재 갈림길·형제 후보·그 뒤에 이어진 장면을 보여준다. 거대한 전체 그래프는 첫 UI 개편 필수가 아니다.
- 읽는 후보만 바꾸면 비용이 발생하지 않는다. 새 후보 생성에는 비용·model snapshot이 있으며 사용자가 명시적으로 선택한 한 번의 호출로 실행한다.
- 기본 한 개 결과에서 계속 쓰는 것은 자연스럽게 경로 선택을 의미한다. 매번 정사 채택 확인 팝업을 추가하지 않는다.
- 후보 선택을 다른 기기의 읽기 위치나 전역 head로 곧장 동기화하지 않는다. 후보와 후손을 삭제하지 않는다.

### 5.6 프리셋·로어·보조 역할

- composer의 프리셋 선택 → 기존 프리셋 클릭 → 다음 요청에 적용. 재사용 프리셋 원본과 현재 이야기의 수정값은 분리.
- 빠른 적용 중 수정 중인 폼을 덮어쓰거나 오래된 profile PUT로 새 값을 되돌리지 않는다. conflict를 가까운 위치에서 표시하고 입력을 보존한다.
- 장르·시점·문체 등을 매번 조정해야 하면 이야기 설정에서 전체 편집 후 '프리셋으로 저장'. 현재 구현되지 않은 genre fields는 기능 확장으로 분리하고 가짜 저장 버튼을 넣지 않는다.
- '항상 포함'과 '모델이 필요할 때 읽기'를 사용자 언어로 노출한다. 같은 허용 scope의 자유로운 검색을 frontend가 top-k 제한으로 바꾸지 않는다.
- '관련 자료 ID'는 검색 가능한 자료 선택기로 대체하되 서버에는 기존 ID/ref를 전달한다.
- 본문·번역·상태·이미지 모델은 이야기 설정에 있고 연결 관리는 앱 설정에 있다. '창작 프리셋'을 바꿨다고 API 키/모델이 바뀌지 않는다.
- 상태/이미지는 보조 결과를 native component로 표시한다. 표시 실패로 본문을 재생성하지 않고, 도착 시 viewport를 점프시키지 않는다. 상태 화면이 현재 원고 시점의 결과인지 확인한다.

### 5.7 모델·오류·진단

- 현재 `Connection.protocol`은 `fixture-sse-v1` 하나다. UI 이름만 OpenAI/Gemini/Vercel로 바꾸거나 임의 API key 입력을 추가해 live 지원처럼 보이게 하지 않는다.
- 기존 UI에서 사용 가능한 것은 실제 model preset·catalog·manual ID·max output·temperature다. reasoning effort 등은 현재 schema에 없으므로 capability-aware API/adapter 확장이 필요한 별도 작업이다.
- fixture 모드의 정직한 표시는 연결/모델 선택기에서 한다. 미연결인데 지워진 경고 대신 '정상 AI 연결' 초록불을 그리지 않는다.
- 기본 오류는 작업 결과 가까이에: '원문은 저장됨 · 번역 실패 · 번역만 다시 시도'. 인증 실패는 모델 연결 설정으로 이동할 수 있게 한다.
- refusal는 짧은 결과 카드로, 긴 대체 작품을 자동 생성·번역하지 않는다. 의미적 불일치를 100% 자동 판정한다고 하지 않는다.
- 표시 계층: (1) 현재 작업 한 줄, (2) 작업 패널의 단계별 상태/비용, (3) 선택된 run의 상세 진단. 기존 Inspector를 삭제하지 말고 마지막 계층으로 이동한다.
- HTTP/SSE 연결 상태와 원격 작업 상태는 다르다. '연결 끊김'이 곧 '생성 실패'는 아니다.
- 사용량은 confirmed/estimated/unknown을 유지한다. 숨긴 검사나 지원하지 않는 과금 데이터가 0으로 보이면 안 된다.

UI의 scroll root가 window에서 reader로 바뀌므로 `scrollY` 기반 복원과 `getBoundingClientRect()>60` 가정도 함께 바꿔야 한다. window의 스크롤 listener를 남겨놓고 시각 셸만 고치면 복원이 깨진다. sourceRevision + block anchor + 내부 offset 기준을 우선하고, pixel-only 저장의 한계를 구분한다.

실시간 refresh 개선은 별도 계측으로 범위를 정한다. 이벤트별 targeted cache update가 가능하면 사용하고, 전체 ChatDetail refetch밖에 없다면 coalescing/visible component isolation부터 수행한다. 안전한 원고 저장과 event cursor 계약을 버리면서 억지로 프레임 수만 줄이지 않는다.

## 7. 구현 순서와 완료 범위

### UI-1: 기본 화면 전환 (최우선)

셸·sidebar·header·reader·composer, 요청/원고의 논리 턴, 안전한 본문 렌더링, 원문/번역 전환을 실제 현재 API로 연결한다. 관리/백업/진단을 새 목적지로 이동한다. 기존 기능을 삭제해서 화면만 비우지 않는다.

첫 확인 대상은 길이가 짧은 환영 화면이 아니라 **원고가 길고 번역이 있고 과거 작업이 쌓인 이야기**다. 1440×1000과 390×844의 스크린샷을 먼저 보고 계속한다.

### UI-2: 선택과 관리 흐름

봇-first 시작, 페르소나/프리셋/본문 모델 picker, 서재 검색/상세, 이야기 설정, 후보 drawer, 작업 현황, 앱 연결 설정. 현재 데이터/API로 표현 가능한 항목부터 구현한다. 새 metadata·genre·reasoning·실제 API 연결은 필요한 작은 기능 변경으로 구분한다.

### UI-3: 실사용 검증과 마감

여러 이야기/탭 전환, 긴 원고·translation arrival·실패·부분 완료, 모바일 overflow/키보드/설정 sheet, focus/IME·뒤로가기·커서 보존·코드 회귀를 확인한다. 시각적 변경 전후와 알려진 제한을 남긴다. 새로운 M2 기억·규칙 엔진을 이 작업에 끼워넣지 않는다.

### 비공개 원격 preview는 별도 후속 조치

이번 요청은 UI 개편안이며 배포 승인이 아니다. 현재 사용자 PC의 폴더/키를 건드리거나 공개 URL을 만들지 않는다. 실제 폰 확인용 preview를 할 때는 승인된 host, 단일 인증 사용자, HTTPS 또는 사설 접속, 지속 저장·백업, SSE/20분 작업의 수명, 자격증명 저장을 확인한다. live provider 연결 작업과 외관 개편을 한 완료 주장으로 합치지 않는다.

## 8. UI 검증은 버튼이 눌린다는 것보다 더 넓다

현재 저장소 명령은 **npm** 기준이다: `npm run check`, `npm run build`, `npm run verify -- --milestone M0`, `npm run verify -- --milestone M1-local`. 새 UI 전용 명령을 추가했다면 실제 실행 후 문서화한다. pnpm/새 lockfile로 이유 없이 바꾸지 않는다. `check`는 현재 typecheck이지 존재하지 않는 lint를 돌렸다는 뜻은 아니다.

관련 검사를 좁게 반복하고 최종 코드에서 필요한 전체 회귀를 실행한다. UI를 바꾸므로 기존 구조에 의존한 locator 변경은 정당하지만 scope·원문 보존·후속 작업/사용량 assertion을 약화해 통과시키지 않는다.

독립 HTML의 이번 검증: 원문/번역 전환, 프리셋/후보 UI, 서재 검색, 기본 모의 생성, 모바일 탐색/설정, 집중 읽기, 360/390/768/1024/1440 너비에서 기본 overflow와 입력창 위치. 실제 OS 키보드·스크린리더·API·장문 성능 검증은 아니다. 상세 수용 시나리오는 `UI_ACCEPTANCE.json`을 사용한다.

합격의 중심은 **일반 사용자가 DB ID·revision·fixture·job·source hash를 알아야만 이야기를 시작하고 읽고 이어갈 필요가 없는가**다. 개발자 관찰 가능성은 유지하면서 일반 경로의 정보 우선순위를 바꾼다.
