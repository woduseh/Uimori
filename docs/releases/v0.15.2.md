# v0.15.2

번역이 쓰이는 대로 보이고, 거절된 본문은 자동으로 다시 생성해요. 도우미가 프로바이더의 일시 오류와 필요 없는 컨텍스트 정리 때문에 실패하던 경우를 고쳤고, 채팅을 열 때 받는 양과 저장 공간을 줄였어요.

- **번역이 쓰이는 대로 보여요.** 전에는 장면이 다 쓰인 뒤 번역이 끝날 때까지 아무것도 보이지 않았어요. 이제 번역으로 읽는 장면은 번역 중인 글이 도착하는 대로 보여요. 거절되어 다시 시도한 번역은 마지막 시도의 글만 보여요. [읽기](../READING.md)
- **거절된 본문을 자동으로 다시 생성해요.** 본문이 거절 판정, 프로바이더의 거절이나 안전 차단, 빈 응답으로 끝나면 같은 요청을 다시 보내요. 기본값은 켜짐과 최대 2회예요. **앱 설정 → 새 채팅 기본값**에서 횟수(0~5회)를 바꾸고, 채팅의 **고급 실행 설정**에서 그 채팅만 켜거나 꺼요. 따로 정하지 않은 기존 채팅에도 적용돼요. 취소, 연결 실패, 호출 한도나 컨텍스트 한도 초과, 결과를 알 수 없는 오류에는 다시 보내지 않아요. 거절된 실행은 기록에 그대로 남고, 다시 보낸 실행은 사용량이 따로 들어요. [거절 뒤 자동 다시 생성](../GENERATION.md#거절-뒤-자동-다시-생성)
- **도우미가 덜 실패해요.**
  - 프로바이더가 요청 한도 초과(HTTP 429)나 서버 오류(5xx)로 답하면 5초, 20초, 60초 뒤에 다시 시도해요. 세 번 뒤에도 같으면 전처럼 작업이 실패해요. Codex 실행기를 쓰는 도우미는 해당하지 않아요.
  - 제한 시간을 넘긴 작업을 "취소됨"이 아니라 실패로 표시하고, 제한 시간을 바꾸는 설정으로 안내해요.
  - Gemini 모델에서 도구 호출이 쌓이면 입력을 실제의 세 배 가까이로 추정해 필요 없는 컨텍스트 정리가 일어나던 문제를 고쳤어요. [컨텍스트 한도](../CONTEXT-LIMITS.md#추정과-검증-범위)
  - 추론을 쓰는 컨텍스트 정리 모델이 출력 한도에 걸려 요약을 끝내지 못하던 문제를 고쳤어요.
  - 프리셋을 저장하는 도구 호출에 정의되지 않은 값이 들어가면 작업이 실패하던 문제를 고쳤어요. 이제 도우미가 오류를 받아 고친 뒤 다시 저장해요.
  - 같은 대화에서 앞 작업이 쓴 앱 기능의 사용법을 다음 작업이 이어받아, 사용법을 다시 찾는 호출이 줄어요.
- **채팅을 열 때 덜 받아요.** API 응답을 압축하고, 바뀌지 않은 응답은 다시 내려받지 않아요. 채팅을 열 때 읽기 화면 자료를 두 번 받던 것을 한 번으로 줄였어요. Risu 카드로 그린 장면은 같은 장면을 다시 열 때 다시 그리지 않아요. 처음 받는 스크립트는 1,212,478바이트에서 786,996바이트로 줄었어요.
- **저장 공간을 덜 써요.** 원고 검색 색인이 글을 한 번만 저장해요. 기존 색인은 서버가 한가할 때 조금씩 새 형식으로 옮기고, 옮기는 동안에도 검색은 그대로 돼요. 읽기 화면이 더는 보여 줄 수 없는, 끝난 실행의 스트림 조각은 시작할 때 지워요. [원고 검색](../MANUSCRIPT-SEARCH.md)
- **고친 것**
  - Story UI 블록의 입력란에 글을 쓰거나 초안이 복원될 때 블록이 처음부터 다시 그려지던 문제를 고쳤어요.
  - 작업이 끝난 뒤 안 쓰는 이미지를 찾는 1.6~2.1초 동안 서버가 다른 요청에 답하지 못하던 문제를 고쳤어요.
  - 사이드바 활동 목록의 실행 중 항목에 진행 표시가 빠져 있던 것을 고쳤어요.
- **진단 자료가 늘었어요.** 모델 호출마다 첫 응답과 첫 글자까지 걸린 시간을, 본문 실행마다 단계별 시간을 기록해요. API 응답에는 `Server-Timing` 헤더가 붙어요. [진단](../DIAGNOSTICS.md)

기존 **SQLite 스키마 15**를 유지해요. 업데이트 뒤 처음 시작할 때 더는 보여 줄 수 없는 스트림 조각을 지우고, 그 뒤 서버가 한가할 때 검색 색인을 새 형식으로 옮겨요. 원고, 대화, 설정은 바꾸지 않아요. SQLite 페이지 캐시를 64MiB로 늘려서 서버가 메모리를 그만큼 더 쓸 수 있어요. [데이터 호환성](../DATA-MIGRATIONS.md) · [업데이트 안내](../UPDATES.md)

**알려진 문제:** 요청 한도 초과가 몇 분씩 이어지면 도우미의 다시 시도(합쳐서 85초)로는 넘기지 못하고 작업이 실패해요. 실패한 도우미 작업을 멈춘 자리에서 이어 가는 기능은 아직 없어서, 다시 요청하면 자료를 처음부터 다시 읽어요. 그 밖은 v0.15.0과 같아요. 봇이 있는 채팅에서는 장면이 완성되는 순간 본문이 위아래로 조금 움직일 수 있고, 봇의 화면 형식으로 그린 장면에서는 변경 카드가 바뀐 자리의 근처까지만 열어요. 채팅 로어를 바꾼 변경 카드는 그 변경을 보여 줄 화면이 아직 없어요.

<summary>구현·검증 범위 — 에이전트 작성 (Claude Fable 5.2)</summary>

변경 커밋은 `v0.15.1..v0.15.2` 범위에 있어요. 두 갈래의 작업이 들어갔어요.

- **도우미 실패 수정(`5c868892`, `c9570d2e`, `7af36a0a`, `d6341845`, `9b8833a1`):** 운영 DB의 도우미 작업 121건(2026-09-28~11-23)을 읽기 전용 집계로 분석했어요. 끝나지 못한 28건의 원인은 HTTP 429가 11건, 시간 초과가 7건, 프리셋 검증 오류가 4건, HTTP 400이 2건, 안전 차단이 2건, 컨텍스트 정리 실패가 1건, Codex 도구 거절이 1건이었어요. 프리셋 검증 오류와 HTTP 400은 그 뒤의 릴리스에서 이미 고쳐진 경로였고, 이번에는 `resource.save`에 남아 있던 같은 종류의 경로만 고쳤어요. 각 수정은 실패하는 테스트로 먼저 재현했어요.
  - 다시 시도 간격은 `core/helper.ts`의 `HELPER_PROVIDER_RETRY_DELAYS_MS`예요. 대기 중 취소와 제한 시간은 그대로 적용돼요.
  - 시간 초과는 `HELPER_TASK_TIMEOUT`으로 끝나고, 실패 줄의 **설정 확인**이 역할별 모델 설정을 열어요.
  - 입력 추정은 정리 판정(`measureProviderRequest`)과 전송 전 한도 검사(`core/vertex.ts`)가 서명(`thoughtSignature`)과 추론 본문을 뺀 본문을 재도록 맞췄어요. 한 작업에서 판정 추정이 258,852였을 때 프로바이더가 보고한 입력은 92,495였어요. 서명을 뺀 추정은 Vertex 도우미 호출 1,146건에서 실제 입력의 0.88~1.22배(호출 순서 구간별 중앙값)였어요. OpenAI와 Anthropic의 연속 요청은 측정 자료가 없어 바꾸지 않았어요.
  - 요약 호출은 추론을 쓰는 모델이면 출력 한도를 줄이지 않아요(`core/context-summary-policy.ts`).
- **번역 스트리밍, 자동 다시 생성, 전송·저장·표현 캐시, 진단(`f113f73d`부터 `18ed2f23`까지 17개 커밋):** 다른 작업 세션에서 구현하고 검증했어요. 이 노트의 수치(처음 받는 스크립트 크기, 이미지 검사 시간)는 그 커밋 기록에서 옮겼고 여기서 다시 재지 않았어요. 거절 판정을 응답 앞부분만으로 일찍 내리는 방식은 운영 판정 1,593건을 재생해 본 결과 줄일 수 있는 양이 3.35%여서 넣지 않았어요(`886bbe92`). 도우미의 읽기 도구 병렬 실행도 읽기가 수 밀리초라 넣지 않았어요(`1e7dbe57`).
- **로컬 검증:** 릴리스 후보에서 `quality`, 전체 Vitest 3,137개(건너뜀 42개), 문서 검사를 통과했어요. 도우미 화면을 바꾼 커밋에서는 `verify:chat-unification` 29개, 번역 키와 문구 검사를 통과했고, 로컬 빌드에서 실패 줄을 1280px와 375px 너비로 확인했어요. Windows에서 실행했어요. 전체 브라우저 회귀는 이 후보에서 실행하지 않았어요.
- **CI 검증:** 릴리스 커밋의 GitHub `Quality` 워크플로 통과를 확인한 뒤 태그와 릴리스를 발행해요.
- **검증하지 않은 것:** 실제 프로바이더에서의 429 다시 시도와 시간 초과 표시, Gemini 입력 추정 수정의 실제 효과(운영 기록과 합성 테스트로만 확인했어요), 실제 휴대폰에서의 렌더링이에요. 도우미가 느려지는 긴 모델 호출(완료된 작업에서 가장 긴 호출의 중앙값 163초)의 원인은 이 릴리스의 첫 응답 시간 기록이 쌓인 뒤에 가릴 수 있어요. 셸 도구가 들어간 뒤 도우미 완료율이 84.2%에서 64.4%로 낮아진 원인도 가리지 못했어요.
