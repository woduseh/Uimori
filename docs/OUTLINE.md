# 구성·집필 작업실

작품 전체를 설계하거나 이번 회차만 가볍게 구성하고, 선택한 단위의 실제 본문으로 이어가는 기능이에요. 구성을 사용하지 않는 기존 이어쓰기는 그대로 유지해요. 계획이 있다는 이유로 본문을 생성하거나, 미래 사건을 이미 일어난 사실로 기록하지 않아요.

## 시작과 화면

채팅 메뉴의 **계층형 구성**에서 구성·집필 작업실을 열어요. 빈 화면의 **도우미와 구성 시작**은 기존 도우미에 요청과 대상을 준비하며, 직접 전송하기 전에는 모델을 호출하지 않아요. **직접 추가**는 회차부터 시작할 수 있어요.

데스크톱에서는 구성 목록·선택한 내용과 기존 도우미를 함께 사용해요. 화면이 좁으면 현재 구성 선택기를 사용하고, 모바일에서는 구성과 도우미를 전환해요. 돌아와도 선택한 항목·펼친 목록·편집 중 입력은 보존해요. 본문 읽기 위치는 별도로 유지해요.

항목의 주요 행동은 **상세화**, **이 단위 집필/이어 쓰기**, **원문과 점검**이에요. 이름·구성 내용 편집, 하위 추가, 유지 조건, 순서 이동과 삭제는 관리 메뉴에 있어요. 다른 화면에서 저장한 변경은 도우미 작업 상태 갱신·화면 재진입·새로고침에서 다시 읽되, 편집 중인 초안을 덮어쓰지 않아요. 도우미에서 구성으로 돌아올 때도 최신 점검 결과를 읽고 선택·편집 초안은 유지해요. 낡은 수정 번호로 저장하면 충돌과 현재 저장 내용을 보여줘요.

## 수준과 내용

다섯 종류는 `core/outline.ts`의 `OUTLINE_LEVELS`를 사용해요.

| 코드 | 표시 | 한 번의 집필 대상 |
| --- | --- | --- |
| `theme` | 작품 방향·주제 | 아니요 |
| `mainStory` | 메인 스토리 | 아니요 |
| `arc` | 큰 사건 | 아니요 |
| `episode` | 회차 | 예 |
| `beat` | 작은 사건 | 예 |

중간 단계를 생략하거나 어느 수준에서든 독립 항목으로 시작할 수 있어요. `theme → episode → beat`, `episode → beat`, 독립 `beat`도 유효해요. 부모가 있다면 자식보다 앞선 수준이어야 하며 같은 수준의 중첩·역순·자기 참조·다른 채팅의 부모는 거절해요. 필수 빈 상위 항목을 자동 생성하지 않아요.

입력은 이름과 자유로운 구성 내용이 중심이에요. 안내는 작품의 정서, 인물의 목적, 준비할 요소, 변화, 정보 공개와 멈출 지점을 제안하지만 필수 양식은 아니에요. 모든 장면에 갈등·반전·교훈을 요구하지 않고, 기존 작품 문체와 RP 참여자의 선택 범위를 유지해요.

## 유지할 조건

`fixed`는 **일반적인 상세화·재구성에서 보존할 창작상의 조건**이에요. 절대적인 편집 잠금이 아니며, 사용자가 그 조건 자체를 바꾸라고 명확하게 요청하면 도우미나 직접 편집으로 바꿀 수 있어요. 조건 해석은 모델 지침이지 완전한 의미 검증기가 아니에요.

직접 편집과 사용자가 지시한 도우미 편집은 같은 저장 규칙을 사용해요. 과거의 별도 모델 전용 고정/집필 완료 편집 제한은 제거했어요. 기존 배치 영수증의 `authority` 값은 재전송 비교용 출처 태그이며 현재 권한 등급이 아니에요. 진행 중인 집필 단위의 수정·중복 실행은 계속 막고, 실제 원문이 연결된 항목이나 그 상위의 삭제도 거절해요. 계획 편집은 이미 저장한 원문을 다시 쓰지 않아요.

## 관련 구성과 이번 입력 컨텍스트

편집기의 **함께 참고할 구성**에서 같은 채팅의 다른 계획을 최대 40개 연결할 수 있어요. 한 회차의 준비가 다른 회차에서 회수되는 경우처럼 필요한 연결만 사용해요. 자기 자신·존재하지 않는 항목·다른 채팅·중복 연결은 거절해요. 상호 참조는 가능하지만 참조를 재귀적으로 따라가지는 않아요.

집필 미리보기는 `GET /api/outline-nodes/:id/brief`에서 프로그램이 저장 자료를 조립해요. 모델 호출·별도 편집 원본·본문 저장은 없어요.

- `path`: 존재하는 상위 방향부터 현재 단위까지.
- `children`: 현재 단위의 직계 하위 계획.
- `related`: 위 항목들에 명시적으로 연결된 관련 계획. 이미 포함된 항목은 중복하지 않아요.
- `sources`: 현재 단위 및 그 하위에 연결된 실제 원문의 ID·현재 hash·귀속 항목.
- 실제 Run에는 기존 원문 계보에 있는 다른 집필 항목도 `written`으로 최대 40개 포함해요.

구성 지침은 선택한 단위만 작성하고 현재 단위에 허용된 정보 공개 시점을 따르게 해요. 뒤의 결과를 미리 폭로하지 않되 공개할 차례가 된 반전을 무기한 감추지도 않아요. `related`는 추가 집필 대상이나 과거 사실이 아니에요. 실제 문체·지식 일관성과 복선 품질은 실모델 평가가 필요해요.

`RunSnapshot.outline → MainInput.outline → main-host-context`의 기존 본문 입력 경로를 재사용해요. 이 컨텍스트는 현재 요청과 실제 원문·메모·로어를 대체하지 않으며 최종 입력 토큰 예산 검사를 받아요. 전체 계획을 무조건 삽입하거나 예산을 넘는 중요 조건을 조용히 버리지 않아요.

## 집필과 나누어 쓰기

**이 단위 집필/이어 쓰기**를 누르면 선택 단위와 준비된 요청문이 보여요. 추가 지시·멈출 지점을 고친 뒤 **집필 시작**으로 실제 본문을 생성해요. 미리보기와 선택만으로는 실행하지 않아요.

1. `POST /api/outline-nodes/:id/scene-command`로 구성에 연결된 장면 요청을 만들어요. 새 UI는 대상 수정 번호와 계획 hash를 보내, 미리보기 뒤 바뀐 계획에 옛 요청을 붙이지 않아요.
2. 기존 `POST /api/scene-commands/:id/run`으로 본문을 예약해요. 별도 작문 실행기·도우미 산출물의 자동 본편 승격은 없어요.
3. 실행 입력은 예약 시 고정해요. 기존 단일 writer·취소·원문 저장 경계를 유지해요.

한 구성에 여러 원문을 연결할 수 있어요. 이미 쓴 원문이 있으면 새로운 명시 요청은 **이어 쓰기**로 준비하고 기존 원문을 참고해요. 원문을 다시 쓰거나 다른 전개를 만드는 것은 기존 편집·독립 사본 흐름을 사용해요. 자동 연속 집필은 하지 않아요.

원문 연결 수는 의미적 완성도가 아니에요. 회차에 원문을 만들었다고 하위 사건을 모두 완료 처리하지 않고, 하위를 작성했다고 부모의 의도가 모두 달성됐다고 단정하지 않아요. 화면은 실제 원문 수와 하위 항목의 연결 현황을 구분해요.

## 예약·재전송·변경

아직 실행하지 않은 예약에 사용된 상위 경로·직계 하위·명시적 관련 계획이 실질적으로 바뀌면 같은 저장 트랜잭션에서 예약을 취소해요. 관련 없는 형제, 수정 번호만 바뀐 경우, 배치 중 변경했다가 원래 내용으로 되돌린 경우, 롤백된 배치는 취소하지 않아요. 이미 접수된 Run은 당시 입력을 유지해요.

브라우저는 구성 저장과 집필의 요청 본문·키를 전송 전에 보존해요. 응답이 유실됐으면 **요청 결과 확인**으로 같은 요청을 확인하고 새 실행으로 바꾸지 않아요. 이후 다른 이어쓰기를 시작했어도 원래 키는 원래 구성·장면 요청에만 연결돼요. 다른 대상이나 내용으로 키를 재사용하면 충돌이에요. 브라우저가 복구 기록을 보존할 수 없으면 새 전송을 시작하지 않아요.

## 도우미 선택과 점검

선택된 구성은 제목 대신 채팅·항목 ID·수정 번호·작업 목적을 전달해요. 선택이 바뀌었다고 이미 작성한 도우미 요청문을 덮어쓰지 않고, 준비한 요청을 덧붙일 수 있게 해요. 다른 채팅의 대상이나 낡은 수정 번호는 모델 호출 전에 거절해요. 특정 원문 선택과 구성 선택은 한 번에 하나의 활성 대상으로 관리해요.

`outline.read`와 `outline.write`는 기존 도우미 앱 도구예요. `outline.read`는 기본 `overview`, 특정 `nodeId`의 `subtree`, 한 항목의 `detail`을 제공해요. 모든 모드는 `offset/limit`을 사용해요. 목록은 항목 수(기본 20, 최대 50), 의도는 UTF-16 단위 수(기본 6,000, 최대 10,000)를 뜻하며 큰 limit 요청도 모드별 상한까지 반환해요. 하위 트리는 `depth`(0=선택 항목, 1=직계 자식, 생략=전체 자손)를 사용해요. `detail`의 `section`은 `intent`·`related`·`writings`이에요. writings는 선택 단위와 자손의 실제 본문 참조 목록이에요.

모든 페이지는 해당 조회 범위의 `version`, 정확한 반환 범위와 재호출 가능한 `nextRead`를 제공해요. 이어 읽기는 `expectedVersion`이 필요하고 구성이 달라지면 `OUTLINE_CHANGED`와 재조회 경로를 돌려줘요. 과거 스냅샷 저장소나 편집 잠금은 만들지 않아요. 버전은 해당 목록·하위 트리·상세 구간에 영향을 주는 메타데이터를 한 읽기 트랜잭션에서 계산해요. 관계없는 형제 구성의 변경은 해당 항목 상세나 다른 하위 트리의 이어 읽기를 막지 않아요. 모드나 section을 바꿀 때는 새 첫 조회로 시작하고, 같은 범위의 다음 페이지에만 받은 버전을 이어 써요. 본문을 매 페이지 hash하지 않아요. 개요의 `intentCodePoints`는 SQLite Unicode 코드 포인트 수이고 본문 범위는 UTF-16 단위로 구별해요. 목록 끝은 의도 전문이나 본문을 모두 읽었다는 뜻이 아니며, `coverage.excludedByDepth`로 깊이 때문에 빠진 항목도 명시해요. 의도 상세의 `coverage.wholeField`는 **이번 한 응답이 필드 전체를 포함하는지**만 나타내요. 예를 들어 전체 841자 중 마지막 `600–841` 구간은 `wholeField:false`, `nextOffset:null`이에요. 마지막 페이지인지는 `nextOffset`으로, 여러 페이지를 합쳐 읽은 범위는 실제 start/end와 동일 조회 버전으로 판단해요. 기존의 모호한 `coverage.complete`는 이 의도 응답에서만 `wholeField`로 바꿨어요.

응답은 JSON 직렬화 24,000 UTF-16 단위 이내로 조립해요. 전체 detail을 만들고 마지막에 자르지 않고, 의도 상세는 선택한 노드만 읽고 목록 미리보기는 페이지별 일괄 쿼리로 읽어요. 연결·원문 참조는 해당 상세 모드에서만 조회해요. 원문 참조는 유효한 `data.read` 인자를 반환하고, 작업에 고정된 원문과 현재 편집된 원문을 구별해요. 현재 이력에서 읽을 수 없는 연결도 대체 본문을 추측하지 않고 명시해요.

`outline.write`는 모델에게 전체 detail 대신 `operationId`, `applied`, `atomic`, `created`, `changes`를 반환해요. `revisionAfterOperation`은 해당 작업 직후의 수정 번호이며 나중의 현재 상태를 보증하지 않아요. 기존 원자적 저장·작업키·완료 효과 처리를 유지하고 브라우저의 전체 detail 응답은 그대로예요. 기존 `task.inspect(kind:"helper")`의 `committedEffects`에서 확정 영수증의 ID·시각·알려진 도구/호출 ID를 다시 확인할 수 있어요. 이것은 원래 저장이 커밋됐다는 뜻이지, 그 뒤 내용이 그대로이거나 본문 집필까지 성공했다는 뜻은 아니에요. 세부 변경을 다시 보려면 해당 구성 항목을 읽어요. 새 작업 단위 undo나 별도 영수증 도구는 추가하지 않았어요.

`outline.write`는 create/update/move/remove를 한 호출에서 최대 200개 적용하고, 새 항목의 ref/parentRef로 계층을 만들 수 있어요. 관련 항목은 실제 ID를 읽은 뒤 연결해요. 현재 선택을 가진 구성 요청에만 상세 작문 안내를 제공하며 일반 자료 관리 요청마다 작문 지침을 추가하지 않아요.

**원문과 점검**은 현재 구성과 현재 연결된 원문을 비교하는 명시적 읽기 전용 요청이에요. 실제 전송 전까지 모델을 호출하지 않아요. 기존 data.search/read, 읽기 전용 db.query와 app.tools/app.call을 사용할 수 있어요. 점검의 앱 도구 목록과 실행은 outline.read 및 기존 본문·로어 읽기로 제한하며 쓰기는 계속 거절해요. 이 요청에서 앱 변경·독립 장면 생성 도구는 제공하지 않고 실행도 거절해요. 별도 승인 체계나 새 점검 에이전트는 만들지 않아요. 도우미 대화·사용량·점검 근거 기록은 정상적으로 저장해요.

점검의 초기 입력은 선택 구성의 작은 개요와 이어 읽기 경로, 최대 세 개 원문의 짧은 발췌예요. 초기 원문 발췌에는 입력 예산의 1/8 이내이면서 최대 1,500 추정 토큰을 사용하고 최종 입력에는 기존 모델 컨텍스트 예산 검사를 적용해요. 긴 계획이나 많은 본문 연결을 처음부터 모두 넣지 않아요. 처음 제공한 계획/원문이 일부이면 `partial`로 표시하고, 도우미가 추가로 읽은 구간은 작업 기록에 남겨요. 메타데이터를 본 것과 전문을 검토한 것을 구별해요. 점검의 이후 변경됨 표식은 페이지 버전과 분리해, 선택 구성의 상위 경로·하위 구성·관련 계획과 연결 원문 hash를 기준으로 해요. 관계없는 형제 구성 수정만으로 점검을 오래된 결과로 표시하지 않아요. 이 표식은 원문을 전부 읽었다는 증거가 아니며 `partial`과 실제 읽기 구간은 별도로 유지해요. 옛 점검의 계획 hash 판정도 그대로 읽어요.

결과는 기존 도우미 대화에 남아요. 구성 화면에는 최근 점검의 상태·대화 참조·제공 범위만 연결하고, 그 뒤 계획이나 원문이 달라지면 **이후 변경됨**을 표시해요. 옛 입력 전문을 영구 보관하거나 자동 재점검하지 않아요. 과거 집필 당시 계획을 완전히 재현하는 기능이 아니라 **현재 계획과 현재 원문**의 비교예요. 제안 적용은 새 사용자 변경 요청으로 수행해요.

## 저장·사본

구성 항목과 편집 영수증은 `outline_nodes`·`outline_batches`에, 관련 구성·원문 연결·점검 근거는 `outline_links`·`outline_writings`·`outline_reviews`에 저장해요. 지원하는 DB 형식과 백업 범위는 [데이터 정책](DATA-MIGRATIONS.md)을 따라요.

구성 항목과 원문 자체는 한 벌만 유지해요. 성공한 실행의 큰 입력은 기존 수명 정책에 따라 정리하고, 구성 수정 번호·계획 hash·source 참조 등 필요한 작은 메타데이터만 남겨요. 성공한 점검의 원문 발췌도 작업 snapshot에서 제거해요.

독립 사본·휴대용 채팅 백업은 구성 내용·계층·순서·유지 조건과 관련 참조를 새 ID로 연결해요. 복사한 과거 범위 안의 실제 원문 연결만 새 source ID로 옮겨요. 복사 시점 이후의 원문·원래 Run/예약/배치 영수증·도우미 점검 작업은 재생하지 않아요.

## 검증과 범위

`tests/outline.test.ts`, `tests/helper-outline.test.ts`, `tests/helper-workspace.test.ts`, `tests/database-schema.test.ts`와 관련 사본·원문·도우미 검사를 사용해요. 빌드 뒤 `npm run verify:outline`은 390/1440px의 구성·편집·집필·도우미 전달을 합성 프로바이더로 확인해요. 화면 폭에 독립적인 저장/실행 재접속과 점검은 대표 폭에서 한 번씩 검사해 중복 실행을 줄여요.

브라우저의 구성 목록과 상세 조회는 한 요청에서 현재 노드·진행 상태·관련 구성·원문 연결·최근 점검을 모아서 조립해요. 읽어 온 노드의 ID·부모별 조회표를 한 번 만들고 각 점검의 경로·하위 구성·원문 연결 계산에 재사용해요. 원문 수정 hash와 점검의 변경 여부는 매번 현재 자료에서 계산하고 요청 사이의 캐시나 저장 사본을 만들지 않아요. 편집 배치에서는 변경 전후 및 각 이동·삭제 시점의 현재 노드로 조회표를 새로 만들어요. 조회 회귀는 구성 규모가 늘어도 SQL 호출 수가 늘지 않는지와 원문·점검·순서·진행 상태의 동일성을 함께 확인해요.

실제 프로바이더의 작문 품질, 반전 공개 준수, 인물 동기와 문체 개선은 합성 검사로 입증하지 않아요. 모델·작품·분량·비용을 정한 별도 평가가 필요해요. 자동 재계획, 여러 회차 자동 집필, 공유 구성 템플릿, 그래프 편집기, 새로운 기억 추출이나 계층별 독립 에이전트는 이번 범위가 아니에요.
