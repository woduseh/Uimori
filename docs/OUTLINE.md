# 계층형 구성과 집필

작품의 상위 의도부터 세부 사건까지 구성한 뒤, 그 구성에 따라 본편을 집필하는 기능이에요. 기존의 "다음 장면을 요청하면 이어 쓰는" 흐름은 그대로 유지되며, 구성을 만들지 않아도 아무것도 달라지지 않아요.

## 수준

사용자가 요청한 다섯 수준을 그대로 사용해요. 정의는 [`core/outline.ts`](../core/outline.ts)의 `OUTLINE_LEVELS`예요.

| 코드 | 화면 표기 | 집필 단위 |
| --- | --- | --- |
| `theme` | 전체 주제 | 아니요 |
| `mainStory` | 메인 스토리 | 아니요 |
| `arc` | 큰 사건 | 아니요 |
| `episode` | 회차 | 예 |
| `beat` | 작은 사건 | 예 |

상위는 정확히 한 수준 위여야 해요. `theme`만 상위가 없어요. 한 요청으로 집필하는 단위는 `episode`와 `beat`뿐이에요(`OUTLINE_WRITABLE_LEVELS`). 큰 사건은 여러 회차에 걸치므로 한 번에 집필하지 않아요.

다섯 수준을 끝까지 채울 의무는 없어요. 전체 주제만 두거나 큰 사건까지만 계획할 수 있어요. 회차를 만들 때는 전체 주제 → 메인 스토리 → 큰 사건의 상위 경로가 필요하며, 상위 수준을 생략하고 회차부터 시작하지는 않아요.

## 소유와 저장

구성은 **채팅의 한 분기**에 속해요. 항목은 `outline_nodes`, 배치 요청 영수증은 `outline_batches`에 저장해요. 둘 다 스키마 v15에 추가되는 표라서 기존 DB는 버전을 유지한 채 열 때 없는 표만 얻어요(`initOutline`, 삽화 표와 같은 방식).

- 항목별 `revision`으로 수정 충돌을 막아요. 저장할 때 `expectedRevision`을 보내요.
- 서재에 저장해 여러 채팅에서 재사용하는 공유 구성은 이번 범위가 아니에요(5절 결정).
- 내보내기·복원은 `archiveTables`의 `OUTLINE_TABLES`로 등록했고, 복원 검증은 `validateOutlineArchive`가 수준 관계·상위 순환·분기 소유·요청 키 중복·연결한 장면 요청의 소유를 다시 계산해요.
- 삭제는 `chat-deletion.ts`의 채팅 전체 목록과 분기 전용 목록 양쪽에 등록했어요.

## 진행도는 저장하지 않아요

구성 항목의 진행 상태는 **저장하지 않고 읽을 때 계산해요**(`OutlineProgress`). 계획이 있다는 사실만으로 완료가 되지 않아요.

집필 단위는 기존 `scene_commands`에 연결돼요. 그 장면 요청이 실제 Run을 통해 원문을 확정하면(`status='consumed'` + `source_revision`) 비로소 `written`이 돼요.

| 상태 | 화면 표기 | 뜻 |
| --- | --- | --- |
| `planned` | 구성만 있어요 | 장면 요청을 아직 만들지 않았어요 |
| `scheduled` | 집필 예약 | 장면 요청은 있고 Run은 없어요 |
| `writing` | 집필 중 | 연결된 Run이 진행 중이에요 |
| `written` | 집필 완료 | 실제 원문이 확정됐어요 |
| `failed` · `cancelled` | 집필 실패 · 집필 취소 | 연결된 장면 요청이 그렇게 끝났어요 |

## 구성이 집필에 영향을 주는 방법

집필은 새 생성 경로를 만들지 않아요. 기존 본편 경로를 그대로 써요.

1. `POST /api/outline-nodes/:id/scene-command` — 그 항목에 장면 요청을 만들고 연결해요. 요청문은 기본으로 `회차 집필 요청: {이름}`과 그 항목의 의도로 만들며 직접 지정할 수도 있어요.
2. 기존 `POST /api/scene-commands/:id/run` — 기존 예약·CAS·단일 writer·취소·중복 규칙을 그대로 사용해요.
3. 예약 시점에 `freezeOutline`이 적용 구성을 `RunSnapshot.outline`에 고정해요.

고정하는 것은 다음 세 가지뿐이에요.

- `path`: 뿌리부터 집필 대상까지의 사슬. 여기에 상위에서 정한 의도가 들어 있어요.
- `children`: 대상의 **직계** 하위만. 더 깊은 수준은 한 요청의 입력에 넣지 않아요.
- `written`: 이 Run 자신의 원문 계보(`snapshot.history`)에 있는, 이미 집필한 다른 항목. 최대 40개예요.

형제 회차의 계획은 들어가지 않아요. `hash`로 무엇을 고정했는지 봉인해요(`sealOutlineSnapshot`).

전송 경로는 `state`·`notes`와 같은 방식이에요. `MainInput.outline`이 되고, 프롬프트에 `outline` slot 블록이 있으면 그 자리에, 없으면 현재 요청 바로 앞의 host context 메시지에 실려요. 기본 프롬프트는 바꾸지 않았으니 직접 배치하려면 프롬프트 구성에 `outline` slot 블록을 추가해요.

### 정보 공개 경계

상위 계획에는 결말이나 반전이 적혀 있을 수 있어요. `OUTLINE_CONTRACT`가 요청 계약에 붙어서 구성은 계획이며 이미 일어난 사건도, 인물의 기억도, 세계의 사실도 아니라는 것과, 마지막 `path` 항목이 지정한 단위만 쓰고 이후 단위와 상위에 적힌 결말·반전은 그 단위가 올 때까지 드러내지 않는다는 것을 명시해요. 복선 전용 엔진이나 시간 그래프는 추가하지 않았어요. 사건 순서와 서술 순서를 같게 강제하지도 않아요.

## 권한

구성 쓰기는 두 권한으로 나뉘어요.

- **사용자**(`POST /api/chats/:id/outline`): 화면에서의 직접 편집이에요. `expectedRevision`만 맞으면 자기가 고정한 항목도 바꿀 수 있어요.
- **모델**(도우미 도구 `outline.write`): 명확한 사용자 지시로 받은 허가 안에서만 동작해요. 다음은 거절하고 **충돌을 드러내요**.
  - 사용자가 고정(`fixed`)한 항목의 수정·이동·삭제 — 어떤 항목과 충돌하는지 이름을 담아 알려요. 상위 항목을 이동하거나 삭제해 보호된 하위를 우회해서 바꿀 수도 없어요. 고정은 그 항목의 문구와 존재를 지키는 것이라서, 고정한 항목 **아래에 하위를 계획하는 것은 막지 않아요**.
  - 이미 집필한 항목의 수정 — "남은 구성만 바꿀 수 있어요".
  - `fixed` 값 변경 — 고정은 사용자만 바꿔요(403).

집필한 항목의 삭제는 두 권한 모두 거절해요. 진행 중인 Run이 있는 항목은 먼저 취소해야 해요. 아직 집필하지 않은 항목을 지우면 그 하위와 예약된 장면 요청을 같은 트랜잭션에서 취소해요.

허가 판정은 기존 `directHelperGrants`를 그대로 써요. 구성/개요/줄거리 + 만들어·짜·정리·수정·바꿔 같은 명령형 문장이 `outline.write`를 만들고, 인용문·로어·모델 출력·OOC는 허가를 만들지 않아요. `outline.read`는 허가가 필요 없어요.

## 도우미 도구

| 도구 | 허가 | 하는 일 |
| --- | --- | --- |
| `outline.read` | 불필요 | 현재 분기의 구성 전체를 id·revision·고정 여부·진행도와 함께 읽어요 |
| `outline.write` | `outline.write` 필요 | create·update·move·remove를 한 번에 최대 200개 적용해요 |

`outline.write`는 새 항목마다 `ref`를 주고 상위를 `parentRef`로 가리켜서 **한 호출로 트리 전체**를 만들 수 있어요. 도우미 기본 한도(총 24회·도우미 12회)를 늘리지 않고도 다섯 수준 구성을 처리하려면 이 형태가 필요해요. 한도는 그대로예요.

`outline.write`는 원문을 쓰지 않아요. 구성만 만들라는 요청이 본문 집필로 확대될 경로가 구조적으로 없어요. 반대로 전체 구성을 만들었다고 본문이 자동 집필되지도 않아요.

같은 `operationId`로 다시 호출하면 도우미의 기존 operation 영수증이 재생을 막아요. 구성 Store도 `outline_batches`에 분기·권한·전체 변경 목록·생성한 id를 원자적으로 기록해요. 같은 `idempotencyKey`와 동일한 요청을 다시 보내면 create·update·move·remove 모두 처음의 접수 결과와 현재 구성을 돌려주며 변경을 반복하지 않아요. 이후 항목을 편집하거나 삭제했어도 예전 요청을 재확인하면서 되살리거나 덮어쓰지 않아요. 같은 키의 내용·분기·권한이 다르면 충돌이에요. 새 요청은 항목별 revision CAS를 그대로 거쳐요. 한 배치의 중복 `ref`나 일부 잘못된 연산도 전체 배치를 거절해요.

## 분기와 포크

과거 지점에서 포크하면 **포크 지점이 속한 분기의** 구성만 복사해요. 다른 분기의 구성은 따라오지 않아요. 연결은 **포크 계보 안에서 확정된 장면 요청만** 유지해요. 다른 갈래에서 나중에 집필한 회차는 계획만 남고 `planned`로 돌아가요. 포크된 Run의 `outline.written[].sourceRevision`은 새 원문 id로 다시 매핑하고 hash를 다시 봉인해요(`mapForkSnapshot`). 고정한 구성 노드 id는 원본 채팅의 값 그대로 남아요 — `forkedFrom`과 같은 성격의 과거 귀속이에요. 배치 영수증은 원래 요청 대상에 남으며 새 채팅으로 복사하지 않아요. 내보내기·복원에서는 영수증도 보존하고, 나중에 삭제된 항목에 대한 기록은 허용하되 살아 있는 다른 채팅·분기의 항목을 가리키는 영수증은 거절해요.

## 화면

채팅 메뉴 → **계층형 구성**이에요. 수준별 이름·의도·진행도를 보여주고, 하위 추가, 이름·의도 수정, 고정 토글, 삭제, 집필 단위의 `이 단위 집필`, 집필 완료 항목의 `집필한 원문 읽기`를 제공해요. 대형 그래프 편집기나 필수 입력 양식은 만들지 않았어요.

구성이 만든 장면 요청은 채팅 설정 → 상태와 문맥의 **장면 예약** 목록에도 `회차 1화 잠긴 문`처럼 나타나요. 구성 항목이 참조하는 동안은 그 목록에서 지워지지 않고, 구성에서 먼저 분리하거나 구성 항목을 지우라고 알려요.

화면은 기존 `보관된 전개`·`작업 현황`과 같은 모달 대화상자예요. 열려 있는 동안 뒤 화면은 비활성이라 도우미에게 구성을 요청할 때는 닫고 요청한 뒤 다시 열어요. 다시 열면 최신 구성을 새로 읽어요. 열린 채로 도우미가 구성을 바꿔도 자동으로 갱신되지는 않으며, 낡은 revision으로 저장하면 충돌 안내가 나와요.

집필을 누르면 장면 요청 생성과 실행 두 단계의 멱등키를 브라우저 세션에 먼저 저장해요. 공급자가 확실히 거절한 4xx에서만 키를 지우고, 불확실한 실패에서는 키를 남겨 다시 누를 때 같은 요청으로 확인해요.

## 하지 않은 것

- 여러 회차를 한 요청으로 연속 집필 — 지정 단위 실행만 해요(5절 결정).
- 집필 결과에 따른 자동 재계획 — 계획은 사용자가 바꿀 때만 바뀌어요(5절 결정).
- 서재에 저장하는 공유 구성 템플릿(5절 결정).
- 기본 프롬프트 변경, 별도 계획용 에이전트, 계획 전용 모델 역할, 삭제된 매 턴 기억 추출의 복원.
- `EditDraftKind` 확장 — 구성은 항목별 revision CAS로 충분하고, 미적용 raw JSON 버퍼가 필요한 편집기가 아니에요.

## 검증

- 서버 계약: [`tests/outline.test.ts`](../tests/outline.test.ts). 구성을 만들지 않은 기존 즉흥 집필, 다섯 수준 구성과 본문 미생성, 잘못된 상위 거절, 배치 전체의 멱등·CAS·원자성·한도, 집필 입력의 상위 의도와 선행 원문 계보, 집필 단위 제한, 사용자 수정과 원문 hash 불변, 보호된 하위의 이동·삭제, 장면 요청 재확인과 소유, 포크·영수증·내보내기·복원, 추가 표가 없는 이전 v15의 재열기, 허가 판정을 확인해요.
- 화면: `npm run verify:outline`(OUTUI01·OUTUI02 × 390/1440px). 편집 폼은 한 글자씩 입력해 포커스와 모든 글자가 남는지 확인하므로, 중첩 컴포넌트 정의로 되돌아가면 실패해요. `npm run verify:redesign`에도 필수 case와 화면 증거로 등록했어요.
- 실제 모델이 상위 의도를 얼마나 잘 반영하는지, 공개 시점을 지키는지는 **검증하지 않았어요**. 고정 응답 검사는 저장·권한·범위·입력 조립의 정확성만 증명해요.
