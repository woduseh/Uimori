# 자동 백업

작업실의 데이터베이스를 주기적으로 안전하게 보관하는 자동 백업 기능의 설정 방법, 보관 정책, 전체 복원 절차를 안내해요.

## 설정과 화면 조작

- **화면 위치**: **설정 → 데이터 관리 → 자동 백업**에서 관리해요.
- **활성화 및 저장**: 스위치를 켜고 **백업 설정 저장**을 눌러 확정해요. 기본값은 꺼짐 상태예요.
- **실행 시간과 보관 수량**:
  - 활성화 시 기본 일정: 한국 시간(`Asia/Seoul`) 매일 **03:00**에 실행돼요.
  - 기본 보관 개수: 최근 성공본 **7개**를 보관해요.
  - 사용자 지정: 실행 시간과 보관 개수(최소 1개 ~ 최대 30개)를 원하는 대로 변경할 수 있어요.
- **지금 백업**:
  - 설정 저장이나 자동 백업 활성화 여부와 무관하게 즉시 수동 백업을 생성해요.
  - 현재 설정된 보관 개수 정책이 함께 적용돼요.
- **동시 실행 방지**: 자동 백업과 수동 백업은 한 번에 하나만 만들며, 이미 백업이 진행 중일 때 추가 생성 요청이 들어오면 409 오류로 거절해요.

## 저장 및 화면 동작 규칙

- **수정 번호(Revision) 기반 일괄 저장**: 스위치 상태, 시간, 보관 개수는 같은 수정 번호(`expectedRevision`)로 함께 저장돼요. 빈 값이나 유효 범위를 벗어난 입력은 저장되지 않아요.
- **비활성화 시 화면 동작**: 자동 백업을 끄면 예약 시간 입력란만 접히며, 수동 백업에도 적용되는 보관 개수와 **지금 백업** 버튼은 그대로 유지돼요.
- **다음 백업 시각 안내**: 화면에 표시되는 다음 백업 시각은 작성 중인 미저장 초안이 아니라 서버에 실제 저장된 일정을 기준으로 표시해요.
- **설정 창 닫기**: 설정을 닫을 때 **저장하고 닫기**를 선택해도 자동 백업 변경사항을 함께 저장해요. 입력 검증이나 저장에 실패하면 창이 닫히지 않고 초안을 유지해요. (단, 서재 자료나 채팅 가져오기 파일이 선택되어 있으면 먼저 가져오기를 완료하거나 선택을 취소해야 하며, **저장하고 닫기**가 파일을 대신 가져오지는 않아요.)
- **다중 탭 충돌 처리**: 다른 탭과 설정 수정 번호가 충돌하면 **다시 확인** 버튼으로 최신 설정과 수정 번호를 불러와요. 미저장 변경을 버릴 때만 확인하고, 취소하면 작성 중인 설정을 유지해요.

## 백업 보관 및 실행 정책

- **보관 개수 축소 시 정리 시점**: 보관 개수를 기존보다 줄여서 저장해도 기존 파일이 즉시 삭제되지는 않아요. 다음번 자동 또는 수동 백업이 성공한 뒤 새 개수에 맞춰 오래된 성공본을 정리해요.
- **일회성 다운로드와의 분리**: 기존 `/api/backup`을 통한 일회성 다운로드는 이 보관 목록에 추가되지 않아요.
- **놓친 일정 보충**: 서버가 꺼져 있어서 예정된 일일 일정을 놓친 경우, 정상 재시작 직후 한 번만 놓친 백업을 보충 실행해요.
- **실패 시 동작**: 실패한 자동 실행은 즉각 재시도하지 않고 다음 일정을 기다려요. 즉시 다시 시도하려면 **지금 백업**을 사용해요.
- **서버 상태별 실행 제어**:
  - 유지보수 검증 부팅 모드와 테스트 모드에서는 백업 예약기를 시작하지 않아요.
  - 이미 시작한 자동·수동 백업은 유지보수의 진행 작업에 포함되어 완료될 때까지 기다릴 수 있어요.
  - 서버 정상 종료 시에는 현재 진행 중인 스냅샷이 끝날 때까지 대기하며, 강제 중단되어 남은 임시 폴더는 성공본으로 표시하지 않아요.

## 백업 데이터 범위와 복원 안내

- **백업에 포함되는 내용**: 전체 DB 스냅샷에는 원고, 이미지 에셋, DB에 저장된 API 키가 포함돼요.
- **포함되지 않는 항목**: 서버 환경 설정 파일(`.env`), TLS 인증서, 외부 Codex 실행기 로그인 파일까지 담은 서버 전체 백업은 아니에요.
- **보관 위치의 한계**: 같은 서버 디스크에 저장된 백업은 사용자의 실수로 인한 오삭제를 복구하기 위한 용도예요. 서버나 디스크 자체의 물리적 고장·상실에 대비하려면 백업 파일을 외부 저장소에 별도로 보관해야 해요.
- **안전한 전체 복원 절차**:
  1. 실행 중인 서버를 완전히 중지해요.
  2. 라이브 운영 DB를 UI에서 직접 덮어쓰지 마세요.
  3. 호환되는 앱 버전을 준비하고, **별도 경로의 사본**으로 DB를 열어 원고, 번역, 이미지, 설정이 정상적으로 읽히는지 검증해요. (manifest의 빠른 검사와 실제 데이터 복원 검증은 별개예요.)
  4. 검증이 완료된 사본으로 전환하여 운영을 재개해요. 이전 DB는 검증이 완전히 끝날 때까지 보관해 두세요.

## 구현 참고

- **저장 경로 및 Docker 볼륨 구성**:
  - `UIMORI_BACKUP_DIR` 환경 변수로 서버의 저장 디렉터리를 지정해요. 미지정한 로컬 설치 환경에서는 DB 디렉터리 하위의 `backups` 폴더를 사용해요.
  - 제공되는 두 Docker Compose 예시에서는 `/backups` 경로에 `UIMORI_BACKUP_VOLUME`(기본값 `uimori_backups`)을 별도로 마운트해요. 데이터 볼륨을 전환하더라도 백업 볼륨은 동일하게 유지해야 해요.
  - 새 컨테이너 이미지는 초기 백업 디렉터리의 UID 1000 소유권을 자동으로 준비해요. 이미 생성된 호스트 디렉터리를 직접 마운트할 때는 운영자가 컨테이너 쓰기 권한을 준비해야 해요.
  - 배포 파이프라인 전용 백업은 이 기능의 보관 정책과 별개로 관리돼요.
- **SQLite 온라인 스냅샷 및 검증 워커**:
  - SQLite 온라인 스냅샷을 생성한 후, 별도 Worker 스레드에서 `quick_check`, 외래 키(Foreign Key), DB 형식 및 버전을 검사해요.
  - 파일 크기, SHA-256 해시, 앱/빌드 버전을 manifest에 기록하고, 작업 디렉터리를 완료 디렉터리로 원자적으로 전환한 뒤 성공으로 확정해요.
  - 새로운 백업이 성공하기 전에는 오래된 성공본을 절대 정리하지 않아요. 디스크 공간이나 권한 문제가 발생하면 기존 성공본을 안전하게 보존한 채 실패로 표시해요.
  - 불완전하게 남은 `.partial-*` 임시 디렉터리와 다른 운영 파일은 정상 백업 목록이나 자동 삭제 대상에서 제외돼요.
- **백업 API 엔드포인트**:
  - `GET /api/backups`: 백업 목록 조회
  - `PUT /api/backups/settings`: 백업 설정 저장 (`expectedRevision` 필요)
  - `POST /api/backups`: 백업 즉시 생성 요청 (202 Accepted 반환)
  - `GET /api/backups/:id/download`: 특정 백업 파일 다운로드
  - 기존의 일회성 다운로드인 `GET /api/backup`도 유지돼요. 모든 엔드포인트는 파일 시스템 경로를 요청 인자로 받지 않으며, 기존 작업실 인증 및 유지보수 게이트를 재사용해요.
- **테스트 스위트**:
  - `npm test -- tests/backup-service.test.ts tests/database-schema.test.ts tests/personal-workspace-flow.test.ts`
  - 임시 SQLite 사본의 재열기, 이미지·원문·설정 보존, 백업 실패 후 기존 보관 파일 유지(retention), 일정 동작, 수정 번호 CAS, 중복 요청 방지, API 인증 및 유지보수 게이트를 검사해요. (실제 Docker 볼륨 전환과 물리 디스크 고장은 별도의 운영 검증 항목이에요.)
