# 자동 백업

**설정 → 데이터 관리 → 자동 백업**에서 켜요. 기본은 꺼짐이며, 켰을 때 한국 시간 매일 03:00, 최근 성공본 7개를 보관해요. 시간과 보관 개수(1~30개)를 바꿀 수 있어요. `지금 백업`은 설정 저장·자동 백업 활성화와 별개예요. 같은 작업실의 스냅샷 생성은 순서대로 실행해요.

`UIMORI_BACKUP_DIR`로 서버가 저장 위치를 정해요. 미지정한 로컬 설치는 DB 디렉터리 아래 `backups`를 사용해요. 두 Compose 예시는 `/backups`에 `UIMORI_BACKUP_VOLUME`(기본 `uimori_backups`)을 별도로 마운트해요. 데이터 볼륨을 전환해도 같은 백업 볼륨을 유지하세요. 새 이미지가 초기 백업 디렉터리의 UID 1000 소유권을 준비해요. 이미 만든 호스트 디렉터리를 마운트하면 운영자가 쓰기 권한을 준비해야 해요. 배포 전용 백업은 이 기능의 보관 정책과 별개예요.

SQLite 온라인 스냅샷을 만들고 별도 Worker에서 `quick_check`, 외래 키, DB 형식·버전을 검사해요. 파일의 크기·SHA-256·앱/빌드 버전을 manifest에 기록하고 완료된 디렉터리로 전환한 뒤 성공으로 표시해요. 성공 전에는 옛 백업을 정리하지 않아요. 공간·권한 문제는 기존 성공본을 보존한 채 실패로 표시해요. 불완전한 `.partial-*`와 다른 운영 파일은 정상 목록·자동 삭제 대상이 아니에요.

서버가 꺼져 놓친 일일 일정은 정상 재시작 뒤 한 번만 보충해요. 실패한 자동 실행은 다음 일정을 기다리며 즉시 재시도하려면 `지금 백업`을 사용해요. 유지보수 검증 부팅과 테스트 모드에서는 예약기를 시작하지 않아요. 정상 종료는 현재 스냅샷을 기다리고, 강제 중단된 임시 폴더는 성공으로 표시하지 않아요.

전체 DB에는 원고·이미지·DB의 API 키가 포함돼요. 환경 파일·TLS 인증서·외부 Codex 실행기 로그인까지 담은 서버 전체 백업은 아니에요. 같은 서버 디스크는 오삭제 복구 지점이지 서버/디스크 상실 대비 외부 백업이 아니에요.

전체 복원은 서버를 중지하고 호환되는 앱으로 **별도 경로의 사본**을 열어 검증한 뒤 전환해요. 이전 DB는 검증 완료까지 보관하고, 라이브 DB를 UI에서 덮어쓰지 않아요. manifest의 빠른 검사와 실제로 원고·번역·이미지·설정을 읽는 복원 검증은 별개예요.

API: `GET /api/backups`, `PUT /api/backups/settings`(expectedRevision), `POST /api/backups`(202), `GET /api/backups/:id/download`. 기존 `/api/backup` 다운로드도 유지해요. 경로를 요청으로 받지 않고 기존 작업실 인증·유지보수 게이트를 재사용해요.

검증: `npm test -- tests/backup-service.test.ts tests/database-schema.test.ts tests/personal-workspace-flow.test.ts`. 임시 SQLite 사본의 재열기, 이미지·원문·설정 보존, 실패 후 retention, 일정·CAS·중복, API 인증과 유지보수를 검사해요. 실제 Docker 볼륨 전환과 운영 디스크 고장은 별도 운영 검증이에요.
