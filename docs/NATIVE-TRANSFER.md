# 독립 자료 교환

독립 자료 교환(개별 백업)은 봇·페르소나·모듈·프리셋 자료를 Uimori 설정, 연결된 종속 모듈, 에셋 이미지와 함께 묶어 다른 작업실로 옮기거나 보관하는 기능이에요. Risu 형식 내보내기나 전체 SQLite 백업과 분리된 Uimori 고유의 독립 교환 규격이에요.

## 개별 자료 백업과 가져오기

### 자료 가져오기 방법
- **접근 경로**: **설정 → 데이터 관리 → 백업 파일 가져오기**를 열어요 (자료 백업과 채팅 백업이 같은 입구를 사용해요).
- **자동 판별**: 파일 확장자 대신 파일 내부의 JSON 형식과 아카이브 목차를 자동으로 분석하여 자료 백업인지 채팅 백업인지 판별해요.
- **검토 및 등록**:
  1. 파일을 선택하면 자료 목록과 에셋 요약을 화면에 미리보기로 보여줘요.
  2. 내용을 확인한 뒤 **새 자료로 가져오기**를 누르면 등록이 완료돼요.
  3. 지원하지 않거나 손상된 파일은 같은 영역에 명확한 오류를 표시하고 다시 선택할 수 있게 안내해요.
- **새 자료 원칙**:
  - 가져오기는 기존 자료를 덮어쓰거나 강제로 병합하지 않고 항상 **새 ID의 독립 사본**으로 추가해요.
  - 자료 묶음 내부의 상호 참조 관계도 새로 생성된 ID로 연결돼요. 같은 이름의 기존 자료가 있더라도 영향을 주지 않아요.
- **작업실 전체 복구와의 구분**: 전체 SQLite 백업은 서버를 종료하고 `UIMORI_DB` 환경 변수로 복원하는 기존 방식을 사용해야 하며, 이 개별 자료 가져오기 화면으로는 불러오지 않아요.

### 네트워크 재시도 안전장치
- 가져오기 도중 네트워크 응답이 끊겨 완료 여부가 불분명한 경우 선택한 파일과 요청 상태를 그대로 유지해요.
- 다른 파일을 다시 올리기 전에 반드시 **같은 요청으로 다시 확인**을 눌러 서버의 실제 반영 여부를 먼저 확인해 주세요.
- 자료 추가가 이미 성공한 뒤 목록 화면 갱신만 실패한 경우에는 추가 완료와 갱신 실패를 명확히 분리해 안내하며, 가져오기 작업을 불필요하게 반복하지 않아요.

## 자료 처리 및 호환 규칙

### 모델 및 인증 정보 처리
- **프리셋 외부 모델 조정**: 프리셋 조언자 설정에 특정 외부 모델이 지정되어 있던 경우, 새 작업실로 가져올 때 '주 모델 따르기'로 자동 전환해요 (모델이 변경된 파일은 가져오기 요약에서 명확히 안내해요).
- **인증 정보 제외**: 프로바이더 API 키나 개인 접속 정보는 백업 파일에 일절 포함되지 않아요.

### 에셋 이미지 처리
- **메타데이터 보존**: 이미지의 이름, 설명, Risu 참조 이름은 원본 그대로 충실히 보존돼요.
- **WebP 변환**: 이미지 바이트는 공통 WebP 처리 파이프라인을 거쳐 저장돼요 (이미 WebP 형식인 이미지는 불필요한 재압축을 거치지 않아요).

## 파일 형식과 제한 규격

### `.uimori` 아카이브 규격
화면에서 새로 생성하는 백업은 `.uimori` 확장자 파일이에요.

- **컨테이너**: `uimori-archive` 버전 1의 무압축 ZIP 컨테이너를 사용해요.
- **내부 구성**:
  - `manifest.json`: 자료 메타데이터 및 종속 관계 정보
  - `images/<SHA-256>.bin`: 해시 기반 고유 이미지 바이너리
- **효율적인 압축**: 이미 압축되어 있는 이미지 바이너리를 다시 이중 압축하지 않으며, 거대한 base64 JSON 문자열로 조립하지 않아요.

### 용량 및 에셋 한도
- **파일 전체 용량**: 최대 512MiB
- **메타데이터 용량**: 최대 32MiB
- **고유 이미지 수**: 묶음 내 서로 다른 고유 이미지 바이트는 최대 65,534개까지 포함할 수 있어요.
- **논리 에셋 수**: 개별 카드에 등록된 논리 에셋은 최대 12,288개까지 보존하며, 내용이 동일하더라도 이름이나 역할이 다른 이미지는 각각 독립적으로 유지돼요.
- **레거시 JSON 호환**: 과거 `.json` 형식(`uimori-native-transfer`) 파일의 검토와 가져오기도 계속 지원해요 (JSON 요청 크기 한도는 최대 256MiB예요).
- **신규 출력 API 종료**: 새 백업은 `.uimori` 아카이브로만 생성되며, 레거시 JSON 출력 API인 `POST /api/native-transfers/export`는 제거되어 404를 반환해요.

## 에이전트 및 구현 참고

### 내부 모듈과 책임 분리
- **자료 묶음 처리**: `server/resource-bundle.ts`가 사용자 자료 묶음의 직렬화 생성과 작업실 적용을 총괄해요.
- **이미지 변환**: `server/transfer-images.ts`는 묶음 내부 이미지의 WebP 변환 및 SHA-256 참조 치환만을 전담해요.
- **영수증 및 이력**: 전체 실행 이력의 임의 재현이나 신뢰 증명을 위한 별도의 영수증(receipt) 체계는 두지 않으며, 현재 저장된 자료의 상태만을 내보내요.

### 2단계 원자적 적용 파이프라인
1. **사전 검증 및 스테이징**: 업로드된 `.uimori` 파일의 목차, CRC, 이미지 SHA-256 무결성을 검사하고 이미지를 하나씩 변환·준비한 뒤 사용자에게 검토 요약을 반환해요.
2. **원자적 등록**: 사용자가 승인하면 준비된 바이너리 파일을 순차 등록해요. 검토 단계의 검증 결과와 요약을 그대로 재사용하므로 적용 시점에 동일 파일을 다시 검증하거나 이미지를 재변환하지 않아요.
3. **트랜잭션 저장**: 새 자료 레코드와 중복 요청 방지 영수증은 하나의 단일 트랜잭션으로 원자적으로 저장돼요.
4. **스트리밍 내보내기**: 내보내기 시에는 읽기 전용 DB 스냅샷에서 이미지를 하나씩 직접 스트리밍하므로, 다운로드 도중 다른 세션의 자료 변경이나 이미지 정리가 진행되어도 전송 바이트가 손상되지 않아요.

### 동시성 잠금과 준비(Staging) 파일 수명주기
- **순차 처리 잠금**: Risu 파일 가져오기와 `.uimori` 백업 준비 작업은 서버 프로세스 전체에서 1건씩 순차 실행돼요. 다른 준비 작업이 진행 중이면 큐를 늘리지 않고 완료 후 다시 시도하도록 안내해요.
- **연결 단절 처리**: 클라이언트 네트워크 연결이 끊기면 즉시 준비 작업을 취소하고 임시 산출물을 정리해요 (이미 시작된 이미지 변환은 완료 즉시 결과를 폐기하고 다음 이미지로 진행하지 않아요).
- **만료 및 정기 정리**:
  - 가져오기가 성공하면 준비 파일은 즉시 정리돼요.
  - 미완료 준비 결과는 24시간 후 자동 만료돼요.
  - 만료된 준비 파일은 쓰기가 활성화된 서버 시작 시점과 실행 중 매시간 정기 작업에서 정리돼요 (정리 실패 시 다음 주기에 재시도해요).
- **안전한 디렉터리 격리**: 업로드 및 준비 결과를 정리할 때는 SQLite DB 파일이 실제로 위치한 디렉터리 하위만을 대상으로 한정해요. 정리 대상이나 경로가 심볼릭 링크 또는 junction인 경우 건드리지 않으며, 진행 중인 준비 결과도 보존해요.

### 멱등성 영수증 보관 정책
- **일반 자료 영수증**: 일반 자료 가져오기 영수증은 최근 256개를 보관하여 중복 처리를 방지해요.
- **장기 보존 대상**: 채팅 백업, transcript, Risu 가져오기 완료 영수증과 재시도 영수증은 이 256개 순환 정리 대상에서 제외하여, 이후 일반 자료를 많이 가져오더라도 이전 가져오기 요청이 새 채팅이나 생성을 중복으로 만들어내지 않도록 완벽히 차단해요.
