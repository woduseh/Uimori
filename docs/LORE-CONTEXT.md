# 로어의 포함·배치·유지

공통 로어의 `loading`은 **포함 여부**, `loreContext`는 **고정 자료의 배치**를 정해요. `pinned`는 매 요청에 제공하고 `discoverable`은 모델이 `knowledge.search`와 `knowledge.read`로 선택해요. 읽기 도구가 반환하는 현재 턴의 위치를 임의로 옮기지는 않아요.

```json
{
  "id": "harbor",
  "title": "항구의 현재 상황",
  "description": "방문 전에 참고할 상황",
  "text": "동쪽 부두는 수리 중이다.",
  "loading": "pinned",
  "loreContext": { "placement": "scene", "group": "harbor", "order": 10 }
}
```

`placement`는 `background` 또는 `scene`이에요. 생략한 로어와 다른 고정 패키지 본문은 배경에 들어가요. 같은 패키지·부착 역할 안에서 그룹은 처음 등장한 순서를 유지하고, 그룹 안에서는 `order`가 작은 항목부터 배치해요. 같은 값은 원래 배열 순서예요. `group`은 선택적인 200자 문자열, `order`는 선택적인 -1000000–1000000 정수이며 생략값은 0이에요. 편집 폴더는 이 순서에 영향을 주지 않아요.

기본 PromptProgram은 **고정 배경 자료 → 이전 대화와 조회 자료 → 메모·고정 장면 자료 → 변동 host 정보 → 현재 입력** 순서예요. 사용자 정의 PromptProgram의 역할·순서·cache anchor는 유지해요. 실제 실행한 `references`, `bot`/`description`, `persona`, `lore`/`lorebook`, `backgroundLore`, `sceneLore` 슬롯이 이미 제공한 자료는 자동 삽입에서 제외해요. 꺼진 블록이나 선택되지 않은 조건 분기는 자료를 제공한 것으로 계산하지 않아요. 사용자가 같은 본문을 여러 슬롯에 직접 작성한 중복까지 제거하지는 않아요.

변동 host 정보에는 `discoverable` 로어가 **목록**으로만 실려요. 항목마다 ID·revision·종류·제목과 설명을 160자로 줄인 요약이 들어가고 본문과 `loreContext`는 빠져요. 고정 자료는 이미 본문을 보내므로 목록에는 제목만 남기고 요약은 비워요. 목록 전체는 직렬화 기준 24,000자 예산 안에서 앞에서부터 싣고, 예산을 넘어 빠진 항목은 `catalogPage`로 개수를 알리며 `knowledge.search`로 찾도록 안내해요. 요청 contract에는 쓰기 전에 이번 요청에 필요한 항목을 골라 `knowledge.read`로 읽으라는 안내를 함께 넣어요. 이 압축 목록은 `uimori-prompt-2`로 컴파일한 새 Run에만 적용돼요. 2026-09-14 이전에 컴파일된 Run(`promptCompilation.compilerVersion`이 `uimori-prompt-1`)을 검증하거나 후보로 다시 돌릴 때는 이전처럼 항목마다 전체 메타데이터를 100개까지 싣던 목록을 그대로 재현해요.

## 키워드 활성화

[패키지](PACKAGES.md)가 `loreActivation.mode = 'keyword'`이면 `activation` 규칙이 있는 로어는 `loading`이 아니라 Risu 스냅샷의 활성화 엔진(`activateLore`, RisuAI `loadLoreBookV3Prompt`의 순수 함수판)이 정해요. 예약 시점에 고정된 대화(오래된 순, 이번 요청이 마지막)를 패키지의 `scanDepth`만큼 뒤에서 훑어 키·보조 키·selective·정규식·`@@` 규칙을 Risu와 같은 규칙으로 판정하고, 재귀 검색과 확률·우선순위·`insertorder` 정렬까지 같아요. 켜진 항목은 그 Run의 고정 자료가 되어 `loreContext` 배치를 따르고, 켜지지 않은 항목은 그 Run의 조회 목록과 읽기 도구에서도 빠져요. 규칙이 없는 로어와 `discoverable` 모드 패키지는 이 절의 영향을 받지 않아요.

활성 예산은 위 표의 **조회 자료 문자**(`maxRetainedChars`)예요. Risu가 토큰으로 세는 자리에 UTF-16 코드 단위 길이를 넣으므로 켜진 항목을 `insertorder` 순으로 더해 이 값을 넘는 항목부터 제외하고, 값이 0이면 규칙 있는 로어는 하나도 켜지지 않아요. 켜진 로어는 고정 자료 합계에도 포함되므로 고정 자료 문자 한도를 넘으면 같은 `LORE_PINNED_BUDGET_EXCEEDED`로 알려요. 조회 자료 유지 기능과 수치를 공유할 뿐 켜진 로어가 유지 구간을 소비하지는 않아요. 결과는 [snapshot 영수증](RESERVATION-SNAPSHOTS.md#snapshot-영수증)에 고정되어 후보·포크·복원에서 다시 판정하지 않고, 확률 지시문은 run seed로 결정적이에요. `keep_activate_after_match` 계열이 남기는 활성 상태 변수는 저장하지 않으며 위치 지시문은 적용하지 않아요.

## 모델 선별

[패키지](PACKAGES.md)가 `loreActivation.mode = 'model'`이면 본문 요청 전에 호스트가 문맥 정리 모델을 한 번 불러 그 패키지의 `discoverable` 로어 가운데 이번 턴에 필요한 항목을 고르게 해요. 모델에게는 항목마다 ID·제목·160자 요약·본문 문자 수를 담은 목록과 최근 대화 12개(항목당 1,000자), 이번 요청(4,000자), 문자 예산을 보내고 `{"selected": [ID 순서]}` 형식의 JSON만 받아요. 목록은 직렬화 기준 200,000자에서 자르고 잘린 경우 영수증에 `partial: 'catalog'`로 남겨요. 고정 로어는 이미 본문을 보내므로 후보가 아니며, Risu `activation` 규칙은 `discoverable` 방식과 똑같이 무시해요.

호출은 채팅에 고정된 **문맥 정리 모델**(`contextModel`)을 `context` 역할로 사용해요. 미지정이거나 비활성이면 다른 모델로 대체하지 않고 선별을 건너뛰어요. 이 호출은 작업당 모델 호출 한도(`maxCalls`) 한 회를 쓰고 본문 호출 한 회를 남겨요. 남은 예산이 모자라거나 공급자 호출·출력 형식이 실패하면 그 패키지는 **결정 없음**으로 남아 모든 로어가 자기 `loading`대로 동작해요. 어떤 실패도 본문 생성을 막지 않아요.

예산은 [채팅 정책](#채팅-정책과-새-장면)의 **조회 자료 문자**(`maxRetainedChars`, 기본 48,000)와 **조회 자료 구간**(`maxRetainedEntries`, 기본 64)이에요. 모델이 준 순서대로 본문 문자 수를 더해 예산을 넘는 항목부터 `budget` 이유로 제외하고, 값이 0이면 하나도 고르지 않아요. 목록에 없는 ID는 `unknown` 이유로 기록만 하고 아무것도 결정하지 않으며, 같은 ID를 여러 번 준 경우 처음 한 번만 세요.

고른 로어는 그 Run의 고정 자료가 되어 `loreContext` 배치를 따르고, 고르지 않은 로어는 조회 목록과 읽기 도구에 그대로 남아요. 키워드 활성화와 달리 어떤 항목도 목록에서 빼지 않으므로 선별이 놓친 항목을 모델이 직접 읽을 수 있어요. 결과는 [snapshot 영수증](RESERVATION-SNAPSHOTS.md#snapshot-영수증)에 고정되어 후보·포크·복원에서 다시 부르지 않아요.

## 턴 사이 조회 자료 유지

완료된 메인 Run의 성공한 `knowledge.read` 결과를 당시 불변 자료로 다시 계산해 검증해요. 실제 읽은 UTF-16 구간만 다음 Run에 고정하고 검색 metadata, 읽지 않은 나머지 본문, 실패·취소된 Run, 다른 분기, 보조 역할의 읽기는 가져오지 않아요. `skills.load`, `notes.read`, `story.read`는 이 로어 유지 기능의 대상이 아니에요.

유지된 자료에는 ID·revision·본문 hash·읽은 범위, 처음 읽은 원문 ID/hash·Run·call ID를 붙여요. 처음 읽은 원문의 assistant 메시지 직전에 **이전에 읽은 참고 자료**라는 별도 사용자 역할 메시지로 넣어요. 실제 대화나 새 tool result로 기록하지 않으며, 과거 opaque continuation·도구 호출을 재실행하지 않아요. 기존 구간은 그대로 두고 새로 읽은 미포함 구간만 추가해요. 최근 사용 정보는 정리 판단에만 쓰고 모델에게 보내는 기존 메시지는 바꾸지 않아요.

M2의 최근 이력에서 원래 위치가 빠지면 여전히 유효한 자료를 최근 이력 앞에 둬요. 별도 전체 문맥 planner가 `context-summary` 메시지를 제공하면 그 요약 뒤·최근 이력 앞에 두며 요약 본문은 변경하지 않아요. 이 경계 이동은 문맥 정리에 따른 변경이며 모든 턴의 요청 접두부가 항상 동일하다는 뜻은 아니에요. 자료 본문을 매번 요약하는 별도 모델 호출은 추가하지 않았어요.

## 채팅 정책과 새 장면

채팅 설정의 로어 문맥에서 다음 값을 저장해요. 이는 전체 모델 입력 토큰 한도와 별개인 **자료 문자·구간 상한**이에요.

| 항목 | 기본값 | 허용 범위 |
| --- | ---: | ---: |
| 조회 자료 유지 | 켬 | 켬/끔 |
| 조회 자료 문자 | 48,000 | 0–200,000 UTF-16 코드 단위 |
| 조회 자료 구간 | 64 | 0–256 |
| 고정 자료 문자 | 200,000 | 1–2,000,000 UTF-16 코드 단위 |

이 값은 최적 품질이나 공급자 tokenizer를 측정해 정한 수치가 아니에요. 이모지 하나는 2개 코드 단위일 수 있어요. 고정 자료 합계에는 첨부 본문·인물 정보·고정 로어·위치를 별도로 지정하지 않은 패키지 지침을 포함해요. 기본 시스템 지침, 사용자 프롬프트, 별도 위치의 지침, 대화·도구·메모을 모두 합친 최종 입력 길이는 이 상한과 달라요. 기존 compiler와 provider 형식 제한도 계속 적용해요.

조회 상한을 넘으면 오래 사용하지 않은 구간을 통째로 제외해요. 제외한 구간을 다음 턴에 과거 이력 재검색으로 되살리지 않아요. 모델이 다시 읽으면 새로운 성공한 읽기로 포함할 수 있어요. 고정 자료 상한을 넘으면 HTTP 409 `LORE_PINNED_BUDGET_EXCEEDED`로 알려요.

전체 입력 planner도 이전 대화를 뺀 고정 입력이 너무 크면 같은 순서로 조회 구간을 정리해요. 진단 이유는 `overall-context-budget`이며 이후 턴에도 제외 결과를 유지해요. 자동 대화 요약과 함께 처리하는 순서는 [입력 한도 문서](CONTEXT-LIMITS.md)를 확인해요.

입력창 하단 **더보기 → 다음 생성에서 조회 로어 제외**를 고르면 이번 생성의 조회 문맥을 비워 시작해요. 다음 장면에서 새로 읽은 자료는 다시 유지해요. 장면을 추측하는 모델을 호출하지 않아요. 이 선택도 Run의 idempotency payload에 포함하므로 응답 유실 후 재확인으로 다른 요청이 생기지 않아요. 선택한 경우에만 입력창 안에 **조회 로어 제외 ×** 칩을 표시하며 전송 전에 해제할 수 있어요. 서버가 요청을 수락한 뒤에만 화면의 선택을 해제해요.

## 무효화·미리보기·보관

새 Run은 자료 ID/revision/hash와 메인 역할 허용 범위, 실제 원문 ancestry/hash, 사용자 메모을 다시 확인해요. 페르소나 없음 선택·자료 개정·첨부 해제는 해당 구간을 제외하고, 그 읽기 당시의 원문이나 선행 원문 수정·메모 변경은 그 문맥에서 얻은 조회 자료를 무효화해요. 고정 자료가 된 본문은 조회 사본을 제외해요. 과거 Run snapshot은 수정하지 않아요.

로어 미리보기는 저장된 자료·프롬프트와 정책 초안으로 같은 선택·조립을 실행해요. DB·Run·조회 기록·상태·난수를 변경하거나 모델을 호출하지 않아요. 다른 채팅 설정의 미저장 초안까지 반영하지는 않아요. 미리보기와 Run 진단에서 유지 구간·문자·정리 이유·출처를 볼 수 있어요.

포크는 실행 tool log를 복제하지 않고 검증된 읽기 증거를 새 원문/Run/자료 ID에 맞춰 복제해요. 보관 복원은 당시 원문과 읽기 범위뿐 아니라 바로 이전 Run의 유지 자료·새 성공 읽기로 가능한 전이인지 검사해요. 추가 예산 정리는 순서를 유지한 통째 항목 제외만 허용하고, 앞서 reset·예산 정리로 제외한 오래된 읽기는 되살리지 않아요. 원본 채팅 없는 독립 포크도 복원할 수 있어요. 나중에 수정된 원문이나 메모 변경의 **과거 증거 보존**과 **현재 요청에서 다시 사용할 권한**은 별도로 검사해요. 보관 파일 전체를 신뢰할 수 있는 서명으로 인증하는 기능은 아니에요.

구현은 [선택·유지](../server/lore-context.ts), [범위·배치](../core/lore-context.ts), [보관 검증](../server/lore-context-archive.ts), [요청 조립](../server/prompt-snapshot.ts)에 있어요. 합성 검증 결과는 [작업 결과](../project-plan/LORE-CONTEXT-RESULTS.md)에 기록해요. 실제 모델의 설정 준수율·lost-in-the-middle 완화·cached input 사용량·청구액은 별도 실모델 평가가 필요해요.
