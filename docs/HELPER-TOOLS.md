# Helper data and app tools

The helper exposes three Uimori tools when the Linux runner is configured: `data.exec`, `app.tools`, and `app.call`. `data.search`, `data.read`, and `db.query` are discoverable app operations rather than separate provider tools. They remain available through `app.call` and the `uimori call` CLI. Setups without `UIMORI_SHELL_ROOT` and explicit outline reviews expose only the two gateways; review discovery and dispatch remain read-only. The preferred general-purpose inspection path is `data.exec`. Existing app operations include resource saves, chat options, lore overrides, notes, outlines, context summaries, and reading previously saved independent scenes. Codex uses the same compact native dynamic tools within one thread and turn per task; other providers retain their own tool transport.

The writer, advisors, and translation jobs retain their existing source-scoped tools. A helper's live cross-chat SQL access is not automatically inherited by those roles. Conversation summarization still reads its complete selected source prefix, not keyword search hits.

Non-Codex helpers and advisors with history/catalog context send that unchanged reference data in a first user-content block, before the current source, controls and question. Selected drafts and prior consultation updates remain in the current-source block. No context is dropped or promoted to system instructions. Anthropic and Responses mark the reference boundary when automatic or explicit caching is selected; automatic Responses anchors require reviewed explicit-cache support. Empty reference requests retain the existing tools/instructions anchor. Unset and disabled modes add no reference anchor, native authored prompt boundaries and signed continuations stay intact, and Codex retains its own cache policy while its serialized input places history before the current question. This establishes a reusable prefix, not measured cache hits or billing savings. Actual reuse remains provider-reported; see [model cache settings](MODEL-PARAMETERS.md#캐시-위치자동-배치유지-시간).

## Linux data workspace

`data.exec {command, timeoutMs?}` executes noninteractive Bash in a reusable `shell-runner` Compose service (with `rg`, `jq`, Python 3 and Node). Multiple searches, transforms and scripts can run in a single call without forwarding their intermediate results into the model. The runner has no network, application database mount, application environment, or credentials. Compose shares only a dedicated workspace volume and two local Unix sockets. The app owns the database and builds each helper task's files on the first shell request.

Read `INDEX.md` and the `library/index.jsonl`, `chats/index.jsonl` catalogs first. The task-local `GUIDE.md` explains data ownership, Risu authored vs derived fields, and when an app read is live instead of frozen; consult it when unfamiliar with a resource. The guide is compiled with the server and is not an additional provider tool. Saved content and prompt resources have canonical `library/<id>/resource.json` files; `lorebook.jsonl` is derived for fast name/content search. Saved chat scene exports appear as `chats/<id>/scenes/<source-id>.txt`; `chats/<id>/scenes.json` has ordered scene metadata and is refreshed only for confirmed projected edits. `current/scenes.json` indexes the frozen task-admission ancestry (including disabled scenes) and never updates with live saves. Both expose UTF-16 `charCount`, UTF-8 `byteCount`, and bounded `preview`, which is not full-source coverage. Reserved editor, current-writing and conversation snapshots are also available for inspection. Use `scratch/` for intermediate calculations. All paths in the workspace are plain files, not an emulated shell or filesystem.

The CLI is a small adapter to the same application dispatcher as `app.call`:

```sh
uimori tools '{"names":["resource.read","resource.patch","db.query"]}'
uimori call db.query '{"sql":"SELECT COUNT(*) AS count FROM agent_resources"}' > scratch/count.json
uimori call resource.patch --input scratch/patch.json
python3 prepare-arguments.py | uimori call resource.patch --input -
```

`uimori tools [JSON | --input <file|->]` accepts the same discovery arguments as `app.tools`. `uimori call <operation> [JSON | --input <file|->]` accepts one JSON argument object, defaults to `{}`, and writes the operation's result as JSON to stdout. App errors return a nonzero exit status and the existing structured error; malformed local arguments exit with status 2. Use `uimori --help` for syntax. Scripts can query, filter and perform several app operations without sending intermediate data back to the model. These calls retain the existing task scope, editor-draft protection, revision checks, save effects and operation identity; the CLI contains no separate storage implementation. App operations are discovered on demand, and recursive `data.exec` calls are not app operations.

Confirmed CLI effects are included in the outer shell result even when stdout is redirected. Saved operations retain durable helper receipts. Notes, context edits/compaction, options and lore updates record those receipts in the same transaction as their existing save, so a later response failure cannot make the task eligible to replay a completed write. Cancelled compaction does not create a successful save receipt. An unexpected write failure blocks later bridge calls in that execution and stops the task for outcome inspection. No CLI request is automatically replayed. Shell completion, cancellation and timeout also abort and settle its in-flight app calls.

Editing an exported file changes only the task's working copy. To save, use `uimori apply library/<id>/resource.json` or `uimori apply chats/<id>/scenes/<source-id>.txt` inside a shell call. The application handles revision checks, existing save effects and helper operation receipts. Successful saves refresh that canonical file; concurrent external edits fail rather than silently overwrite them. Derived indexes and reserved editor snapshots are not apply targets. The `app.call` gateway still handles higher-level saves and operations. After successful app mutations, exported canonical files are refreshed when still locally unmodified.

For content, `title`, `description`, and `text` are derived from the native card/module; edit the `authoredContentPaths` in `manifest.json`. JSON formatting alone is a no-op. Edits that normalize back to the unchanged saved model are rejected with `SHELL_NO_AUTHORED_CHANGE`, preserving the local file and leaving revisions and undo unchanged. Successful apply returns `receiptId`, the saved revision, `contentHash`, and up to twenty actual `changedPaths`; `changesTruncated` marks omitted paths. `normalizedPaths` identifies fields normalized by the save (excluding the automatic package revision), with its own truncation flag. These results describe saved data, not the proposed file. Native resource saves use the existing helper undo provenance and task receipt attribution. A post-commit projection/notification failure returns a saved result with a warning, never a false failed save.

New content/preset resources created or cloned through `app.call` are added to the task files and catalog. Clean existing files refresh after app writes; dirty files keep their original base and local edits. A stale apply returns `SHELL_REVISION_CONFLICT`. Use `uimori refresh <path>` to fetch the latest saved data: clean files update in place; dirty files remain unchanged and the returned `latestPath` names a separately editable copy under `scratch/refresh-*/`. Compare the draft with that copy, reconcile into `latestPath`, then apply it. Its current revision/hash become the save guards, so another concurrent change still conflicts. An exact public `nextRead` also permits recovery through `app.call`. Repeating apply on the stale draft does not refresh its base. Refresh performs no database writes or automatic merges. Scene apply/refresh use the same current-chat ancestry check as app scene operations: if a replacement response removed the exported scene from the current story, its old working file remains intact but cannot be refreshed or saved as a current scene.

A shell call defaults to ten seconds (maximum thirty). It is synchronous: timeout, caller cancellation, normal shell exit, and runner shutdown terminate remaining children in that execution's process group. Deliberate process-group escape is not a supported background-job interface. The returned preview stays within 16KB and shows the head and tail when truncated; every result includes its complete `scratch/exec-*.log` path. Use `rg`, `sed`, `tail`, or a short Python script to filter that file. The helper budgets shell result size separately from command size; oversized serialized output retains execution status and directs a smaller log read, never a replay of the command. Completed read metadata retains the log path and execution status across compaction while the task workspace exists.

A runner transport failure can follow a committed apply. It reports an unknown outcome plus already confirmed `applied` receipts and stops the task for outcome inspection. Cancellation never implies that an earlier completed save was undone. Task working directories are removed at normal completion or cancellation; process crashes can leave files for manual cleanup. The runner is optional for development setups without `UIMORI_SHELL_ROOT`; the app gateways and their operations remain available.

## Search and partial reads

Use the `data.search` app operation for exact-reference factual lookup (`app.call` or `uimori call data.search`). The JSON examples below are operation arguments. It searches authored scalar fields once rather than returning the entire editing model with duplicate projections. Native content uses its card/module fields; the same description is not also repeated through `content.text` and `package.body`. Prompt programs and unsaved editor fields are searchable too. Search does not execute native CBS/Lua or infer facts from scripts. Use discovered app reads, such as `knowledge.read` and `chat.lore`, for their established effective-context contracts.

```json
{"scope":"library","query":"하린","kinds":["bot"],"patterns":["나이","Age","years old"],"match":"any"}
```

Whitespace-separated `query` terms must all match title/ID/kind or, in the library, the category (`bot`, `persona`, `module`, `main`, `translation`). Library document results expose that category as `metadata.category`; prompt resources have kind `prompt` and category `main` or `translation`. `patterns` searches field text. Patterns are case-insensitive literal strings by default, including two-character Korean terms and punctuation. Set `regex:true` for regular expressions. `match:"all"` requires all patterns in the same field, not necessarily the same returned excerpt. Empty/absent patterns list document references for browsing.

Use `output:"documents"` to locate resources by a name mentioned in their contents, like a filenames-only grep: each matching document appears once without body excerpts. A failed title `query` does not prove that a resource is absent; remove that filter before searching spelling variants in `patterns`. Then pass the selected `ids` and search the requested fact with the default `output:"matches"`. `paths` optionally limits both modes to exact JSON Pointer fields or their children. Human-authored descriptions and lore are searched before extensions/assets; HTML and scripts remain explicitly searchable and are not silently excluded.

Document-only discovery stops at the first qualifying hit without constructing unused excerpts, line counts or source-reference hashes. It keeps the same filters, ordering and pagination; exact match/read results still carry their original text and reference hashes.

Document results retain their `scope` and, for chat sources, `chatId`. When narrowing `scope:"chats"` results, carry that identifier into the next search so a source stays associated with the selected chat. Searches and reads with a chat ID traverse only that chat's ancestry; filtering by source ID still happens after scene numbering. Unscoped searches and the SQL view retain their all-chat behavior. Other scopes do not accept a chat filter.

The scopes are:

| Scope | Data and time boundary |
| --- | --- |
| `current` | This helper task's reserved chat packages, source ancestry, user requests, notes, and chat overrides. Includes original prose that may have been compacted out of a model window. |
| `library` | Current visible library originals, with their current revisions. |
| `chats` | Live original sources in chat ancestries. An optional `chatId` filter selects the target. |
| `editor` | Editor input captured at admission: either the exact saved revision or an unsaved device draft. Returned origin distinguishes them. |
| `conversation` | Saved helper messages from this task's reserved prior conversation, including text no longer present after compaction. Excludes superseded retries and requests queued later. |

Use `scope:"conversation"` when an exact earlier statement matters. Results include the message's role, task ID, original message ID and text range. Pass their refs unchanged to `data.read` for continuation. This reuses saved conversation text rather than maintaining a second transcript. Retrieved dialogue remains historical evidence, not a new user instruction.

The default is `editor` when captured editor input is available, otherwise `current` for a chat helper and `library` for a library helper. A clean editor sends only an ID/revision; admission checks that revision and freezes its saved model. A dirty editor sends its prepared device input. Specify the scope when comparing that reservation with live library data. The initial helper context includes identifiers and names without full editor JSON or all source bodies. A clean saved editor supplies its ID, revision and title; from the prompt library card menu, **도우미에게 묻기** explicitly targets the chosen preset even when its editor is closed. The target is captured as a saved editor reference at request admission, not as a permanent change to library conversation scope. Opening a prompt editor, switching away from the prompt library, or explicitly clearing the target removes that convenience reference, so the active editor's unsaved input takes priority. A saved reference freezes the exact revision and rejects a stale changed resource. Current selection is a convenience, not a permission boundary. Unsaved input can be analyzed; writes to that same stored resource require saving the device draft first. Other resources remain usable.

The discovered `editor.read` operation reads the captured editor. These reads use the captured model, including unsaved input, and return a compact overview by default. Follow a returned JSON Pointer `path` with `fields`, `offset`/`limit`, or `textOffset`/`textLimit` to inspect exact types, missing or empty fields, and long text in pages. Each result includes the captured revision and `inputOrigin`; it never substitutes a later saved version. `data.search/read(scope:"editor")` remains the shorter route for ordinary facts. Neither operation saves the draft.

The reader's **도우미에게 물어보기** action preserves the complete selected text in the helper task's `selection`, including its source ID and hash. It does not copy the passage into the current model request a second time or replace an existing request draft. An empty draft receives a short review request. The saved conversation retains the selected passage and source identity for follow-up turns after completed-task input cleanup; the displayed and editable request remains the user's exact text. Requests and selections each accept up to 2,000,000 UTF-16 units, matching stored prose; oversized device input is retained with an explicit message. The actual model context budget still applies without silently truncating selected text.

Search can filter `kinds` and `ids`. Resource kinds include `bot`, `persona`, `module`, and `prompt`; chat sources use `chat`, notes use `note`, unsaved input uses `editor`, and chat overrides use `override`. Explicit author notes and imported-memory claims have distinct metadata. A conflicting override is identified as conflicting rather than silently presented as an applied fact.

Each hit contains an exact `ref`, source `origin`, an original-text excerpt, UTF-16 `range`, `matchRange`, `line`, `totalChars`, and continuation information. Chat metadata includes its scene number and head. `context` counts surrounding UTF-16 units, not lines. Copy a returned reference unchanged:

```json
{"refs":[{"scope":"library","kind":"bot","id":"<returned-id>","revision":7,"field":"/card/description","hash":"<returned-hash>"}],"offset":120,"limit":1200}
```

An empty reference field denotes a document directory. Read it to obtain paged field references, then read the needed field. Field names are JSON pointers, not executable paths. A live revision/hash change yields `DATA_SOURCE_CHANGED`; search again rather than silently reading a different version. Returned source text and offsets are not normalized or rewritten, and surrogate pairs are not split.

`data.read` always accepts `refs` (one to sixteen). A single read still uses a one-item array. Each entry returns its own outer `ref` and `read` or `error`; a successful `read` does not repeat that same reference. Reuse the outer `ref` for continuation. A shared text offset/limit applies to all entries. Mixed directory and text reads work with omitted limits. A non-null `nextIndex` identifies refs not returned because of the batch output budget. Submit `refs.slice(nextIndex)` in another call; `nextIndex` is not a text offset. Source-specific `nextOffset` still indicates unread content inside each field.

Search results page by matching windows. Later matches in the same long field remain discoverable. Follow `nextOffset`; `complete` means the selected search traversal is complete, not that the contents of every excerpt have been read or that a fact is absent. Different aliases, omitted ranges, or a different scope can still matter. Do not reread a full bot merely because a bounded excerpt was returned when the supplied evidence already answers the question.

Search defaults to five results, at most fifty, with at most eight patterns. Search responses fit 8,000 serialized UTF-16 units including metadata; `complete:false` and `nextOffset` expose the remaining page. Excerpts are at most 2,000 UTF-16 units. Each text read defaults to 4,000 and accepts at most 10,000 units; directories default to twenty fields, at most fifty. Directory/SQL result assembly retains its approximately 16,000-character output budget. References, metadata, and JSON transport overhead are separate from text length.

## Editing saved scenes

`chat.read` returns current ancestry IDs/hashes plus visible `sceneNumber` (starting with the first **enabled** scene, which may be an introduction), `originalLength` in UTF-16 units, and `sceneEnabled`. Hidden scenes retain their ID but use `sceneNumber:null`, so they do not shift the visible numbering. Pass `includePreview:true` to add up to 60 local tokens of original text per scene; previews are omitted by default and do not label an entry as Greeting or provide a translation length. This metadata helps identify the target `sourceId` before reading or editing.

Discover `scene.search`, `scene.read`, `scene.patch`, `scene.patchMany`, `scene.versions` and `scene.restore` through `app.tools`, then execute through `app.call`. Discovery adds no provider-facing tools. These operations use live saved scenes in the selected chat, unlike the frozen ancestry returned by `story.read`. Locate a source ID with chat/story/data reads; a scene number is local to its chat, not a write identifier. The host checks current chat ancestry before reading or saving. Optional `chatId` selects another chat without changing the helper conversation's default scope.

`scene.read` requires a `sourceId` and explicit `target` (`original` or `translation`). It returns editable stored text, not rendered HTML or a CBS display transformation. Read long text using its returned continuation rather than treating one page as the whole scene. For nonzero offsets (including random access), supply `expectedRevision`, `expectedSourceHash`, and `expectedTextHash` from the same read; missing guards return correctable `SCENE_PAGE_GUARDS_REQUIRED`, while stale values still reject mixed versions. Its `editTarget` supplies the expected revision and source hash for saving. Translation reads use the same usable completed-result projection as the Reader, including a previous completed translation while a new attempt is pending; the displayed result identity is distinct from the latest revision used for save conflicts. Continuations also bind the exact text hash, so completion during paging cannot mix two translations.

`scene.search regex:true` executes case-sensitive Unicode regular expressions in the existing memory- and time-bounded read-only data process, not the main transaction. It searches the same live editable scene scope, returning literal matched text (up to 1,000 characters), UTF-16 ranges, bounded context, per-match `editTarget`, and guarded page continuations. Matches longer than 1,000 characters have `truncated:true`; read the exact text by `scene.read` before constructing a patch. Zero-width matches are ignored and regex matches are non-overlapping (unlike overlapping literal searches). For a single scene, regex search also accepts the same optional source/text hash guards as literal search. Matched text and context excerpts preserve whole Unicode characters. The isolated search result is advisory; `scene.patch` always checks the live guarded base before saving.

For multi-scene literal editing, omit `sourceId` in `scene.search`: it scans enabled scenes owned by the selected chat in ancestry order (including disabled scenes only with `includeDisabled:true`), excluding fork-parent scenes that the helper cannot edit. Results include per-match `editTarget`, `matchedScenes`, `scannedScenes`, `excludedScenes` and `unmatchedTranslations` when searching translated text. The `searchHash` snapshot guard covers the current ancestry, search patterns and all searchable scene versions, and `nextSearch` retains it across bounded pages; changing the patterns requires a fresh search. An absent translation is skipped; an old cursor fails rather than mixing versions. No search index or full scene bodies are sent to the model. `scene.patchMany {items}` accepts 1–16 distinct `scene.patch` requests with each source's guards. Every item validates and commits inside one transaction or all are rolled back; one scene cannot appear twice. Returns per-item results and changed `sourceIds` for reader notification. It does not provide an automatic grouped scene undo.

`scene.search` accepts optional `sourceId`, `target` (`original` or `translation`) and 1–8 case-sensitive literal `patterns` (maximum 256 characters each). It searches **live saved scenes**, not the frozen `data.search scope=current` projection, returning original UTF-16 `start`/`end` offsets and per-match `editTarget` guards for `scene.patch`. Single-scene literal search additionally reports `counts` per pattern (including overlapping matches). Results are ordered by pattern index then text offset within each scene, with chat-wide searches in ancestry order. Match-index `offset` and `limit` default to 0/10 (max page 20); `context` defaults to 80 characters (max 120). Copy `nextSearch` unchanged for more matches. If the helper read budget reports `HELPER_READ_TOO_LARGE`, retry its narrower `nextRead` (same search and match offset), not the entire scene. Nonzero offsets without snapshot guards return `SCENE_SEARCH_GUARDS_REQUIRED`; a changed scene requires restarting. Regex is opt-in via the isolated read-only worker; derived HTML and automatic editing are not supported.

`scene.patch` accepts either a complete `text` replacement or literal `changes` (`oldText`, `newText`, optional `expectedCount`). Each nonempty old excerpt must match exactly `expectedCount` literal occurrences in the saved base text (default 1); all occurrences are replaced only if they are **nonoverlapping**. Overlaps within one pattern or across change items are rejected. Whitespace-only excerpts are valid, for example to normalize a unique run of blank lines. All counts and ranges validate against the **same pre-edit text** before one save; an invalid or stale edit leaves the whole scene unchanged. No unchecked replace-all or regex-based write is provided; for multiple guarded scenes use `scene.patchMany`. Explicit requests to edit include saving; review and proposal requests do not. Full rewrites require the complete source and a complete response, never a silently truncated page or output.

For a source-format correction that must preserve an existing translation, `scene.patch` (and each `scene.patchMany` item) accepts an optional `translation` object containing a full, independent `scene.patch`-shaped translation target and its exact pre-edit guards. The host verifies both inputs before saving, invalidates old dependent jobs as usual, and writes the reviewed translation as a new manually edited completed result bound to the **new** source hash in the same transaction. The translation is not silently kept or guessed: both targets must be explicitly supplied, and one conflict rejects all changes. Translation images and in-flight attempts follow existing edit invalidation rules. This does not make arbitrary original edits semantically safe for translation reuse.

Scene and retained-version text reads reject offsets beyond the selected text rather than reporting a completed empty page. An offset exactly at the end is valid. If the helper round output budget rejects a scene page, its `HELPER_READ_TOO_LARGE` recovery keeps the same chat, source, target/version, offset and guards while reducing the page limit. Execute that public `app.call` request unchanged in the next round.

The existing source and translation save paths own revision checks, preservation, job invalidation and illustration placement. HTTP and helper edits share post-commit cancellation of superseded jobs and reader notification. A source edit makes old translation jobs stale; saved execution inputs remain unchanged. Existing summary source-hash checks determine whether a previous summary is usable; scene editing does not author a replacement summary. The helper returns a compact saved receipt rather than echoing the whole manuscript. Mutation receipts use host-owned task/call identity, and changed source revisions reject stale new calls.

`scene.versions` exposes metadata for the original and the two retained original edits, with bounded text reads for a selected version. For random offsets in a retained version, use `editTarget.expectedRevision` and `editTarget.expectedSourceHash` from that text page, but set `expectedTextHash` to its `textHash` (the retained version's content, not the current original). Following `nextRead` unchanged avoids assembling these guards manually. `scene.restore` saves a retained original version as a new edit after checking the current source revision/hash. This does not delete intervening history or restore translations. Task-pinned older text is not exposed as an editing archive. Translation restoration, automatic retranslation, scene titles and persistent writing options are outside these operations.

Reader drafts remain in their existing device-local editor state. If a helper changes their saved base, the existing conflict UI preserves the draft and requires reconciliation. Scene tools do not read unsaved Reader drafts or track drafts across tabs. Separate resource-editor draft protection still applies to resource mutations.

## Read-only SQL

Call `db.query` without `sql` to discover actual view columns and examples. Unknown SQL columns return correctable `DATA_SQL_UNKNOWN_COLUMN` and prompt schema discovery, not an automatic SQL rewrite or replay; other SQL errors and authorization denials keep their existing classification. The server supplies connection details; neither database paths nor credentials are tool arguments.

| View | Purpose |
| --- | --- |
| `agent_resources` | Current visible bots/personas/modules/presets and their single authored JSON representation. |
| `agent_chats` | Chat titles, current heads, and attached package references. |
| `agent_messages` | Live source ancestry, scene numbers, original request/text, and source hashes. |
| `agent_usage` | Provider-reported attempt usage, role, model, helper task/purpose/segment. |
| `agent_helper_inputs` | Small per-helper-attempt input estimates and preparation timings. |

Use positional `?` parameters and explicit chat filters for scoped questions. SQL is live cross-chat data, not the helper's frozen reservation or an unsaved editor. `agent_messages.request` is the stored run request, not a claim to reproduce every later native script projection.

```json
{"sql":"SELECT id,title,revision FROM agent_resources WHERE kind=? ORDER BY title LIMIT 20","params":["bot"]}
```

```json
{"sql":"SELECT helper_task_id,SUM(input_tokens) input_tokens,COUNT(*) calls FROM agent_usage WHERE helper_task_id IS NOT NULL GROUP BY helper_task_id ORDER BY input_tokens DESC LIMIT 10"}
```

```json
{"sql":"SELECT m.helper_call,m.estimated_input_tokens,m.tool_schema_tokens,m.preparation_ms,m.compaction_ms,u.input_tokens FROM agent_helper_inputs m JOIN agent_usage u ON u.id=m.attempt_id WHERE m.task_id=? ORDER BY m.helper_call","params":["<helper-task-id>"]}
```

SELECT/CTE, joins, aggregates and built-in JSON functions are available. Mutations, extension loading, multiple statements, and unrelated application tables are not part of this interface. Saves continue through app operations so resource revisions and side effects are maintained.

SQL returns at most 200 rows (default 50). Long text cells become explicit 2,000-character previews. `truncated` signals omitted rows and `truncatedCells` counts cell previews. Continue using deterministic ordering and narrower columns/conditions or SQL LIMIT/OFFSET. Large integers outside JavaScript's safe range return as decimal strings; binary values return omitted-byte metadata.

Library title/ID/kind query filters are checked against metadata before loading matching authored document bodies. This preserves the same normalization, ordering and pagination; it reduces local body transfer, not the returned evidence or provider input. Broad queries may still load every matching document.

Both SQL and grep run in a short-lived Node child process with a read-only connection, a three-second deadline, bounded JS/SQLite allocations and cancellation. This keeps a pathological query or regular expression from blocking the server's event loop. Within one `data.read` transaction, references to the same document reuse its parsed source and field directory; every reference still checks its own revision/hash. The cache ends with that request. These short-lived read workers do not maintain a file mirror, polling service, new database migration, or extra package dependency; the separate Linux shell keeps a task-local file projection. Process creation and bounded source loading still have a local cost; these tools reduce model input, not all work to zero.

When an HTTP provider returns adjacent `app.call` requests for `data.search`, `data.read` or `db.query` in one response, the helper runs up to four at a time, capped by Node's `availableParallelism()`. Each finished reader immediately starts the next read in that group. Results, logs and the shared round-output budget follow the original call order after the group settles. All other calls form sequential boundaries; no read passes an app mutation. Cancellation stops active reads, leaves queued reads unstarted, and waits for active work to settle before leaving the group. Native Codex callbacks keep their existing serialized dispatch. This uses short-lived workers without a persistent pool, background scheduler or new setting. The CPU-based cap is a small heuristic, not a workload or container-memory tuner.

## Discovering and executing app operations

An explicit `chatId` selects the target chat for that operation without changing the helper conversation's default scope. Metadata reads, renames, lore operations and outline navigation do not prepare an unused writing snapshot. Only operations that consume reserved story/reference context, ancestry or a writing head prepare it for an explicit target: story/reference reads, forks, notes, context edits/compaction, and outline detail with `section=writings`. Calls without an explicit target retain the task's original reservation. Read/write classification, outline-review availability and writing-context needs share one helper tool policy; `chat.lore` and `library.organize` remain reads only for `action=read`.

For operations unfamiliar to the helper, request their exact schemas first:

```json
{"names":["resource.read","resource.patch"]}
```

That is an `app.tools` request. With no names, the tool returns a compact catalog, optionally filtered by `query`, with an `offset` continuation. Execute the discovered operation through `app.call`:

```json
{"name":"resource.read","arguments":{"kind":"content","id":"<resource-id>"}}
```

The gateway schemas and selected nested mutation schemas include short `examples` for their argument shape. Example IDs and revisions are illustrative; use discovered IDs and current read guards for actual writes. A `HELPER_READ_TOO_LARGE` recovery's `nextRead` always names a public helper tool: app operations use `app.call` with nested `name` and `arguments`, while data operations remain direct. Invoke that request unchanged in the next round.

`resource.read` defaults to a small overview with `source`, `regions`, and `readyPaths`. Prompt-preset overviews additionally expose `nativeName` (or a bounded `nativeNamePreview` with the exact read path for an unusually long name) and a direct ready path to the independent native Risu name. Follow a JSON Pointer `path` to page through an object or array (`offset`, `limit`), or name a few object `fields`. Small scalar values keep their JSON types; missing optional fields have `exists:false`. Long strings use `textOffset`, `textLimit`, and `nextOffset`. The serialized read response stays within 12,000 local o200k tokens, including JSON overhead. Omitted textLimit uses a 2,000-token body budget; explicit textLimit retains its existing UTF-16 cap. Pages never claim that omitted text is a complete field.

For text comparisons across resources, `data.read` already accepts up to sixteen search references from different documents. Use `resource.readMany {items}` when typed fields or array structure are needed: each of 1–16 flat selections contains `kind`, `id` and the single-path `resource.read` options (no nested `paths`). Results contain `requestIndex` and `result` or a local error. The entire batch shares the 12,000-token budget; `nextIndex` resumes unread selections with `items.slice(nextIndex)`, while each result's `nextOffset` resumes its text or array page.

`resource.read version=previous` reads the single retained undo model through the same bounded paths. It returns `revision:null`, `version:previous`, and `currentRevision`, without editable item targets. It is not a historical archive; later saves replace that slot. For native presets, `readyPaths` links directly to `promptTemplate`, toggle definitions, default variables and saved values. A preview is not an exact name or ID; follow its path when the full value is needed. These are authored UTF-16 lengths, not evaluated CBS or model token counts. `resource.patch` edits native card/module content and native preset fields using `kind`, `id`, `expectedRevision`, and `changes`. `set` changes a simple typed field or the complete translation guide at `source.translationGuidePath`; `replaceText` replaces one unique literal occurrence. Current saved array pages expose an optional `target` for editable object items. Copy it into a change to bind that original item at `expectedRevision`, then use a relative `path` such as `/text`. All targets bind before changes run, so earlier insertions, deletions or moves cannot redirect an edit. Only `set`, `replaceText`, and `remove` accept a target; targeted removal uses `path:""`. Referring to an item removed earlier in the patch fails the whole proposal. This does not add persistent IDs or change ordinary sequential path semantics.

## Accounting and summary preparation

Host helper compaction keeps the current request exact and preserves a suffix of at most two complete earlier user turns, including their assistant replies. The suffix budget is the smallest of 2,048 estimated tokens, one eighth of the helper input limit, and half the room remaining after fixed instructions, the current request, receipts and read references. A turn that would exceed this budget, and every older turn before it, goes wholly into the summary; individual messages are never silently cut. Only the older prefix and tool results reach the summarizer. The final encoded candidate must still fit the model input budget and be smaller than the previous request before adoption.

The checkpoint records the summarized prefix separately from the retained message IDs and current request ID. Subsequent tasks reload the exact retained conversation; retry invalidates a checkpoint if either its summarized or retained messages are replaced. Original stored messages, exact mutation receipts and completed read references keep their existing ownership. This is bounded local context preservation, not evidence that a real model follows every earlier instruction. Native Codex still owns its active turn's tool history and compaction.

Public task lists and task detail views read a compact projection of task status, usage, the reserved model title and committed-effect counts. They do not restore the full execution snapshot in JavaScript. The browser advances its event cursor without reloading the conversation for diagnostic-only tool/input/context/progress events; task usage/status changes still refresh the view. Execution and retry still read the original snapshot; failed-task inputs and committed-effect receipts keep their existing retention and retry rules.

Execution budget checks and attempt completion read current counters directly from SQLite without loading the reserved manuscript. Attempt admission still checks the recorded limits, owner and generation in its transaction; a repeated completion cannot add usage twice. Session lists retrieve conversation metadata, running/queued counts and the latest event cursor together, preserving empty sessions and existing order.

Closed helper panels and hidden browser tabs pause display timers and response-stream reads while retaining server work, drafts and the received stream cursor. Reopening or focusing the page refreshes immediately. Active work keeps short polling intervals; idle helper lists and sidebar summaries poll every ten seconds. The selected conversation reads events when the list's `latestEventSeq` advances, preserving theme/settings notifications, and accepting a local task triggers an immediate refresh.

The helper UI labels input tokens as cumulative and counts execution requests. A native Codex request can contain several internal model calls; their count remains unknown, and the configured call limits count host requests rather than those internal calls. The selected model timeout, cancellation and existing task deadline still apply. Provider usage is accumulated across attempts; it is not the last request size. The new `input.measured` event is tied to the actual attempt ID and records local input estimates, component estimates, local preparation time and compaction time without preserving another full request copy. The component estimates are independently serialized diagnostics and do not necessarily sum to the encoded request estimate. `preparation_ms` excludes measured compaction work; `compaction_ms` includes summary work and provider waiting. Neither is a first-token or total end-to-end latency measurement.

These numeric events remain after ordinary completed-input cleanup. Tool events retain `callId`, `elapsedMs`, `queueMs`, `originalResultChars` and `providedResultChars` for the handler result before and after the helper boundary; the size fields do not measure the entire source resource behind a paged read. Old attempts need not have these values; no historical values are fabricated. `agent_usage` is provider-reported usage; `agent_helper_inputs` is local serialized-input estimation with the app's margin. New `input.measured` events capture the selected tokenizer and fallback alongside the estimator; old events retain their original o200k policy. Do not combine these estimates and usage as though both were actual billed tokens.

Codex helpers use one ephemeral native thread and turn for each helper task. The configured Uimori tool set is registered as dynamic tools; `item/tool/call` feeds the same dispatcher, result limits, revision checks and receipts used by other providers. Uimori does not create another Codex process and serialize the accumulated results after each tool call. Native tool exchanges are recorded as task events without accumulating a second in-memory history for host compaction. Final output is ordinary assistant text; public commentary is kept separate from the final answer. The native turn may compact its own history. Host compaction can still prepare an oversized conversation history before the turn starts, and manual conversation summaries keep their existing owner.

A short Uimori-specific `baseInstructions` replaces the default coding instructions. Illustration turns have their own short instructions and image-only tool configuration. Each override participates in the descriptor and stable-prefix identity. Codex's native tool descriptions and other runtime context remain outside the local app-input estimate, so the provider input total can still be higher. Reported cached-input and reasoning-output usage are retained in numeric raw usage when supplied; absent values remain unknown.

Manual conversation compaction indexes logical messages once and fits its known source prefix without reconstructing the full writer input for every candidate. It still validates source identity and complete source coverage, preserves recent exchanges, sends every selected fragment, and checks the actual merged summary before adopting it. Automatic compaction and semantic summary length policy are not replaced by a keyword-only shortcut.

## Goal evaluation

[Helper goal evaluation](HELPER-EVALUATION.md) fixes synthetic sources, allowed/forbidden changes and completion oracles before execution. Scripted provider checks verify transport and storage; they do not establish a real model's tool-selection or instruction-following quality.


### Illustration presets

Discover `illustration-preset.list` and `illustration-preset.guide` through `app.tools` and invoke them with `app.call`. The list returns compact names/revisions/descriptions and selections, not every workflow. Use `resource.read/save/undo/delete` with `kind: illustration-preset` for the authored model and the existing revision/operation receipt contract. A new save does not select a preset or generate an image. Editing a selected preset changes future reservations only; existing jobs and retries keep their frozen recipe. Provider credentials, model routing, automatic policies and per-chat reference images stay outside the preset. User-facing selection and portability are documented in [Illustrations](ILLUSTRATIONS.md#삽화-프리셋).


### Bounded composition reads

`outline.read` through `app.call` uses overview/subtree/detail modes, not the browser's full tree response. All modes use offset/limit: lists count items and intent counts UTF-16 units. Lists default to 20 and clamp at 50 items. Intent defaults to 3,000 local tokens; explicit limit remains a UTF-16 cap of at most 10,000. The complete page fits 12,000 local tokens. Only a selected intent is materialized, and selected preview rows are read in one query. Related/writings references are fetched only for those sections. `coverage` distinguishes returned metadata/previews from intent ranges, counts depth-excluded nodes, and never certifies a complete review. For intent only, `wholeField` replaces the ambiguous `complete`: it is true only when this response covers start=0 through the field end. A last partial page still has wholeField=false and nextOffset=null. Follow nextOffset for pagination; aggregate returned ranges only within the same view. Search tools keep their existing complete semantics. Copy `nextRead` including `expectedVersion` to continue the same query scope; start a new first page when changing mode/section. Unrelated sibling edits do not invalidate a node detail or another subtree. Changed views return a recoverable `OUTLINE_CHANGED` without read coverage; a removed selection redirects to overview. A round-budget rejection retries the same outline range at a smaller size, not an unrelated library search. Coverage, version, exact source refs and continuation instructions remain in completed-read metadata after host compaction.

Writings identify exact frozen or current edited source hashes and return existing data.read refs. The live agent_messages view uses the latest source edit; current scope remains the task's frozen text. A source absent from the current history is reported unavailable rather than matched to another scene. `outline.write` retains its atomic operation receipt but returns only created IDs and per-operation results instead of hydrating the entire tree. Browser outline responses remain unchanged. See [OUTLINE](OUTLINE.md) for modes, limits, seed coverage and review staleness.


`knowledge.search mode=browse` is also available through existing `app.tools/app.call`, including read-only review. Its package/folder references and versions address the task's frozen effective writing resources, not the live outline view or an unrestricted library. Wrap its returned main-tool `nextRead` in app.call. Browse metadata carries scope/coverage into compaction but does not count as a retained knowledge.read range. The view is built once per frozen Run object/role and weakly held for that object’s lifetime; page navigation does not rehash the corpus. The current JEV and flat catalog policy is unchanged; see [Folder navigation](TOOL-CONTRACTS.md#folder-navigation).

### Token budgets and isolated read processes

Host resource/editor/chat-lore reads default to 2,000 local o200k body tokens; scene and outline-intent reads default to 3,000. Resource batches, inspection, lore and outline pages share a 12,000-token serialized-response allowance; scene body pages use 9,000. Explicit legacy text limits remain UTF-16 caps, and all returned source coordinates/hashes remain exact. Retrying an omitted-limit token page does not turn its measured character length into a new fixed character default.

The isolated data/SQL/regex worker retains its existing character pages, memory/time limits and IPC size guards. Tokenization stays in the host: returned model-facing reads also pass the per-result and shared-round token budget above. Shell command/output byte limits and exact completed mutation receipts are separate from model prose budgets.
