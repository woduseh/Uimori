## A. 채팅/번역 렌더링 전면 개편 검토

### A1. 출처와 재현된 문제

이 안은 2026-10-21 ChatGPT의 **「렌더링 원인 해결」(이전 대화 표기 「렌더링 원인 확인」)** 세션에서 논의되었다. 사용자는 같은 채팅에서 일부 대사가 강조되지 않고, 루비 등 HTML 인라인 요소가 섞였을 때 읽기 설정이 일관되게 작동하지 않는 문제를 제기했다. 이후 *렌더러가 둘이고 규칙/예외가 복잡하다면 전체 구조를 단순하게 다시 설계해도 좋다*는 방향을 요청했다.

**과거 세션에서 확인하거나 제시한 사실**

- 모델이 `<ruby>…</ruby>`를 백틱 안에 출력한 경우, Markdown 토큰이 `code_inline`이 되어 HTML로 해석되지 않는 사례가 있었다. 이 사례는 파서만 교체해도 해결된다고 단정할 수 없다. 코드의 리터럴 의미를 무조건 HTML로 바꾸지 말 것.
- 2026-10-21의 특정 운영 번역문 조사에서는 원문/번역 손상이나 누락보다 **현재 채팅이 Risu 네이티브 경로가 아닌 일반 본문 경로를 거쳐 읽기 설정이 반영되지 않는 가능성**이 중심으로 좁혀졌다. 운영 CSS/대사 엘리먼트만 보고 원인이 확정된 것은 아니다.
- Risu 네이티브 Markdown은 HTML 인라인 토큰이 있는 문단 전체에 읽기 마커를 달지 않도록 되어 있어, 정상적인 루비가 *일부 문단의 대사 강조를 막는* 구조적 제한도 있다.
- 이전 세션에서 **Risu 실행기를 유지하고 `Reading Compiler → 인용 분석 → 안전한 렌더 트리 → ReaderSurface`로 표시 경로를 단일화**하자는 안을 제시했다. **구현은 하지 않았다.**

### A2. 추천 논리 구조(설계 후보)

```text
저장 원문 / 저장 번역 / 도우미 본문 / 생성 중 공개 텍스트
                   │
                   ├─ 일반 본문: 표시용 입력 정규화(저장 텍스트 불변)
                   │
                   └─ Risu 본문: 기존 CBS·Regex·Lua·리소스·HTML/CSS 실행
                                    (현재 도구/작동 순서 보존)
                   │
             Reading Compiler
             ├─ 유일한 Markdown 문법 해석(markdown-it 계열)
             ├─ 텍스트/인라인 요소/코드/루비/작성자 HTML의 구조적 구분
             ├─ 공통 인용 역할 분석 및 읽기 설정 투영
             └─ 안전한 출력 표현(단일 규약)
                   │
             ReaderSurface(공통 읽기 의미·스타일)
             ├─ 일반 텍스트/번역/도우미 어댑터
             └─ Risu HTML·CSS·컨트롤/Shadow DOM 어댑터
                   │
             화면에만 반영 (DB 저장물, 모델 입력 등 불변)
```

**중요한 의미:** 단일화할 것은 **텍스트 파싱·대사 의미 분석·읽기 규약**이지, 모든 Risu 카드 HTML을 일반 Markdown으로 평탄화하거나 CSS/액션/Shadow DOM을 없애자는 뜻이 아니다. 실행기와 UI 사이의 계약을 얇게 유지할 것. `ReaderSurface`는 위 도식의 역할 이름일 뿐, 반드시 새 React 컴포넌트 하나를 추가하라는 지시가 아니다.

**제거·교체 방향(구현 전 검토 필요)**

- `web/Prose.tsx`의 **자체 Markdown 파싱 구현**은 공통 컴파일러로 대체한다. `Prose` 호출부의 외부 API나 편집/리더 경계가 깨지지 않도록 이행을 설계한다.
- `web/reading-dom.ts`의 **파싱 후 의미를 다시 추측해 DOM을 교체하는 책임**을 없애거나 최소화하고, 컴파일 시점의 구조화된 읽기 주석으로 대체한다. DOM 유지·포커스·위치 복원까지 무턱대고 삭제하지 않는다.
- `server/risu-reading-markdown.ts`의 **HTML 인라인이 들어갔다는 이유로 문단 전체를 제외하는 예외**를 폐지할 수 있는지 검토한다. 정상 문단의 텍스트 구간만 인용 분석하고, HTML/위젯/코드/링크는 보호 구간으로 다룬다.
- 인용 부호 역할 설정(`"…"`, `“…”`, `「…」`, `'…'`, `‘…’`, `『…』`)은 **한 의미 분석 함수**가 소유하고, Risu/일반/번역에서 중복 구현하지 않는다.
- `RisuMessageSurface`의 작성자 HTML 정화·CSS·리스너·버튼/트리거·상호작용 잠금·상태 유지 및 Shadow DOM 처리는 *보존 대상*이다. 독립 작성자 컨트롤 내부의 텍스트를 대사로 재해석하면 안 된다.
- 생성 중 공개 텍스트의 **리터럴 표시 정책**은 사용자 경험과 상충 없이 유지할지 별도 승인한다. 완료 텍스트와 무조건 동일 Markdown 포맷을 강제하면 스트리밍의 내용/레이아웃이 튀거나 의미가 달라질 수 있다.

### A3. 파서·보안·표현 정책 검토 포인트

1. **파서의 실제 소유권**: `markdown-it`은 이미 의존성과 Risu 서버 렌더러에 있다. 동일한 문법을 공유하더라도 컴파일러를 서버/브라우저 중 어디에 둘지, 동일 토큰 규약을 어떻게 사용하는지 확정해야 한다. 두 런타임에서 파서 래퍼가 다시 갈라지지 않게 한다. 추가 파서 라이브러리는 구체적인 이점 없이는 도입하지 않는다.
2. **텍스트 보호 구간**: 인용 분석은 인라인 `ruby`, `rt`, `rp`, `code`, 코드블록, 링크 URL, HTML 속성, Risu 버튼·컨트롤·위젯, `{{…}}`와 같은 보호 토큰을 대사로 읽지 않아야 한다. **루비를 포함한다는 이유만으로 문단 전체를 포기하지 말고 주변의 실제 텍스트만 분석하는 것**이 핵심이다.
3. **루비와 백틱**: 정상 `<ruby>…</ruby>`(허용된 HTML)는 표시 지원을 검증한다. ``` `<ruby>…</ruby>` ```처럼 *코드 의미로 생성된 것*은 일반적으로 문자 그대로 유지해야 한다. 모델에 코드 펜스 없이 실제 루비를 쓰게 지시하는 것이 1차 방안이다. 제한된 호환 보정이 필요한지는 **실제 원시 출력·오탐 사례를 보고 별도 승인**한다.
4. **안전성**: 일반 저장 본문은 현재의 제한된 읽기용 HTML 허용 정책(속성 없는 ruby/u/sup/sub/mark/small/b/i/s/br 등)과 안전한 링크/이미지 규약을 유지한다. Risu 카드의 작성자 HTML은 기존 정화와 작성자 JavaScript 미지원 계약을 유지한다. 표시 개선을 이유로 일반 HTML 실행·이벤트 핸들러 허용·새 네트워크 접근을 추가하지 않는다.
5. **경계 및 원본 불변성**: 표시 컴파일 결과는 저장된 원문·번역문, 해시·오프셋·앵커·이미지 귀속·복사/내보내기·모델 전송과 별개로 유지한다. 기존 읽기 위치, 번역 전환, 편집기 초안/선택 범위도 유지한다.
6. **표시 상태 불변성**: 읽기 설정을 바꾸거나 액션 리비전이 갱신됐다고 작성자 DOM을 재생성하면 `input` 값·`details` 접힘·포커스가 사라질 수 있다. 현재 Risu 표면이 이를 막고 있으므로 새로운 구조에서도 동등하게 보존한다.

## B. UI 설명/보조 레이블 줄이기 — 재검토 결과

### B1. 목적과 검사 증거

> **시각적 구조로 이미 설명되는 문구는 줄이고, 사용자가 시각적으로 추론할 수 없는 동작·상태·위험만 남긴다.**

2026-10-22의 소스/화면 감사에서, 기존 `scripts/check-ui-copy.mjs`가 i18n 메시지를 해석하지 않아 0건을 내고 조건부 `hidden` 패널을 놓치던 문제를 고쳤다(커밋 `6bc5544`). 최신 검사기는 148개 JSX/TSX 파일에서 **검토 가능한 출력 관련 항목 428건**, 이 중 **조건부 i18n 분기 108건**, 엄격한 자동 **경고 2건**을 식별했다. **428건은 삭제할 문장 수가 아니라 검토할 소스 지점/분기 수**이며, 자동 경고가 2건이라고 해서 나머지 중복이 없다는 의미도 아니다.

- 재현: `node scripts/check-ui-copy.mjs --json` (설명 텍스트 및 정적 키/소스 줄 번호 목록), `npm run verify:copy` (보수적 자동 경고), `npm run check:i18n` (언어별 키/인자 검사).
- 당시 워크스페이스 증거: `output/ui-copy-audit-20261022/followup-review.md`, `updated-scan.json`, 390px/1440px 합성 캡처 50개. **이 `output/`은 Git 추적 대상이 아니므로 원격에서 당연히 내려받을 수 있는 자료로 간주하지 말 것.** 집에서는 검사기를 다시 실행하고 필요한 화면은 `npm run verify:gallery` 등으로 재확인한다.
- 이 검사는 `p`/`small`과 일부 조건문 중심의 *소스 도구*로, `SectionNavigation`으로 넘기는 `description` 같은 컴포넌트 prop, 맥락적 의미 중복, 실제 화면의 시인성은 완전히 판정하지 못한다. `0 warnings` 또는 `2 warnings`는 UI 적합성 증명이 아니다.

### B2. 판단 기준

1. **삭제:** 섹션 제목·선택 상태·버튼 동작을 다시 문장으로 설명하는 것, 빈 화면에서 CTA에 이미 적힌 행동을 재설명하는 것.
2. **이동/재구성:** 적용 범위(`데스크톱`, `이 채팅만`, `전역 상속`)는 관련 설정을 묶거나 상태로 표시하되, 실제 의미는 유지. 길고 빈번한 설명은 예시/도움말 영역으로 옮길 수 있다.
3. **유지:** 저장 시점, 데이터 소실/원본 보존, 비용 발생/추정, 권한·보안, 기능 제한·지원 차이, 실패/복구, 기본값과 override 관계, 키보드/접근성에 필요한 의미.
4. **금지:** 실제 라벨 없이 placeholder에만 의존, 접근성 이름 삭제, 첫 이용자가 구분해야 하는 봇/페르소나/모듈 차이를 무조건 숨김, 기능 설명을 무의미한 툴팁으로 일괄 이전.

```bash
# 현재 소스/문구 인벤토리
 git status --short --branch
 node scripts/check-ui-copy.mjs --json > /tmp/uimori-copy-review.json
 npm run verify:copy
 npm run check:i18n

# 코드 입구 / 읽기 구현 비교
 rg -n 'RisuMessageSurface|<Prose|PlainProse' web
 rg -n 'markdown-it|markRisuReadingProse|createReadingDecorator|scanReadingQuotes' server web

# 합의 후 필요한 테스트 선택 (전체 실행을 선행 요구하지 않음)
 node --test scripts/check-ui-copy.test.mjs
 npm test -- tests/prose.test.ts tests/reading-quotes.test.ts tests/risu-reading-markdown.test.ts
```

**검토 종료의 산출물**: 두 안을 각각 `채택/수정/보류`로 판정하고, 위험 요소, 실제 코드 소유권, PR 단위, 필수 회귀 케이스, 배포 필요 여부를 적은 짧은 결론. **이 문서 자체는 구현 허가가 아니며**, 이후 채택된 결론만 해당 제품 계약 문서에 반영한다.
