# Risu compatibility, prompts, lore and translation guides

Implementation invariants, ownership boundaries, compatibility limits, and deliberate non-goals for native Risu I/O, prompt execution, lore retention, bot translation guides, and built-in prompts. User-facing behavior lives in [RISU-IMPORT](../RISU-IMPORT.md), [RISU-EXPORT](../RISU-EXPORT.md), [PROMPT-RUNTIME](../PROMPT-RUNTIME.md), [LORE-CONTEXT](../LORE-CONTEXT.md), [TRANSLATION-GUIDES](../TRANSLATION-GUIDES.md), and [BUILTIN-PROMPTS](../BUILTIN-PROMPTS.md); feature entry files live in [CODE-MAP](CODE-MAP.md).

## Risu native import and execution

### Source preservation and projection policy

- **Source document and deprecation policy**: `nativeRisu.card` (card `data`) and `nativeRisu.module` (embedded or standalone module) are stored with `sourceHash` (input SHA-256) and `assets` (`name`/`uri` → `imageId`). `normalizeRisuContentSource` applies `stripDeprecatedRisuCardFields` and `stripDeprecatedRisuModuleFields` (matching RisuToki `deprecated-save-policy.ts`; see [deprecated fields](../RISU-IMPORT.md#폐기-필드-정책-deprecated-fields)) while preserving unknown active extensions, disabled lore entries, and original asset roles.
- **Single projection boundary**: Both import and save call `projectNativeRisuPackage` to derive `body` (`card.description`), first messages, lore, instructions, and default variables from `nativeRisu`. Raw CBS stays verbatim without generating legacy `bodyTemplate`, `compat.risuCbs`, `transforms`, or `behavior` programs; `mes_example` and `post_history_instructions` are consumed at native preset block positions, and importing never changes active prompts or model connections.
- **Size budgets and non-caps**: Card and module JSON share `RISU_IMPORT_MAX_JSON_BYTES` (`assertRisuContentSource`), and individual text fields (body, first messages, lore) are bounded by `SOURCE_TEXT_MAX_CHARS`. There is no separate cap on first-message count or combined list size, display copies are never double-counted, and source documents are never silently truncated on import.
- **Lore and progress-memory boundary**: Always-active entries project as pinned and other active entries default to `loreActivation.mode: 'model'` (judgment model, default JEV); original keys, secondary keys, regexes, and settings remain in source, disabled entries stay excluded from projections, and preserving source fields does not imply execution of every Risu lore directive. Lore entries are never converted into chat notes or disabled on import (no `memoryIds` API/screen exists), while historical `imported-memory` notes, provenance records, and backups remain readable without auto-deletion or reclassification.
- **Image ingestion and WebP check**: `processImage` decodes PNG, JPEG, WebP, AVIF, and GIF from actual bytes under `IMAGE_INPUT_MAX_BYTES` plus pixel/frame limits without storing original files twice, preserving resolution, alpha, and animation. Already-WebP inputs skip recompression and only pass `assertWebpStructure` RIFF container checks (rejecting truncation while storing structurally intact frames with internal pixel corruption as-is); UI/judgment use names and descriptions while scripts resolve original asset reference names, and external URLs are never auto-downloaded.
- **Original container retention**: Only current card/module/preset sources and converted images are stored; full input containers are never kept as separate `sourceFiles` receipts (export builds a new archive from current state).
- **Idempotency and edit lifecycle**: Digest mismatches force re-review (`RISU_IMPORT_DRAFT_CHANGED`), and uncertain saves re-verify with the same file, selections, and `idempotencyKey` against a compact receipt even after temporary uploads expire (preventing duplicate bots, chats, or starts without storing full payloads or overwriting existing data). Source JSON parses atomically on save with unfinished edits kept only in device-local recovery (no server drafts/history), and unsaved changes must be saved before exporting (see [EDITING](../EDITING.md)).

### Precedence of embedded CharX data

- **Embedded ownership**: `module.risum` (`readCardModule`) belongs to the enclosing card rather than an attached module, retaining both `nativeRisu.card` and `nativeRisu.module`.
- **Script and lore replacement**: `nativeRisuRegex`, `nativeRisuTriggers`, `nativeRisuLore`, and `projectNativeRisuPackage` let an embedded module's `regex ?? []` and `trigger ?? []` replace inline card scripts, and let its `lorebook` replace card lore **even when empty (`[]`)**—card lore applies only when `lorebook` is missing or `null`, and the two lists are never merged.
- **Card metadata and strict failure**: The card retains ownership of name, description, and first messages while embedded module images load in metadata order without overwriting the source document. A corrupted embedded module never silently falls back to inline card data; validation enforces RPack, container version, UTF-8, CRC, `RISU_ASSET_MAX`, ZIP paths, and `risuImportExpandedLimit` without filesystem extraction.

### Native content editing and new chats

User-facing flows for greetings, **첫 메시지 바꾸기**, and backups are documented in [RISU-IMPORT](../RISU-IMPORT.md#첫-메시지-바꾸기와-이미지-배치-담당); implementation boundaries are:

- **Single source of truth and revisions**: Direct fields and JSON edits mutate the same `nativeRisu` document while preserving unknown active extensions; saving bumps revision without archiving past saves or deprecated fields, and in-flight runs/jobs retain their pinned inputs while new runs read current state.
- **Rewrites and lore continuity**: Rewrites run fresh with current settings (forking an independent copy for intermediate scenes, optionally replacing the final response after success) with no verbatim historical-environment candidate replay; new chats reuse the bot's active lore and import creates no initial-chat-only memory.
- **Previews, head replacement, and copies**: First-message preview runs one-shot Lua `editDisplay`, CBS, and regexes at the exact stored revision without persisting state, calling models, or including attached modules/chat variables. **첫 메시지 바꾸기** cancels in-flight translation/image jobs for the previous head while keeping prior edits/translations and chat variables intact; chat backups/copies rebind IDs without duplicating full wire inputs or call receipts and never re-run scripts/models on import, and card-authored starts or button-authored replies are excluded from writing-model re-requests.

### Lua lookup APIs and model options

Card-author behavior for lookup APIs (`hash`, `getTokens`, `getAuthorsNote`, `getPersonaDescription`, `getLoreBooks`), `editDisplay` string-only chaining, `axLLM`, streaming, inlays, viewport macros, `risu-trigger`/`risu-btn`/`risu-form`, and output-appended messages is covered in [RISU-IMPORT](../RISU-IMPORT.md#lua-조회와-모델-옵션); runtime and isolation invariants are:

- **Isolated Lua workers and lazy hydration**: `runNativeRisuLua` (`NATIVE_LUA_LIMITS`) runs one persistent isolated worker VM per chat and content revision for chat runs and button actions, refreshing variables and conversation snapshots on each call. Chat history hydrates inside the VM only on first chat read/write and returns only when modified (making non-chat callbacks independent of history length); per-script permission scoping never merges across functions, `listenEdit`, or dynamic `load`, display callbacks deny model calls (`RISU_NATIVE_MODEL_DENIED`), and worker restarts, timeouts, failures, or content changes discard the VM.
- **VM lifetime and render deadline**: Cancelled-run VM state never carries into subsequent runs, and delayed cleanup (`disposeNativeRisuSession(key, owner)`) cannot terminate a newer run's VM in the same chat. Reader `editDisplay` and first-message previews execute in one-shot VMs copied from saved state (non-persisting, no model calls), and reader HTML rendering in `buildPackagePresentation` must finish within `PRESENTATION_RENDER_TIMEOUT_MS` (10 s, including first worker startup), falling back to stored text on failure.
- **CBS worker isolation and read-only operations**: `createNativeRisuCbsSession` reuses one isolated worker only within a single native run with fresh evaluators and no result caching; evaluation errors or timeouts discard the worker without retry or committing variable mutations, and the worker is never restarted after run end or cancellation. Prompt previews, helpers, and manual context compaction use `prepareNativeRisuReadOnly` on a copy of pinned inputs without persistent Lua VMs, input/request/output callbacks, or state mutations, recording omitted callbacks in run receipts (`RISU_NATIVE_*_CALLBACKS_DEFERRED`) while compaction model calls use existing job budgets.
- **Host model routing**: `createNativeRisuHost`, `nativeScriptModel`, and `validateNativeScriptAttempt` map `sys`→`system` and `bot`/`char`→`assistant`, attribute `options.mode` (`otherAx`, `memory`, `translate`) in call logs, and fail explicitly for deleted connections, unsupported modes (`emotion`/`submodel`), or explicit `streaming=false` without silent substitution while keeping credentials and parameters owned by Uimori. Triggers recognize `v2StopPromptSending` alongside legacy `v2StopPrompt` and `stop`.
- **Trigger permissions**: `nativeRisuTriggers` gates permissions by card `extensions.risuai.lowLevelAccess` (default off) for cards and embedded modules and by module `lowLevelAccess` for standalone `.risum`. Per-source permissions are preserved when attached together, and individual trigger fields cannot bypass this top-level gate.
- **Multimodal inlays and lookup non-goals**: `nativeScriptImages` resolves user-message `{{inlay::...}}`/`{{inlayed::...}}`/`{{inlayeddata::...}}` strictly from local run-attached card assets or `request-image:<sha256>` (never Risu UUID inlay storage or external URLs), strips assistant `inlay`/`inlayed` markers, and rejects non-user image sends. Deliberate non-goals: `loadLoreBooks`, lore mutations, character setters, image generation, external HTTP, embeddings, arbitrary JS, and treating Uimori notes as Risu chat-local lore.
- **Support inventories**: The Lua stubs, trigger condition, operator and effect lists, regex modes and preset block types that the runtime enforces are exported from their owning modules and read by the helper's `code.diagnose`, so a support change shows up there without a second list ([Risu code checks](HELPER-TOOLS.md#risu-code-checks)).
- **Tracking upstream API changes**: New Risu Lua APIs or events are never auto-supported; the [Lua change comparison tool](DEVELOPMENT.md#risu-lua-upstream-changes) reports upstream drift against Uimori's bridge, where name exposure does not imply behavioral parity and the tool never updates the runtime.
- **Shadow DOM surface and trust boundary**: Each message renders in one open Shadow Root without iframes or cross-message bridges (`html`/`body` are not re-rooted; `rem`, viewport units, and media queries resolve against the app document; `position: fixed` is viewport-relative without height compensation, fixed-width layouts are not redesigned for mobile, and viewport dimensions are never stored in source, variables, or run records—server evaluations without browser dimensions report viewport CBS macros unsupported). The surface assumes personal cards trusted by the user: DOMPurify strips `<script>`, event attributes, and `<iframe>`, reinforced by document CSP (`script-src 'self'`); style/image/font origins are unrestricted (no CSS network blocker), and external resource requests send `Referrer-Policy: no-referrer`.
- **Background composition**: RisuAI `moduleUpdate` (`src/ts/process/modules.ts`) builds the module part as `'\n' + backgroundEmbedding + '\n'` per module with a non-empty field in `getModules` order, and `BackgroundDom.svelte` renders `ParseMarkdown(risuChatParser(backgroundHTML + '\n' + modulePart))`, so module backgrounds follow the character's and pass through the same CBS evaluation. `nativeRisuContext` keeps the joined card `backgroundHTML` (what Lua `getBackgroundEmbedding` returns, matching RisuAI's character-only value) and stores attached and embedded modules' `backgroundEmbedding` in attachment order through `joinRisuModuleBackgrounds`; `nativeRisuDisplayBackground` reproduces RisuAI's string exactly, and `renderNativeRisuMessageInWorker` prepends it to the message HTML, so module backgrounds share the CBS, asset resolution, and DOMPurify path of card backgrounds. Deliberate differences: RisuAI's import discards a CHARX embedded module's `backgroundEmbedding` (`importCharacterProcess` keeps only its scripts and lore) while Uimori renders it as part of the card, and RisuAI's stale module store when every module background is empty is not replicated.
- **Actions and inline forms**: `{{trigger_id}}` receives a non-empty `risu-id` only during that manual run (`null` on separate display requests—Risu's lingering global lifecycle is not replicated), and `risu-form` invokes `onFormSubmit` in-app without transmitting files or posting externally. Action reconfirmation (`nativeSourceIdentity`) shares in-flight transport across display views, never auto-retries after confirmed failure/cancel, and never persists temporary reconfirmation state to durable drafts or backups.
- **Display asset matching**: `createAssetResolver` in `renderNativeRisuMessageInWorker` checks exact name, URI, and extension aliases first, then Risu's normalized Levenshtein distance ≤ 4 (`assetMaxDifference`) over stored local assets only (preserving original asset order on ties; no external URLs). Auto image placement (`nativeImageTag`) verifies exact round-trip resolution to the chosen local asset, falls back to `{{img::...}}` without a dedicated tag rule, and checks quoted `src="{asset}"` compatibility for legacy unquoted `src={asset}` templates.

### Native lore positioning

Directive semantics (`@@depth`, `@@end`, `@@reverse_depth`, `@@role`) are covered in [RISU-IMPORT](../RISU-IMPORT.md#네이티브-로어-위치); implementation invariants are:

- **Projection and insertion math**: `nativeRisuPosition` is a storage/runtime projection field that never mutates the library card document. `placeNativeRisuLore` applies Risu's forward `@@depth` and backward `@@reverse_depth` index calculation (never flipping direction to match other apps), preserves insertion order, and places conditional entries only when present in the run's pinned lore selection.
- **Slot isolation and non-goals**: `@@depth 0` and `@@end` always append to final instructions even if a preset relocates `postEverything` to the middle (neither that relocation nor applying the slot's wrapper across all lore messages is replicated). Positioned entries are excluded from generic lore/reference slots and automatic background references to prevent duplication; pinned lore budgets and search/read scopes are unchanged, app memories/notes are never synthesized into chat turns, and unsupported directives (`@@position`, `@@inject_*`, negative/out-of-range depths) remain import notices.

### Moving image-selection instructions

User-facing **이미지 선택과 삽입을 Uimori에 맡기기** and **이미지 배치 담당** (**본문 모델** / **판단 모델**) workflows are covered in [RISU-IMPORT](../RISU-IMPORT.md#첫-메시지-바꾸기와-이미지-배치-담당); projection and selection invariants are:

- **Handoff detection and staleness**: `detectRisuImageHandoff` proposes candidates only for lore or titled sections explicitly declaring image-tag rules when an `editdisplay` regex consumes `<img...>`, leaves unmatched CBS block boundaries unselected (`confidence: 'candidate'`), excludes disabled lore/folders, and `validateRisuImageHandoff` / `projectRisuImageHandoff` never auto-reattach stale ranges (`PACKAGE_IMAGE_HANDOFF_STALE`) when source text changes.
- **Body-model naming heuristics**: In **본문 모델** mode, `cardDefinesImageNames` (`CARD_WORD_COVERAGE = 0.95`) omits image names when ≥95% of their words already appear in the included card description, lore, or instructions; `imageNameTree` encodes remaining unnamed lists exceeding `IMAGE_NAME_TREE_MINIMUM` (100) as a shared-prefix tree, while lists ≤100 and described images stay verbatim.
- **Judgment-model isolation and tag reverse-matching**: `nativeImageGuidance` evaluates enclosing CBS branches on copied variables in the originating field before extracting handoff ranges (preventing cross-branch leakage without moving writing instructions). `nativeImageDisplayText`, `nativeCatalogImageTags`, and `nativeImageTag` strip only catalog-bound local asset tags from display copies (leaving arbitrary external images/HTML intact), reverse-match `<img="이름">` and `<img src=이름>` families only when the original regex resolves to the exact same local asset, and preserve stored responses, placement records, and source documents when switching owners.
- **Non-goals and illustration queue**: Missing assets are never substituted and external module images are never downloaded; this is not a general reimplementation of arbitrary regex/Lua image generators. New illustration generation runs on an independent queue (ordinary native replies eligible; authored starts and button-authored replies excluded; no built-in Lightboard module).

### Large files and assets

User-facing large-file upload and **자료 확인 취소** behavior is covered in [RISU-IMPORT](../RISU-IMPORT.md#대용량-자료); constants and staging invariants are:

- **Budgets**: Inline card/module import accepts up to `RISU_IMPORT_MAX_BYTES` (24 MiB) and staged upload up to `RISU_IMPORT_MAX_UPLOAD_BYTES` (512 MiB), with `RISU_ZIP_MEMBERS_MAX` (32,768) ZIP entries, `RISU_ASSET_MAX` (12,288) logical assets (distinct names/roles count separately while bytes deduplicate), `RISU_IMPORT_MAX_ENTRY_BYTES` (64 MiB) per entry, `risuImportExpandedLimit` (max of `RISU_IMPORT_MAX_CONTAINER_BYTES` or 4× input, capped at `RISU_IMPORT_MAX_EXPANDED_BYTES` = 1 GiB), and `RISU_IMPORT_MAX_PREPARED_BYTES` (448 MiB) total converted images (leaving backup room for metadata and ZIP central directory). Standalone `.risum` shares `RISU_IMPORT_MAX_UPLOAD_BYTES` and JSON/entry budgets.
- **PNG and URI normalization**: `readCardPng` and `importRisuAssets` bind omitted PNG `assets` to CCv3 default `icon/main` (`ccdefault:`) while preserving explicit `[]`, prefer `icon/main` over later same-named non-icon assets, accept numeric/named `__asset:{path}` lookup keys while normalizing temp/export paths to sequence numbers (rejecting duplicate keys), and split PNG `ccv3`/attachment chunks and JSON data-URI images into `embeded://` URIs without bulk-rewriting lore/HTML/Lua bodies or counting separated image bytes against `RISU_IMPORT_MAX_JSON_BYTES`.
- **Staging lifecycle**: `readPreparedRisuImport` and `prunePreparedRisuImports` reuse staged images/folder when changing content kind (replacing metadata only; digest mismatch forces re-review), exclude temporary staging from durable storage/backups, preserve a successful save response if post-save cleanup fails (falling back to expiration pruning), and never retain full input containers durably.

### Structured Risu module JSON

User-facing extraction and ZIP packaging steps are covered in [RISU-IMPORT](../RISU-IMPORT.md#모듈-zip과-프리셋-세부-규칙); parsing invariants are:

- **Module representation**: `moduleJsonDocument` and `finishCharacterCard` store both standalone `.risum` and `{ "type": "risuModule", "module": {...} }` in `nativeRisu.module` (leaving `nativeRisu.card` empty), project name/description/active lore for library display without copying module descriptions into writing bodies, and retain regex/Lua/triggers/CSS/toggles/namespace/MCP in source form separate from runtime execution support.
- **Project ZIP binding and fidelity**: Project ZIPs allow at most one top-level wrapper folder, bind images in `.risutoki/workspace.json` `risumAssetFiles` order (falling back to sorted `.risutoki/risum-assets/*.bin`), verify formats from bytes strictly inside the ZIP without filesystem extraction, and reject ambiguous ZIPs (multiple modules or mixed card+module). RisuToki-extracted JSON/ZIP and raw `.risum` are never treated as identical because extraction normalizes and strips deprecated fields.

### Risu preset runtime

User-facing preset import and editing flows are covered in [RISU-IMPORT](../RISU-IMPORT.md#모듈-zip과-프리셋-세부-규칙) and [PROMPT-RUNTIME](../PROMPT-RUNTIME.md); runtime invariants are:

- **Source-driven storage and budgets**: `nativeRisuPresetSource` stores prompt fields in `RisuPrompt.nativeRisuPreset` and generates runtime blocks from source rather than maintaining a manual port; `.risup`/`.risupreset` RPack/gzip/MessagePack decoding and review execute no code, and there is no arbitrary block-count or 750,000-character cap beyond per-boundary memory and token budgets.
- **Memory and ownership boundaries**: Risu's `memory` slot is never substituted with user notes (Uimori delivers summaries in conversation context and notes/corrections separately without duplicating summaries). Uimori exclusively owns models, providers, auth, generation parameters, and tool permissions—importing or editing a RISUP never overwrites or exposes them and never counts them as unsupported loss.
- **CBS and regex pipeline**: `evaluateNativeRisuFields` evaluates CBS verbatim inside an isolated worker sharing cross-field variable mutations and pinning results for the run (never re-run on reconnect/restore); preset regexes run across `editinput`/`editoutput`/`editprocess`/`editdisplay` evaluating CBS after capture substitution with message-appropriate `{{role}}` (`user` for unappended input, `char` for output/starts, message role for history/display). The legacy 32-rule transform cap is removed while worker/memory/output limits remain; host commands (`@@inject`, `@@repeat_back`, `@@emo`) stay unexecuted and reported as issues, and legacy Uimori ASTs / shared text transforms are unsupported.

### Ownership of stored data

`nativeRisu` is the sole editing and execution source of truth, with body, lore, and first-message projections derived from it (`projectNativeRisuPackage`). Request context carries content ID, role, name, and lore entry ID alongside text to disambiguate identical names without mutating card strings; shared modules track the latest stored revision while pinned versions require explicit copies or backups (see [EXECUTION](../EXECUTION.md) and [CHAT-BACKUP](../CHAT-BACKUP.md)).

## Risu export

- **RISUP encoding**: `writeRisuPreset` encodes MessagePack → Risu fixed-key AES-GCM (`sha256('risupreset')`, zero IV) → gzip → RPack; this fixed key is format compatibility, **not** privacy encryption.
- **Deprecated field policy**: `exportRisuContent` and `exportRisuPrompt` apply `stripDeprecatedRisuCardFields`, `stripDeprecatedRisuModuleFields`, and `stripDeprecatedRisuPresetFields` matching RisuToki `deprecated-save-policy.ts`, omitting deprecated card fields, module `cjs`, and legacy top-level preset fields.
- **HTTP and read-only semantics**: `risuExportRoutes` returns an attachment with a UTF-8 filename, `Cache-Control: no-store`, and `X-Uimori-Revision`; it rejects with `409` on `expectedRevision` mismatch, returns `404` for hidden content, reads the latest stored revision when `expectedRevision` is omitted, and never modifies stored state or original imported copies.
- **Size and compression budgets**: CHARX/RISUM export enforces `RISU_IMPORT_MAX_UPLOAD_BYTES`, `RISU_IMPORT_MAX_JSON_BYTES`, `RISU_ASSET_MAX`, `RISU_IMPORT_MAX_ENTRY_BYTES`, and `risuImportExpandedLimit`; `writeRisuPreset` enforces `RISU_IMPORT_MAX_BYTES`. `writeRisuZip` stores PNG/JPEG/WebP/AVIF/GIF bytes uncompressed while deflating JSON/text when total stored size fits `RISU_IMPORT_MAX_UPLOAD_BYTES`; for larger payloads it compresses images to fit, then switches the highest-saving entries back to stored (uncompressed) so final size and `risuImportExpandedLimit(size)` hold together (rejecting with `413` if both cannot be satisfied).
- **Safety and verification boundary**: `assertExportPath` and `exportRisuContent` reject ZIP path traversal, conflicting duplicate paths, and missing/tampered image bindings. Local round-trip tests re-import exports through Uimori's own importers and do not establish execution of every script in the actual RisuAI app.

## Risu native prompt runtime

User-facing preset editing and chat options are covered in [PROMPT-RUNTIME](../PROMPT-RUNTIME.md#저장과-편집); implementation invariants are:

- **Prompt-only import and retired features**: `nativeRisuPresetSource` strips provider/model/sampling fields (unvalidated JSON drafts stay in the editor and block save). `stripDeprecatedRisuPresetFields` silently drops `jailbreakToggle`, `chainOfThought`, `promptSettings.{sendName,sendChatAsSystem,postEndInnerFormat,assistantPrefill}`, `chatAsOriginalOnSystem`, `type2: jailbreak`, and `jailbreak`/`cot` blocks (never converting them to plain text and maintaining no compatibility branch for historical results).
- **Toggle controls and merged sources**: `promptControls` derives UI definitions from `customPromptTemplateToggle` (select/switch default `"0"`, text `""`, no unset choice; not a separate authored source of truth), persisted via workspace revision CAS with mismatched combinations rejected. `effectiveRisuControls` and `nativeToggleVariables` merge preset, attached-module `customModuleToggle`, and card `extensions.risuai.toggles` without mutating source, reporting conflicts on differing types/options, passing original Unicode/dot keys as `toggle_<원래 키>`, and isolating reserved JS keys via `nativeToggleId`.
- **One-off next-request options**: `ChatOptionsStore` stores next-request options independently of source revisions so reservations survive source edits, validates option-definition hashes, consumes them once inside the generation-reservation transaction, and never accumulates cancellation records or full prompt copies.

### Execution and preservation

See [PROMPT-RUNTIME](../PROMPT-RUNTIME.md#실행과-보존) for the four-stage runtime overview; compiler and receipt invariants are:

- **Single compiler contract**: `PROMPT_COMPILER_VERSION` is exclusively `risu-native-prompt-2` (no compatibility branches for older Uimori run-snapshot compilers—separate from external Risu source support). Native prompts requiring preparation never transmit before CBS finishes.
- **Pre-compilation CBS receipt**: `prepareNativeRisuPreset` evaluates active-block fields in order inside the CBS worker and pins source/context hashes, evaluated text, variables, and issues in `nativeRisuPresetProgram`; retired blocks/settings, skipped `memory` blocks, and unused `innerFormat` on empty slots execute zero variable side effects, and `{{jbtoggled}}` is always `"0"`. `projectNativeRisuPresetProgram` projects pinned results without re-evaluating and rejects mismatched hashes or field lists.
- **Compilation and block semantics**: `compileRisuPrompt` assembles messages from evaluated blocks, host slots (`{{slot}}`), history, examples, and toggles without receiving a separate CBS execution context copy, preserves history IDs/hashes, rejects duplicate history insertion, marks all messages `complete` (omitting removed `assistantPrefill`; `planNativeMessages` also rejects prefill with `PROMPT_PREFILL_UNSUPPORTED`), applies `innerFormat`/`role2` only to `persona`/`description`/`authornote`, and leaves Risu `memory` uninjected.
- **Global notes, examples, and translation prompts**: Card `post_history_instructions` replaces `type2: globalNote` text (substituting `{{original}}` before CBS) without duplicating a global instruction; `nativeExampleMessages` parses `<START>` and speakers from raw `mes_example` before CBS and prepends roles to `chat` without persisting examples to chat history. `prepareNativeRisuTranslationPrompt` evaluates the pinned translation preset without mutating card/preset state, leaving translation source text unevaluated by CBS in the current user message (or separate pinned host context if the preset omits the current message); optional `collaboration` and `execution.storySubmission` add no content syntax and follow [AGENT-COLLABORATION](../AGENT-COLLABORATION.md).

### Verification

- **Cross-cutting tests**: `tests/risu-native-prompt-composition.test.ts` and `tests/risu-native-semantics.test.ts` cover vendored CBS, evaluation order, global-note replacement, example roles, toggles, slots, chat ranges, caching, suppression of retired option side effects, and receipt consistency; `tests/risu-retired-execution.test.ts` covers re-projection of historical source snapshots. These synthetic suites do not judge creative or translation quality on live providers.
- **Opt-in local sample checks**: Run `tests/risu-native-local-compatibility.test.ts` (`UIMORI_RISU_LOCAL_CARDS`, `UIMORI_RISU_SAMPLE_PRESET`) and `scripts/verify-risu-native-samples.mjs` (`UIMORI_RISU_SAMPLE_ROOT`); see [Builds and evidence](DEVELOPMENT.md#builds-and-evidence) for flags, privacy redaction, and scope limits.

### Source-preserving request context

- **XML and JSON provenance**: `serializeRisuContextSource` wraps bot/persona descriptions in `<uimori_source>` and `serializeRisuLoreSources` groups general lore under `<uimori_lore_sources>` (`<source>`/`<entry>`), exposing only role, name, content ID, lore ID, and title with the single-sentence `RISU_SOURCE_GUIDANCE` (no permission, knowledge-scope, or priority markers; independent of preset/toggle; preserves `innerFormat`).
- **Projection-only invariants**: XML attributes are escaped while post-CBS bodies stay byte-intact, empty content creates no wrapper, only adjacent same-source entries group (preserving order), `serializePositionedRisuLore` attaches provenance once at positioned lore's original role/depth, and unslotted references carry JSON `risuSource`. Markers are reading boundaries—not XML-parsed bodies or permission boundaries—and never alter stored sources or hashes; actual model comprehension gains require separate response evaluation.
- **Per-connection disambiguation**: When per-connection edits produce distinct bodies for the same source, `projectChatPackageCompilation` attaches `source_scope="connection-1"` (etc.) solely to disambiguate connections within a pinned request, not to signify priority; internal path JSON is never sent to the model.

## Lore context and retention

User-facing retention, budgets, and invalidation rules are covered in [LORE-CONTEXT](../LORE-CONTEXT.md#읽은-구간-유지) and [CONTEXT-LIMITS](../CONTEXT-LIMITS.md); storage and runtime invariants are:

- **Model-facing notes**: `modelAuthorNotes` emits each note body once with kind, author, source anchor, and imported provenance in host reference context while preserving original declaration text in `snapshot.story.notes` and keeping editing/backup formats unchanged.
- **Single-row state and placement**: `retainCompletedLore` and `readLoreRetention` keep **one latest `chat_lore_state` row per chat**, appending non-overlapping ranges via `appendLoreReads` without archiving full model inputs/tool events or calling models to re-summarize read text. `loreHistory` injects references as a separate `user` message near the first-read source (or after the summary and before recent turns when compacted) without fabricating conversation turns or tool calls.
- **Local token estimation**: Token counting uses local `LORE_TOKEN_ESTIMATOR` (`o200k_base`) with a bounded cache, zero remote calls, no billing-parity guarantee, and zero source mutation or separate CBS/Lua execution.
- **Eviction, invalidation, and backups**: `selectLoreContext` and `freezeLoreContext` evict LRU ranges on overflow without rescanning historical run logs, raise `LORE_PINNED_BUDGET_EXCEEDED` when pinned inputs alone overflow, and validate content IDs, revisions, body hashes, source text, and notes per request to invalidate stale ranges and deduplicate newly pinned items. Individual chat backups carry continuation state only (not full lookup archives; full DB snapshots preserve `chat_lore_state`; see [EXECUTION](../EXECUTION.md)).
- **Cross-cutting verification**: `tests/lore-token-selection.test.ts` covers local token counting and JEV pre-selection.

## Bot translation guides

Storage paths and input limits (`TRANSLATION_GUIDE_LIMITS` enforced by `validateTranslationGuide`) are documented in [TRANSLATION-GUIDES](../TRANSLATION-GUIDES.md#저장-구조와-자료-교환-규약).

- **Prompt preview contract**: Translation-mode prompt preview (`promptRoutes`) reflects the server-stored bot guide and translation `contextMode`, returns the guide in response field `translationGuide` (omitted in main mode), and preserves provider `mapping-only` preview semantics. Because host supplemental context delivers the guide when a preset omits the context slot, raw compilation output alone does not indicate a missing guide.

### Server execution pipeline

- **Guide loading and pinning**: `currentBotTranslationGuide` reads the chat's pinned owning bot (falling back to `nativeRisu.module` only when `nativeRisu.card` is empty; never merges attached modules). Translation job creation pins `{botId, botRevision, botTitle, ...guide}` (or explicit `null`) onto `job.input.translationGuide`, and `resolveJobPrompt` binds only that compact metadata onto the snapshot—never re-querying the DB mid-run or archiving full prompts/save history.
- **Context injection**: `translationInput` places the guide in `context.translationGuide` and appends `TRANSLATION_GUIDE_POLICY`, reusing the context slot and host supplemental delivery so default prompts, Hermēneía, and context-omitted presets all receive it without duplicating terms into a separate glossary slot.
- **Reference scope separation (`contextMode`)**: Stored on the default translation policy and pinned onto new jobs (historical policies/jobs lacking it resolve as `full`). Under `source-only`, `translationSnapshot` strips background content, card variables, prior conversation, and notes **before** CBS evaluation so background-slot presets cannot re-pull excluded content, while retaining result-binding metadata (source ID/hash) without modifying stored presets or content.

### Tests and verification commands

- `tests/translation-guides.test.ts`: Saving, validation, revert, import/export, request-time pinning, judgment recovery, and preview/writing separation.
- `tests/translation-prompt-delivery.test.ts`: Serialized outputs across all seven provider protocols for default, Hermēneía, and context-omitted presets in both reference scopes (using local stubs), plus native CBS exclusion of background data under `source-only`.
- Browser workflow checks run via `npm run verify:translation-guides` (see [Verification runners](DEVELOPMENT.md#verification-runners)).

## Built-in prompts

### Delivery and provenance

- **Read-only catalog**: `builtinPromptTemplates` returns metadata only (`title`, `role`, `description`) and `builtinPromptTemplate` returns the selected program and resolved defaults; both are strictly read-only, while adding, editing, and selecting go through existing preset/active-prompt validation, revision checks, and draft protection.
- **Upstream provenance**: Phēmē uses V5.6.0 r2 programs and defaults from `risu/prompts/phēmē/dist/uimori/pheme-roleplay.uimori.json` and `pheme-novel.uimori.json` (RisuToki Phēmē v5.6.0, revision `921a84e`), matching direct `.risup` import with optional collaboration attached separately; Hermēneía uses `dist/hermeneia-preset.risup` (v1.2.0). `server/builtin-prompts/` stores the three preset bodies, defaults, and two writing collaboration definitions.
- **Cache breakpoints**: `planNativeMessages` preserves Phēmē's four authored cache breakpoints under both **explicit caching** and **automatic caching** on Responses and Anthropic connections; in automatic mode, exhausting all four suppresses only extra automatic breakpoints (`PROMPT_AUTOMATIC_CACHE_SKIPPED_FOR_AUTHORED_POINTS`), and selecting a preset never alters model caching or output-token settings.

### Verification scope

`tests/risu-native-prompt-composition.test.ts` checks CBS composition for the built-in presets, and `npm run verify:browser -- --grep BPTUI` covers catalog addition and editing flows.
