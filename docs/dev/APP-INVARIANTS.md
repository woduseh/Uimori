## Personal workspace schema 15

- **Backup horizon (v0.18.0)**: Opening a DB and importing `.uimori` or `.chat.uimori` archives read only the shapes v0.18.0 and later write; no row is rewritten on open. `tests/backup-horizon.test.ts` opens a v0.18.0 automatic-backup snapshot and imports archives exported by v0.18.0, so a change to a stored or archived shape either keeps reading those or ships its own migration with that test updated.
- **Authored opening (`isAuthoredOpening`, `authoredOpeningSql` in `server/authored-opening.ts`)**: A run is the chat's authored opening when its snapshot has `packageStart.mode === 'authored'` or `nativeRisuAuthored.greeting`. Only package starts write the first form; a `.chat.uimori` restore (`restoreCopiedMessages`) and a native action that empties the chat write the second, always on the root run. Everything that asks whether a run is the opening uses this pair: reader navigation, model title and `ReaderRun.opening` (which the web reads instead of `packageStart`), manuscript export and search numbering (the worker receives the SQL through `workerData`), the archive's `opening` flag, native presentation and automatic titles. That keeps restored openings at scene 0 without a migration (`tests/native-transfer-archive.test.ts`).
- **Legacy copy receipts**: Chat copy records lacking a recorded copy command are left unmodified and return `CHAT_COPY_RECEIPT_UNVERIFIED` (409) on retry so the browser clears the leftover key.
- **Single head and concurrency invariants**: Each chat owns its manuscript head (`chats.head_revision`) and execution state directly; the `branches` table, `branch_id` column, and API `branchId` are removed. Task owner/generation tracking, revision CAS, post-cancel late-save blocking, and request-key deduplication remain strictly enforced.
- **Schema 15 on-demand tables**:
  - `helper_seed_messages`: Cloned dialogue from past helper session forks, created on demand at startup.
  - `execution_tool_diagnostics`: Lightweight tool diagnostic metadata owned by main, translation, and illustration tasks; does not replace replay receipts in `tool_events`.
  - `image_cleanup_candidates`: Deferred orphan image hashes waiting for active tasks to finish.
  - `helper_changes` is retired: opening a database or a restored backup drops it (`dropHelperChanges` in `server/database-schema.ts`) and queues the image and theme-asset hashes only its stored baselines referenced, so reclamation frees them. `tests/database-schema.test.ts` opens a database with real-shaped rows and its backup copy.
  - `theme_assets`: Theme font and image originals by hash, retained while referenced by a saved theme or its undo copy, and separate from user fonts (`font_assets`) and body images (`image_blobs`). Unreferenced uploads are pruned on server startup after one day.
  - `search_trigrams`: Derived trigram index created on demand without bumping schema 15; opening a DB drops the retired `search_fts` table ([MANUSCRIPT-SEARCH](../MANUSCRIPT-SEARCH.md)).
- **`app_metadata` key conventions**:
  - `source-title:<sourceId>`: Optional scene names.
  - `illustration-presentation:<sourceId>`: Representative/display selection and translation placement for paragraph illustrations.
  - `helper-read:v1:<conversationId>`: Last seen task-result event sequence for a helper conversation (requires no DB migration).
  - `chat-pin:<chatId>` (`CHAT_PIN_PREFIX`): ISO time the chat was pinned, returned as `Chat.pinnedAt` and deleted with the chat. It is keyed by chat ID and outside the copied chat state, so copies, backups and imports start unpinned; pinning an already pinned chat keeps its time (`tests/chat-organization.test.ts`).

## Deletion, unused-data reclamation and helper cleanup

- **Stale tabs and deleted library items (`isLive`, `available`, `writable` and `editable` in `server/product-store.ts`)**: Every liveness check goes through `ProductStore.isLive` (a stored row that is not in `library_hidden`). `ProductStore.stored` reads the row whatever its state and is meant for what history or a record already names (an old revision, a title, the connection behind a model that is already checked, a role reference kept on purpose) and for provider authorization that answers its own `ProviderContractError`; a read that acts on the item as current uses `available`, `writable` or `editable`. Moving a chat keeps what it holds: a copy, fork, copy-mode retry and chat backup read the chat's packages, pinned prompt and fixed options with `stored` and keep its pinned model (`ReferenceSource` `'preserve'` for `importChatTranscript`, `captureResourceBundle` and the `ChatOptionsStore.get` calls in `server/chat-copy-authoring.ts`), while a transcript import and a library resource export select from the library (`'library'`) and report a deleted package in `skippedAttachments` or refuse it. Running a chat whose pinned prompt was deleted still answers `PINNED_PROMPT_UNAVAILABLE` (`chatPromptWorkspace` with `'library'`), in its copies too. A profile save checks only the packages and pins it adds against the profile or a copy's `held` baseline (`attachableContent` and `updateProfile` in `server/product-store.ts`, shared by `PUT /api/chats/:id/profile` and the helper's `chat.profile.update`, which checks the profile revision first); a pinned prompt the saved profile does not already name is checked for the main role even when a copy holds it, and creating a chat for a deleted bot answers `LIBRARY_ITEM_DELETED` (`createChat` in `server/chat-creation.ts`). A write that names a saved library item, a provider setting, a theme, a palette or a resource answers `REVISION_CONFLICT` when the item is missing, hidden or at another revision (`writable`, or `editable` with a revision), so an editor's conflict path keeps its draft; this covers saves, deletion, resource clone sources, a model's connection, display-order moves, appearance scope writes for a deleted bot or chat and prompt combinations owned by a deleted preset. A read of such an item, and a write that only selects one (applying a prompt preset or combination, choosing a theme, palette or illustration preset), answers the catalogued `LIBRARY_ITEM_DELETED` (`available`, `assertAvailable`), so a deleted bot or preset never reaches the editor or the helper as its last snapshot; built-in themes, palettes and illustration presets are answered before the lookup. A mistyped id and a deleted one share these codes. A selecting write checks the workspace revision first, in the same transaction as the update, so a stale tab gets `REVISION_CONFLICT` before `LIBRARY_ITEM_DELETED`, a role mismatch or `PROMPT_COMBINATION_MISMATCH`. The same split holds outside the library: a write that names a library folder (or a folder-order anchor), a chat folder or chat-order anchor, a chat image (`ProductStore.writableAsset`), a bookmark, a chat (`Store.writableChat`, as for a reading position, a new bookmark, an appearance scope, a scene deletion, chat option, variable and story guide writes, an orphan memory review, a pin, a move, a copy, a profile save, an image upload or chat deletion), a bot whose record was purged (`ChatOrganizationStore.bot` with `'write'`, also for a folder left under it; a read of its defaults or folders answers `LIBRARY_ITEM_DELETED`, and a soft-deleted bot keeps serving its chats) or a scene (`Store.writableSource`, as for an image placement request, a selection revision and the scene a copy starts from), a moved item, a push device to test, or the resource of an undo answers `REVISION_CONFLICT` when that target is gone, and a removed judgment connection, being a selection, answers `LIBRARY_ITEM_DELETED`, as does any read of a chat that no longer exists (`Store.chat`). Two selections keep their own catalogued codes: a removed font answers `FONT_NOT_FOUND` (fonts are not library items), and a deleted model answers `MODEL_SELECTION_UNAVAILABLE`, which it shares with a disabled model or connection. A singleton setting whose service validates the body, such as the prompt workspace or lore context defaults, checks the revision first, so a stale tab gets `REVISION_CONFLICT` before a refused value. `tests/stale-tab-matrix.test.ts` runs the cases in `tests/stale-tab/<domain>.ts` (one file per contract domain, listed in its `domainFiles`) and holds this for every endpoint in `allEndpoints` whose input schema (`analyzeSchema` in `tests/stale-tab/schema.ts`, walking reused sub-schemas per path with ancestor-only cycle detection) has a revision field (`expected…`, `…Revision`) or names a target path (`/(?:^|\.)(?:id|\w+Id)$/`, excluding `clientId`): each has a case that deletes or hides its target, library items in their soft-deleted (`library_hidden`) state, and asserts the answer, or an exemption with its reason, and a new endpoint without either fails with what to add. Every union branch carrying a revision or target field—expanding nested `discriminatedUnion`s (including `z.enum` discriminators) and object-only `z.union`s, while skipping primitive unions such as `queryInt`/`queryBoolean` and non-target branches such as `scope: 'workspace'`—needs a case whose input passes that branch's schema or an `exemptBranches` reason (20+ chars); every input with two or more target paths needs a case naming `target: '<path>'` (populated in `input` and differing in `control` when present) or an `exemptTargets` reason (20+ chars). A `GET` case answering anything other than `LIBRARY_ITEM_DELETED` (including `REVISION_CONFLICT`) requires a stated reason, as does a write answering anything other than `REVISION_CONFLICT` or `LIBRARY_ITEM_DELETED`. A case whose revision belongs to a container (the library organization, theme or font preferences, the prompt or model workspace) repeats the request with a live target and the same revision and expects success, so the conflict is shown to come from the target; a case that answers anything but `REVISION_CONFLICT` is also sent with its revision plus one and must answer `REVISION_CONFLICT` first, unless the revision is the deleted target's own (`targetRevision`, such as the manuscript head a deleted chat's export names). The helper workspace keeps its own answers: a write or read naming a deleted helper conversation or project answers the catalogued 404 `HELPER_CONVERSATION_NOT_FOUND` or `HELPER_PROJECT_NOT_FOUND` (`HelperWorkspace.conversation`, `HelperWorkspace.group`), because the web shows their "may have been deleted elsewhere" text and the handoff in `web/HelperPanel.tsx` opens a fresh conversation on that 404. Their own revision cannot be compared once the target is gone, so the writes that carry it are reasoned exemptions in `tests/stale-tab/helper.ts` and `tests/helper-navigation.test.ts` pins the 404 over HTTP.
- **Role references to a deleted model or connection (`deleteLibraryItem`)**: Deleting a model, or a connection with its models, clears the title model and the main and translation routes and disables agent collaboration whose agent used it. The helper, context-compaction and card script models and the judgment selection keep pointing at the deleted item on purpose: a run then fails that role as unavailable (`contextModelUnavailable` and `scriptModelUnavailable` in `ProductStore.snapshot`, `MODEL_UNAVAILABLE`, `JUDGMENT_CONNECTION_UNAVAILABLE`) and the user sees that the chosen model went away. An empty script model means the main model and an empty judgment selection means TypeSafe, so clearing either would move paid calls to a model nobody chose for that role (`tests/risu-native-model-selection.test.ts`). `assertModelSelection` passes a selection that equals the saved one before looking it up, so such a reference never blocks saving another role; collaboration agents compare with the saved agent of the same id, so applying a preset whose advisor model was deleted is still refused.
- **Reference-based reclamation (`pruneUnusedData`)**: Deletion and save transactions follow live resource references to reclaim orphan `image_blobs` and hidden entries; Reader queries and per-chunk model streaming never scan all stored resources.
- **Deferred cleanup and worker write-invalidation (`PendingImageCleanup`)**: While model or image work is active, candidate hashes queue in `image_cleanup_candidates` and are skipped when both `image_cleanup_candidates` and `library_hidden` are empty. On task completion, `PendingImageCleanup` scans references in a read-only Worker and discards the plan if any write advanced `total_changes()` on the main connection (retrying on the next completion); startup and deletion transactions run the same check synchronously.
- **Draft-protection exceptions and diagnostic snapshots**: Images appearing only in helper conversation text and individual illustration deletions do not enqueue image cleanup candidates because an unsaved draft in another window may still reference them (direct helper attachments and other resource deletions still enqueue). References held only by historical diagnostic snapshots never block reclamation once the last live reference is gone.
- **Helper call-argument cleanup**: Scene, chat, library resource, theme, and illustration preset deletion call `forgetHelperConfirmationTargets`, and scene and chat deletion call `redactHelperArgumentPreviews`, matching records across conversations via stored target scene, `chatId`, and `targets`. Shell commands such as `uimori apply` leave only the command string and are not matched.

## Independent chat backups and copies

### `.chat.uimori` archive structure and BLOB deduplication

- **Archive layout and deduplication**: Uncompressed ZIP (`uimori-archive` v1) containing root `uimori-personal-chat` v1 metadata JSON and `images/<SHA-256>.bin`, deduplicating identical bytes across representative images, body attachments, and scene illustrations. Server validation converts images to WebP and registers confirmed imports atomically without base64 JSON serialization.
- **Restored resource references (`remapRestoredResources` in `server/chat-backup.ts`)**: A restore maps the backup's content ids and prompt preset ids through separate maps. A package attachment or lore override that names no imported content refuses the whole restore with `CHAT_BACKUP_INVALID` and writes nothing, while a pinned prompt that names no imported prompt preset is dropped, because the pin is a preference the user can set again.
- **Profile check before any write (`checkedCopyProfile` in `server/chat-copy.ts`)**: A restore and a copy check each chat's saved profile against a strict schema before anything is written; a wrong type, an unknown key such as `expectedRevision` or `packageAttachments`, or an over-long author note answers `CHAT_BACKUP_INVALID`, and the retired `imageTranslation` flag of earlier backups is accepted and dropped. The restored chat's own profile revision and package attachments always win over the file.
- **Retired JSON export and multi-chat compatibility**: Legacy JSON export `GET /api/chats/:id/backup` is removed and returns 404, while restoring existing JSON backup files remains supported (transcript JSON export is separate). Exports contain only the single selected chat while keeping the metadata `chats` array structure so legacy multi-chat backup files still restore cleanly.

### Staging file lifecycle and concurrency protection

- **Staging TTL and process lock**: Staged files clean up immediately on restore, and incomplete staged outputs expire after 24 hours (cleaned at write-enabled startup and hourly; completed identical requests remain verifiable via receipt). Staging shares the process-wide 1-at-a-time lock (`acquireImportPreparation`) with Risu imports and resource-bundle staging, and client disconnect cleans in-progress staging artifacts immediately.
- **BLOB reuse and restore side effects**: Immutable BLOB reference counting and no-external-callback guarantees live in [CHAT-BACKUP](../CHAT-BACKUP.md#이미지-보존과-복원-시-실행-범위).

### Retry and copy API (`/api/runs/:id/retry`)

- **Mode and replace target retention**: `POST /api/runs/:id/retry` accepts `mode` (`'replace'` | `'copy'`; omitting applies the existing copy rule). Retrying a failed replace reuses the last response already reserved as the replacement target.
- **Copy idempotency**: Copy-check errors preserve the previous request key to prevent duplicate copies. If the target copy was deleted or is a legacy copy record without a recorded copy command, the client notifies the user and clears the leftover key so the next attempt creates a fresh copy.
- **Related contracts**: Full workspace recovery uses [DATA-MIGRATIONS](../DATA-MIGRATIONS.md); per-device reading positions and bookmarks live in [READING-STATE](../READING-STATE.md).

## Portable resource transfers

- **Retired JSON export and receipt scope**: Legacy `POST /api/native-transfers/export` is removed and returns 404; new exports use `.uimori` archives only. No separate replay or execution-history attestation receipt system is maintained—exports hold only currently saved resource state.

### Two-stage atomic apply pipeline

- **Review-to-apply reuse and streaming export**: Pre-validation checks TOC, CRCs, and image SHA-256 and stages converted images one by one; confirmed apply reuses the review summary directly without re-validating or re-converting, committing resources and receipt in one transaction. Export streams images one by one from a read-only DB snapshot so concurrent edits or cleanup cannot corrupt downloaded bytes.

### Concurrency lock and staging file lifecycle

- **Single-job lock and cancellation**: `acquireImportPreparation` serializes Risu imports and `.uimori` staging to 1 job at a time per process without building a queue (callers retry after completion). Client disconnect cancels staging immediately, cleaning temporary files and discarding any already-started image conversion without proceeding to the next image.
- **Expiration**: Incomplete staged files expire after 24 hours (cleaned at write-enabled startup and hourly, retrying on failure). Cleanup touches only 32-hex staging entries and skips the active ones.

### Idempotency receipt retention policy

- **Receipts are never pruned (`saveImportReceipt`)**: Every import, restore, copy and retry receipt stays, so a lost-response retry of any of them answers its original result however many imports followed. Each receipt row is small next to the data its import created, and an earlier prefix-based prune silently dropped archive and transfer restores. `importNormalizedResourceBundle` and the Risu apply commands read the receipt before analyzing or converting the source. A Risu apply receipt saved with an earlier request-hash algorithm yields an idempotency conflict on retry; the saved item remains in the library. For matching request hashes, the receipt takes precedence over the draft, so a later 409 `*_DRAFT_CHANGED` or 410 `NATIVE_TRANSFER_EXPIRED` means nothing was saved under that key; the web relies on that in `definiteImportFailure`.

## Resource editing, recovery, selection revision and helper results

- **Touch-selected reader bar (`placeDocked`)**: On mobile long-press selection, docks to the bottom edge of the reading area (moving to the top edge if covered) to stay clear of native selection menus and handles, waits until handle dragging settles, and acts on the pre-press selection if tapping clears it (`RSEL22` in `tests/reader-selection-browser.spec.ts`).

### Input state and session ownership (`ResourceEditorSession`)

- **Single owner (`ResourceEditorSession`)**: Exclusively owns form model, raw text, saved baseline, dirty state, and save progress using functional updates with no parent sync loop; switching roles or presets only selects sessions.
- **Load lifecycle and auto-save**: Starting a new draft or returning to the list cancels in-flight fetches so late responses never overwrite the active view; list opens and externally targeted preset opens share one lifecycle. Auto-save for current prompt options schedules only on fresh edits (never on recovered input or failed saves), never overwrites post-submit typing, migrates recovery keys to the real ID on new/copy save, and refreshes clean editors while flagging conflicts on dirty editors when a save made elsewhere arrives (`resourceFrame`, a cross-tab storage signal or window focus). `ResourceEditorSession.refresh` decides on the revision it reads: only a revision above the editor's base counts, so the editor's own save never flags itself, a dirty draft only gains the conflict state and keeps its text and recovery copy, a refresh waits for the editor's own save or undo in flight and reads again when one started during its read, so it never cancels a discard or a restore, and the live subscription retries a failed read while a definite rejection such as a deleted target ends it.
- **`Esc`, scroll, and focus restoration**: `Esc` in original/translation editors prompts only when dirty (Cancel keeps draft and tab recovery), while **편집 취소** discards without prompting. Opening original/translation editing scrolls only the Reader and `data-uimori-body-scroll`, restoring reading position and trigger focus on exit; the narrow-viewport scroll-to-bottom button hides during original/translation/request editing while scene list and bookmark editing stay usable.

### Local recovery storage (IndexedDB)

- **Async persistence and transactional clear**: Typing asynchronously overwrites only the latest device-local draft in IndexedDB (never syncing whole resources to `localStorage`), showing recovery-saved status only after confirmed persistence. Saving, canceling, or reverting compares the save identifier inside one IndexedDB transaction so another tab's later unsaved edits are never wiped.
- **Partial path updates**: Regular form edits allocate new objects only along the changed path and skip unchanged subtrees during dirty checks, avoiding cloning or JSON-serializing large cards/presets on every keystroke while preserving raw JSON apply and save-boundary validation.
- **Helper pending queue**: On a helper request, a saved resource sends only its ID and revision for server-side capture at admission, while an unsaved resource sends editor input for analysis; helper edits still target the saved revision and reach the open draft only as an editor conflict ([Editor context](HELPER-TOOLS.md#editor-context)). Helper input and pending requests share the IndexedDB recovery store; persistence failures retain input and allow retrying or sending without recovery storage.

### Concurrency control and idempotency guarantees

- **Single save path and CAS (`saveResource`)**: Both user and helper go through `saveResource` with `expectedRevision` CAS (concurrency control, not an agent permission gate). Existing revision-conflict warnings persist across subsequent save failures until copy-save succeeds or an explicit reload occurs.
- **Creation/clone idempotency and receipts**: Browser new-resource saves and list clones attach per-request idempotency keys backed by small permanent created-ID receipts (no DB schema change; legacy calls omitting keys stay non-idempotent). Unconfirmed new-resource requests live in a per-tab IndexedDB record separate from general unsaved input, and **이전 요청 확인** re-verifies only the frozen payload even while new edits have errors, keeping keys across auth/check errors, flagging conflicts if another window edited the created target, and preserving edits for save-as-new if the target was deleted.
- **Cloning and decoupled post-save work**: Cloning checks source revision and copies saved content only; a prompt's library display name and native internal name are independent. Post-creation folder placement checks the post-creation organization revision and skips with a notice on concurrent changes or legacy receipts; list refresh and folder placement decouple from save completion (never auto-retrying writes on follow-up failure), and resource change events refresh only dependent chats.

### Internal data structure for context control (`scene_context`)

- **Separate revisioned table**: Context toggles live in `scene_context` with a revision number separate from Run/Source rows and govern subsequent model context, compaction summaries, search, and helper chat reads. Context-compaction validity incorporates the scene-context revision because visibility toggles do not change text hashes.
- **Copies, backups, and transcript v2 fallback**: Chat copies, chat backups, and the optional `sceneContext` field in transcript v2 preserve this state; legacy transcript v2 files missing `sceneContext` default to all scenes active.

### Selection revision and in-reader refinement

- **Shared hook and displayed-translation hash**: `SelectionRevision` and `ReaderSelectionTools` share `useSelectionRevision` and `POST /api/sources/:id/selection-revision`. Translation targets send `target: 'translation'` and the displayed translation hash verified by `shownTranslationChanged` (shared with `editTranslation`) because revision alone cannot identify the visible translation while re-translation is in flight.
- **Context slicing and full-draft verification**: `surroundingDraft` slices the requested `context` scope server-side, while the client still sends the entire draft so the server verifies both the translation hash and selection range against the full text.
- **Strict matching (`uniqueTextRange`)**: Decides solely against the saved body without renderer-type gating (all bot chats use the Risu renderer) and, unlike `matchHelperText`, does not normalize trailing line whitespace so saves are blocked when visible selection diverges from saved text.
- **Overlay placement and verification**: Bar and popover mount fixed on `document.body` (outside Shadow DOM theme frames whose `transform` breaks fixed positioning), computed within visible reader and `data-uimori-body-scroll` bounds and hidden when neither above nor below fits. The open-and-apply flows are verified by `RSEL02`–`RSEL04` in `tests/reader-selection-browser.spec.ts` and `tests/selection-revision-browser.spec.ts`; no browser test pins the placement bounds.

### Helper result rows

- **Rows name saved targets only**: Row semantics live in [HELPER-TOOLS](HELPER-TOOLS.md#conversation-history-and-task-results). `HelperTaskResultItems` renders one row per result target and a Story UI preview under a saved theme; opening a row goes through `openHelperResult`, which never reloads an already open editor, so an unsaved draft survives (`HRESULT03` in `tests/helper-task-results-browser.spec.ts`).

### Text diff (`TextDiffView`)

- **Non-color diff accessibility and verification**: Additions and deletions pair `--success-bg` and `--error-bg` with underline, strikethrough, leading `+`/`−`, and screen-reader labels, capped at `--diff-max-h`. `EDIT01` in `tests/editor-changes-browser.spec.ts` covers the labels on the shared `TextDiffView`.

### Helper partial edits and string replacement algorithm

- **Block references and tolerant matching (`matchHelperText`)**: Block references stay bound to the previously read block across earlier deletions or moves. `resource.patch` and `scene.patch` share `matchHelperText`: exact match → CRLF/LF tolerance → trailing spaces/tabs tolerance, applying relaxed tiers only to a unique match and never normalizing quotes or dashes so prose style cannot silently change.
- **Toggles and retained undo**: Toggle definition changes prune newly invalid existing selections and report removed/reset keys while rejecting newly supplied invalid values. The single retained previous save can be read for comparison without saving; multi-step resource history and cloned-preset sync are not provided.

## Outline workspace and writing pipeline

The five outline levels use `OUTLINE_LEVELS`. Helper tool schemas and paging contracts (`outline.read`, `outline.write`) live in [OUTLINE](../OUTLINE.md#도우미-도구-계약-outlineread-outlinewrite) and [HELPER-TOOLS](HELPER-TOOLS.md#bounded-composition-reads).

### Writing context assembly and pipeline

- **Programmatic brief (`GET /api/outline-nodes/:id/brief`)**: Assembles `path`, `children`, deduplicated `related`, same-parent/level `neighbors`, and up to 40 recent current-branch `sources` (`planned`/`focus`) directly from persisted data without a model call; actual Run execution adds up to 40 lineage `written` nodes.
- **Context injection and reservation boundaries**: `RunSnapshot.outline → MainInput.outline → main-host-context` reuses the main writing budget check without replacing user requests, manuscripts, memos, or lore. `POST /api/outline-nodes/:id/scene-command` binds `additionalInstruction`, target revision, and plan hash before `POST /api/scene-commands/:id/run` schedules prose generation; there is no separate outline writer executor, no helper-to-story auto-promotion, and no standalone scene-reservation API detached from an outline.

### Reservation cancellation, idempotency and change detection

- **Cancellation on substantive plan edits**: Editing an unexecuted reservation's ancestor path, direct children, or related plans cancels it in the same save transaction (sibling-only edits, revision-only bumps, and rolled-back changes do not; admitted Runs keep their frozen input).
- **Focus freezing and source linking**: `GET/PUT /api/chats/:id/outline/focus` overwrites focus idempotently; normal Run admission (`run`, `preview-main`) calls `freezeOutlineFocus`, and manuscript commit calls `linkFocusSource` to record a `focus` link.
- **Client idempotency keys**: Outline-save and writing payloads and keys persist locally before send; **요청 결과 확인** verifies the exact request instead of duplicating it, and reusing a key with a different target or payload conflicts.

### Review technical contract

- **Read-only boundary and no persistent review store**: **원문과 점검** restricts app tools to `outline.read` and manuscript/lore reads (rejecting writes) with no separate review agent, approval flow, or persistent review table—outputs stay in helper history and task records. Initial excerpt budgets live in [OUTLINE](../OUTLINE.md#원문-점검과-복사백업-범위).

### Database schema and data preservation

- **Tables and preserved legacy data**: Active tables are `outline_nodes`, `outline_batches`, `outline_links`, `outline_writings` (`origin`: `planned` | `focus`), and `outline_focus`; existing `outline_reviews` and internal scene-command records remain preserved ([DATA-MIGRATIONS](../DATA-MIGRATIONS.md)).
- **Single source of truth**: Only one copy of each outline and manuscript is stored; succeeded execution payloads prune down to revision, hash, and source references. Copy and backup behavior lives in [OUTLINE](../OUTLINE.md#원문-점검과-복사백업-범위).

### Outline verification and scope

- **Single mounted instance (`OutlinePanel`)**: The right-panel outline tab (`sidecar`) and full-screen view (`workspace`) are one `OutlinePanel` instance toggled by visibility only so selection and unsaved edits survive switches; no second narrow implementation is built.
- **Cross-cutting tests and scope**: Verified by `tests/helper-outline.test.ts`, `tests/helper-workspace.test.ts`, and `tests/side-panel-browser.spec.ts` (including constant SQL query count as outline size grows and immutability of preserved review data; runner commands in [DEVELOPMENT](DEVELOPMENT.md)). Automatic replanning, multi-chapter automatic writing, shared templates, graph editors, and new memory-extraction systems are out of scope.

## Original-work reference (Story Guide)

### Execution pipeline and cache policy

- **Context composition**: Receives conversation, current summary, character card, persona, lorebook, card example dialogue (tone reference only, never factual events), author memos/notes, turn outline, and user request; regeneration excludes the replaced response.
- **Strict cache reuse**: A stored reference is reused only when input context, settings, model, and reference prompt match identically; references created after executing additional read tools are never reused.
- **Record ownership**: **마지막 집필 참고문** reflects only the reference actually included in the final main writing call (not the generation cache), so canceling before the main call or excluding it on request edit preserves the prior turn's record. Call structure, summarization budget, and copy/backup scope live in [STORY-GUIDE](../STORY-GUIDE.md#사용량실패-처리와-복사백업-범위).

- **Database contract**: Uses schema 15 lightweight chat metadata with no separate task-queue table, long-term memory store, or full-text search index.

## Manuscript search (FTS5 trigram)

### Index structure and change tracking (FTS5 trigram)

- **Derived tables and dirty queue**: `search_documents` and `search_trigrams` are derived data not rebuilt in full on restart. Edit transactions enqueue only `(source_id, revision)` in `search_dirty_sources`; a read Worker normalizes small batches and the main server checks revisions before applying index updates.
- **Write bounds**: Each index write caps at roughly 256KiB of combined old and new text or up to 8 scenes; a single very large scene indexes alone so responsiveness of other operations beats total index completion time.
- **Index storage format**: `search_documents.text` stores a single plain-text copy for snippets (no persisted lowercased copy) feeding the positionless trigram index `search_trigrams` (`detail=none`, `contentless_delete=1`); phrase queries narrow candidates via trigram AND and verify against stored plain text.
- **Latest-body overlay**: Search overlays dirty documents with their latest text inside the same SQLite read transaction so saves and deletions appear immediately even when indexing lags.

### Search queries and segment scanning

- **Trigram vs sequential scan**: Terms of 3+ characters narrow via `search_trigrams` before text verification, whereas shorter-only queries (including 2-character Hangul/Hanja/Kana auto-queries) scan sequentially in 200-scene segments because a trigram index cannot narrow terms under 3 characters. Cursor stability, snapshot scope, and **남은 원고 검색** live in [MANUSCRIPT-SEARCH](../MANUSCRIPT-SEARCH.md#검색-범위유지보수-모드와-제한-시간).

### API contract and ReaderTarget contract

- **Read-only security boundary (`manuscriptSearchRoutes`)**: Executes read-only (`PRAGMA query_only=ON`, active in maintenance mode) against only the server-chosen DB—never accepting raw SQL or file paths—under an 8-second Worker timeout and max-4 concurrency limit (`ManuscriptSearchQuery` / `ManuscriptSearchResult`).
- **`ReaderTarget`**: Shared navigation contract carrying chat, scene, representation, hash, and paragraph; falls back to scene start if body hash changed, and never places search queries or manuscript excerpts in URLs.
- **Browser coverage and scope**: Live search, navigation, and small-viewport layout are covered by `tests/personal-features-browser.spec.ts`. Dynamic script output and morphological/semantic search are out of scope.

## Reader navigation, streaming, renderer and helper sessions

- **Unused default helper conversation filtering (`listedHelperSessions`)**: Opening the helper creates a chat's default conversation; `HelperWorkspace.list` returns all conversations flagged `unused`, and `listedHelperSessions` hides unmodified empty default conversations from other chats' lists and the global list. ### Reader navigation state and SSE synchronization

- **One live connection per tab (`createLiveHub`, `liveStream`)**:
  - `web/live-stream.ts` owns the tab's only `EventSource`. It opens `/api/events` even when no chat is selected; selecting or switching a chat reopens that same connection with `chat=` and `streamAfter`, so a tab never holds two. Local development and the bundled nginx profile speak HTTP/1.1, where the 6-connection-per-origin limit makes a second per-tab connection stall other requests across two tabs; production behind Tailscale Serve negotiates HTTP/2 but keeps the same rule (`LIVE01` in `tests/live-events-browser.spec.ts`).
  - Global frames (`live`, `chats`, `helper`, `invalidate`) carry metadata only and never an `id:` line, so the composite `Last-Event-ID` below stays owned by the chat stream (`tests/live-events.test.ts`). The hub never replays: consumers re-read through the existing cursor endpoints, and a client whose socket buffer is full skips frames and receives a fresh `live` frame on drain. The `live` frame carries the hub's tails (`chatsSeq`, `helperSeq`, the `invalidations` count and `instanceId`), and the client signals `resync` only when they differ from what it has already received: on the first connection, after a restart, after skipped frames, or when something changed while it reconnected. Selecting a chat reopens the connection, and an unconditional `resync` made every subscriber re-read on each chat switch. `invalidate` frames carry their count so a reconnect also notices a missed volatile change. A return to a visible tab signals `visible`, and `createLiveRefresh` reads then only if it dropped a matching signal while hidden or the stream is not open.
  - `Store.event` and `HelperWorkspace.event` report through `Store.changed`; the hub coalesces those reports with `setImmediate` and reads afterwards. Transactions are synchronous, so the read sees only committed rows and a rolled-back write sends nothing. The same pump publishes each reported chat's stream, which is how replicated `helper.*` events reach an open chat without a manual `publish`. Writers that insert events without `Store.event` (`recordContentProfileEvents`, `recordPromptWorkspaceUpdate`) reach the hub through the app's `publish`/`publishAll`, which also notify it (the prompt-workspace routes and `resourceRoutes` call `publishAll` after each write); the remaining manual calls are harmless because every pump reads from a cursor.
  - The hub's heartbeat is a named `keepalive` event because SSE comments are invisible to scripts. The client reports `down` when the connection stays closed or when nothing, keepalive included, arrives for longer than a heartbeat interval allows (`liveDelay`); the silence rule is what catches a buffering proxy. `useLiveRefresh` polls only while `down`, so polling remains the degraded mode rather than a parallel path. A connection closed by a non-200 response is reopened with backoff, because the browser does not retry it on its own. Event-stream responses leave the `Connection` header to Node: an explicit `keep-alive` on a request that a proxy sent with `Connection: close` made Node answer the next request on the reused upstream socket with 400, which surfaced once the library-screen stream began ending on logout (`SHUI01`). Test mode accepts `POST /api/test/live-frame` to inject a frame for mocked browser harnesses.
  - The helper panel's readers (`useHelperConversation`, `useHelperSessions`, `useHelperActivity`, `useHelperTaskResults`) refresh only on matching frames and `resync`, through `createLiveRefresh`; an open, idle panel therefore makes no requests. A frame carries the event kind and task ID, so the conversation and list readers apply the diagnostic classification to the frame itself and skip diagnostic frames without a read, while task activity and results read on every frame of their task. The exception is a task the open conversation still shows as queued: `HelperWorkspace.start` writes no event, so the first event after the claim, often a diagnostic one, is the only sign that the task began running. The list and task readers space their reads by `helperRefreshSpacing` because tool-heavy tasks emit events in bursts and the conversation list is the most expensive helper read. Degraded intervals live in `helperPollDelay`; task activity and results poll only while their task is active. The all-conversations list also follows `chat.title.*` frames of the chats it lists, because it shows their titles.
  - Views of server data that other code can change subscribe to frames themselves (`web/live-frames.ts`) instead of window events: the library, the prompt workspace, the request preview, resource editors, package features and chat options on finished tasks, saved artifacts, settings and resource writes; content and prompt presets also on `invalidate:resources` (`resourceFrame`), which `ProductStore.saveInTransaction` sends for every content and prompt-preset write, so a save from another device, tab or client reaches the resource editor, package features, the request preview, the prompt workspace and the library without a focus change; themes, illustration presets and fonts on `invalidate:themes`, `invalidate:illustration-presets` and `invalidate:fonts` (`presentationFrame`); prompt-workspace views on `prompt-workspace.updated`. The window events were sent only by the open conversation's reader, so a task finished with the panel closed, in another conversation or on another device refreshed nothing. Those three catalogs write no event row, so their shared writers (`writePreferences` in `server/themes.ts`, `server/fonts.ts` and `server/illustration-presets.ts`, `saveTheme`, `savePalette`, `saveIllustrationPreset`, `registerFont`, `deleteFont`) call `Store.invalidated`; settings, helper tools and resource saves all go through them, which is why the views no longer listen to the helper's `theme.updated`, `font.updated` and `illustration-preset.updated` events, to window focus or to a cross-tab storage signal (`SETSYNC02` in `tests/settings-sync-browser.spec.ts`). `ContextPanel` reads on its chat's `context.*` frames, so it follows a change even while the reader is paused, and polls at `contextJobPollDelay` only while a compaction job is pending, because the move from queued to running writes no event.
  - A local save whose server write produces a frame (`announceLocalChange` with `echoed`) is announced inside the tab only while the stream is not open, so an open tab reads once, from the frame; a save the stream does not echo as that frame (provider settings, resource-editor saves) is announced every time. The one-time read that every subscriber makes on the first `live` frame is the price of not missing a change between its initial read and the connection opening.
  - List changes that write no helper event (creating, copying or deleting a conversation, creating, renaming or deleting a group, raising a read mark) call `Store.invalidated('helper-list')` after their transaction, and a replayed creation request sends nothing. `acknowledgeActivities` sends `activity` only when it stored a new acknowledgement, and deleting a chat sends both, because the deletion writes no event the hub could read. `deleteChat` also sends `chats` (`chatListFrame`), on which `useStory` re-reads the chat list, and `deleteLibraryItem` sends `resources`, so a chat, library item, model or option preset deleted by another tab, device or MCP client leaves the open lists without a focus change; the stream of the deleted chat itself is still closed with `chat.deleted`. `Store.invalidated` inside `Store.transaction` is held until the outermost commit, sent once per name and dropped on rollback, including a rolled-back savepoint. Invalidations are not replayed; a tab that misses one catches up on its next `resync`.
- **Single navigation state machine**: Repeated navigation to the same URL (`A→B→A`) or scene re-selection counts as a new intent so late fetches or retries cannot overwrite the active view or bounce chats.
- **SSE cursor and backoff**: Retries transient errors with exponential backoff up to 5s, marks full resync complete only after applying to screen, and cancels retry timers on chat leave. An initial non-disconnect `snapshot` skips a second full fetch (fetching incrementally only if behind), while new events arriving during the initial fetch trigger immediately; post-disconnect or failed-initial snapshots perform a full resync.
- **Global prompt-setting events (`recordPromptWorkspaceUpdate`)**: Writes one latest-change record in `app_metadata` reserving a sequence from `events`'s `AUTOINCREMENT` so `Store.events()` and `latestEventSequence()` merge `prompt-workspace.updated` into every chat's SSE stream, Reader cursor, and display revision; legacy per-chat rows remain delivered (`tests/response-transport.test.ts`).
- **`/reader` block text**: Slices `text` from original or translation on receipt because the server sends range-only blocks.
- **Idle-tab power saving**: Library view and background tabs pause Reader polling and retries while retaining cursor and notifications; card input prompts check only on SSE events, reconnects, and view return, coalescing overlapping checks and preserving next-prompt drafts across late acknowledgements.
- **Live response streaming**:
  - Multiplexes the selected chat's response text and library-scope helper text (`chatId` null, `subscribeChat(null)`) onto the tab's live connection as `event: stream` frames, with or without a selected chat, instead of per-response connections to avoid HTTP/1.1's 6-connection-per-origin limit (separate chat, main, and helper connections would stall other requests across two busy tabs).
  - `ResponseStreamStore` delivery and persistence batching is owned by [Execution input lifetime, Batch recovery and response streams](PROVIDERS-AND-CODEX.md#execution-input-lifetime-batch-recovery-and-response-streams); cursor polling reads text not yet persisted so push and poll share sequence numbers, and `StreamingResponse` merges push and poll pages through one per-task cursor.
  - Every frame `id` carries composite `<채팅 순번>;<종류>:<작업 ID>:<글 순번>,...` (`<chatSeq>;<kind>:<taskId>:<textSeq>,...`) so browser reconnects resume both independent sequences via `Last-Event-ID` alone; fresh connections pass `streamAfter`, and a gap in frame `after` falls back to cursor polling.
  - Cursor polling fallback (helpers of other chats in the all-conversations view, partial views, disconnects, mount, re-visibility) runs at `responseStreamPollDelay`, once after push silence to avoid stalls behind buffering proxies (`HELPLIVE03` in `tests/helper-live-browser.spec.ts`), and hidden tabs discard push pages and stop polling (`tests/response-stream-browser.spec.ts`).
- **Streaming during translation**: `SourceReader` renders translation streams via `StreamingResponse` with `quietUntilText` (preserving the preparing indicator until `onText`), shows only the latest attempt without Story UI, keeps the existing translation while re-translating, and swaps to the saved translation on completion. Structured output, submit tools, Codex, and Story UI placeholder tags suppress raw streaming via `publicProgressAllowed`; verified by `tests/translation-stream.test.ts` and `STREAMTRANSLATION` in `tests/response-stream-browser.spec.ts`.
- **Side-panel width and reading position**: Opening, closing, or resizing the right panel holds the reading paragraph steady via browser scroll anchoring (`overflow-anchor: auto`, `web/style.css`). Dragging updates only `--panel-w` on `.app-shell` outside React, bypassing `changeLayout` in `useReadingPreferences`; verified by `tests/side-panel-browser.spec.ts`.
- **Bottom follow (`useBottomFollow`)**: Shared by main reader and helper; the main reader follows only from request send until chat completion (never on chat switch or page load). Scrolling up stops immediately, returning within 80px resumes, shrinking content does not count as scrolling up (decided by `followAfterScroll`), callers move a followed scroller only through `follow()` or `place()` so a user scroll in the same frame is still seen as moving up, and in-progress responses scroll the reader container rather than `data-uimori-body-scroll` because they sit outside scene theme frames.
- **Auto-translation switching and interaction guard (`SourceReader`)**: Tracks wheel, touch move, scroll keys, scrollbar clicks, text selection (including Shadow DOM via `readerContains`), and open editors per scene; clears on entering queued/running translation except when a selection or editor stays open at completion. ### Renderer architecture and DOM contract

- **Streaming paragraph rendering (`splitCompletedParagraphs`)**: Compiles completed blank-line-delimited leading paragraphs with the finished-prose compiler (`Prose` / `HelperMessageProse`) while rendering only the in-progress last paragraph as plain text in the same font, ignoring blank lines inside unclosed code fences or `<a2ui>` blocks. ### Helper sessions

- **Session ownership and transcript edits**: Each chat owns independent helper sessions whose background tasks continue across panel close or session switch; chat copies never share mutable defaults. ## Reading state and bookmarks

### Reading position data schema and storage layers

- **Storage split**: `reading_positions` keeps exactly 1 latest position per browser and chat (`chatId`, `sourceId`, `representation`, `contentHash`, `blockAnchor`, `offsetRatio`; no pixel coordinates or scroll logs go to the server). `localStorage` holds the device scroll cache (falling back to `sessionStorage` in the same tab when `localStorage` writes fail), `sessionStorage` holds composer cursor/tab transient state, and the browser's random `clientId` is not an auth credential.

- **Multi-tab CAS and sequential handoff**: Concurrent tab writes use `expectedRevision` CAS; stale positions are not force-retried (re-checked on next entry/return), and new scroll activity during an in-flight save chains sequentially after completion when leaving or closing a tab.

- **Ownership and persistence boundary (`readingStateRoutes`)**: Bookmarks have no TTL and are never auto-deleted on anchor drift; reading positions and bookmarks delete only with their chat. ## Browser storage keys

Families without such an owner signal take a `cap` and are written through `writeRecentStorage`, which keeps the most recently written keys in `uimori:storage-recency:v1`: 500 illustration collapse choices, 200 prompt option groups, 200 helper confirmation declines. Activity acknowledgements the server already returned are dropped locally beyond the newest 100 per chat (`forgetConfirmedAcknowledgements`), which still covers every activity the chat view can show. A collapse or folder state equal to its default is removed instead of written.
- **Per-browser presentation settings (`usePresentationSetting`)**: Screen mode, reading font, size and width, readability, reading language, response display, Enter-to-send, sidebar width, scene navigator and illustration folding stay in this browser's `localStorage` and are not sent to the server, as the user guides promise. A value is written only when it differs from what storage already holds, so opening a tab writes nothing and cannot replace a newer choice made in another tab with its own defaults or repaired values; other tabs follow through the `storage` event. Sidebar collapse and the right panel width are written the same way but are not followed, because they describe one window's layout (`SETSYNC01` in `tests/settings-sync-browser.spec.ts`).
- **Refused writes**: Presentation settings report a refused write once (`watchPresentationWriteFailure`). A refused `sessionStorage` write of a draft (request and helper message edits, source text edits, the retry request, story UI fields, the input translation original, a parked queued request) shows `chatsettings.m159` where the user is editing; IndexedDB drafts, the helper outbox and pending helper requests keep their own error paths. Cosmetic state (collapse, sort, view, folder state) stays silent.

## UI language (I18N)

### Message representation and ICU formatting contract

- **Per-language catalog chunks (`uimori-locale-catalogs` in `vite.config.ts`)**: Four-language sources in `web/locales/*.ts` compile via `web/locales/{ko,en,ja,zh}.ts` into single-language JSON so only `web/locales/ko.ts` ships in the startup bundle (required synchronously for the Korean fallback), while `en`/`ja`/`zh` load on demand. Startup-bundle modules that need Korean messages (`web/i18n.ts`, `web/request-file-errors.ts`) must import `web/locales/ko.ts`, never multi-language sources such as `web/locales/errors.ts`.
- **Startup loading and switching**: Startup awaits `loadInitialLocale()` before first render so wrong-language strings or raw keys never flash (falling back to Korean for the session if chunk load fails); overlapping switches resolve to the latest choice, and synchronous callers/tests preload via `loadLocale()`.
- **ICU runtime and render subscriptions**: Uses `intl-messageformat` as the sole runtime dependency (no custom plural parser or HTML interpolation). Components subscribe via `useI18n()` without caching translations in module-level constants; missing keys fall back to Korean while undefined keys render literally and fail static checks.
- **UI messages (`web/ui-message.ts`)**: UI text the web keeps in state is a `UiMessage` object, never formatted text: `uiMessage(key, values)` names a catalog key typed as `MessageKey` (so a missing key fails `tsc`), and `uiText(text)` carries user text verbatim. A value may itself be a `UiMessage`, or an array of them that renders as their concatenation, and `formatUiMessage()` formats the whole tree at render in the current language. A caught error becomes a `UiMessage` through `toUiMessage(cause, fallback)` in `web/api-errors.ts`: a `UiError`, and `ApiError`, which extends it, gives its `uiMessage`; a core `ValidationError` gives its catalog entry; anything else, including a plain `Error` even when its text looks like a catalog key, `Failed to fetch` and English model or validator text, gives the fallback (`errors.unexpected` unless the caller names one). An error's own text therefore never reaches the screen, and a failure the web raises for someone to read is a `UiError(uiMessage(key))`; one the caller can recover from without an error, such as a folder placement that did not happen, is a result instead. `NoticeBanner`, `TransientNotice`, `DeleteButton`, `LoadingState` and `DismissibleError` accept only a `UiMessage` (`NoticeBanner` children may also be other React content), so `tsc` names every place that still hands them a string, and every `onError` prop takes `UiMessage | null`, where `null` clears the error. `scripts/check-ui-message.mjs`, run by `npm run quality`, fails on reading `.message` (calling a method of that name is not a read) or destructuring `message` anywhere in `web/` outside `web/ui-message.ts`, and on `String(caught)`, a template literal holding `caught` or `caught.toString()` for a `catch` parameter. With no allowlist, it also fails on an `Error`, `TypeError`, `RangeError`, `SyntaxError`, `DOMException` or `AggregateError` built (or a `super(...)` in a class extending one) with anything but literal text, and on throwing a string, so a developer-only invariant keeps literal text and every other failure is a `UiError`. `scripts/ui-message-allowlist.json` has only a `permanent` section, naming a field a library or stored data calls `message` with its exact count and reason (the `@codemirror/lint` diagnostic, and `ProviderRejection.message`, stored in `attempts.response` and `provider_connection_tests.body`); a mismatch there is corrected by hand. `UiError.message`, and so `ApiError.message`, is a diagnostic naming the catalog key and its values, in no interface language, and the check above is what keeps it off the screen. A Risu import or preset finding carries no text: it is a `code` from `RisuImportFindingParams` (`core/risu-import.ts`) or `RisuPresetFindingParams` (`core/risu-preset.ts`), its `level` and typed `params`, and `web/risu-finding-messages.ts` words it; `tests/error-contract.test.ts` holds each message to the finding's param names in all four locales. The same check fails, with no allowlist, on any `JSON.parse` in `web/` outside `web/json.ts`, a module without imports so storage helpers can use it: text or a file someone supplied goes through `parseJsonInput` or `readJsonFile` (`web/json-input.ts`), browser storage and other text that may be stale or corrupt through `tryParseJson` with a fallback, and JSON this build serialized itself (a server event frame, a memo key) through `parseOwnJson`, which leaves a malformed frame unguarded because the server and web ship in one build.
- **Render-time labels and stored status codes**: A label a component computes at render (`IconButton` `label` and `title`, `SaveButton` `label` and `text`, `DraftDiscardActions` button labels) is a plain string from `t()`, because it is recomputed on a language switch; only what outlives a render (state, a callback argument, a thrown error) is a `UiMessage`. Status text the server stores for the web is a code the web renders with `translateStoredCode()`: backup status (`BackupStatusCode` in `core/backups.ts`), a push device's last delivery error (`PushDeviceError` in `core/push.ts`); Korean text that 0.18.x stored in those fields renders verbatim; no Korean text maps back to a key. A context failure (`context_jobs.error`, a run snapshot's `contextPlan.error`, and a `CONTEXT_` code, `CONNECTION_NOT_AUTHORIZED` or `MODEL_REQUIRED:<role>` in `runs.error`) is a `ContextFailureCode` (`core/context-plan.ts`): a context code, `MODEL_REQUIRED:<role>`, a stored request image code (`STORED_REQUEST_IMAGE_ERRORS` in `core/request-images.ts`) or a provider prompt-shape code with its `:block=…` tail removed. `fail()` and `ContextCompactionError.code` take only that type, and `contextFailureCode` in `server/context-failure.ts` folds anything else to `CONTEXT_COMPACTION_FAILED` (or the caller's fallback) and writes `CONTEXT_FAILURE_FOLDED` with `failureLabel` (`server/failure-label.ts`, the same label request failures log) to stderr, so the web table in `web/context-error.tsx`, typed with `satisfies Record<…, MessageKey>`, has a message for every code the server stores. Text an older build stored renders as the generic failure with the raw text under its details; the English text interrupted jobs stored (`Server stopped; explicit retry required`) reads as `CONTEXT_JOB_INTERRUPTED`. A connection test keeps the transport code it stored, because `ProviderModelTest` and `helper-vertex-location-tools.ts` branch on exact codes; the screen words it by family (`providerFailureKey` in `web/provider-failure.ts`, shared with `RetryFailure`) and keeps the code under its error details. The prompt preview answers `error: { code, detail? }`: a `ProviderContractError` code with its diagnostic tail in `detail`, or `PROMPT_PREVIEW_FAILED`, never an exception's text.
- **Built-in labels (`web/builtin-labels.ts`)**: The web names built-in layouts, palettes, the default illustration preset, provider protocols, tokenizer profiles and usage kinds through maps typed by their id unions (`BuiltinThemeId`, `BuiltinPaletteId`, `ProviderProtocol`, `TokenizerProfileId`, `UsageKind`), so a new id without a label fails `tsc`. `core` keeps no translation keys: `BUILTIN_THEMES` and `BUILTIN_PALETTES` keep Korean `title` and `description` because the helper's `theme.list` reads them, and provider definitions, tokenizer profiles and usage kinds carry no labels. A built-in palette is one without a `revision`. A new item's default name (a layout, illustration preset, regex, lore entry or folder, toggle label and select options, an unnamed pasted request image), a copy suffix (`shared.copySuffix`, trimmed through `copyTitle` in `core/copy-title.ts` to the title limit wherever the item has one), a collaboration template's agent name and description (`settings.agent*`, distinct from the picker button text), and a built-in's duplicate or export are the text of the current language at the moment of creation, stored as plain text and never a key; a saved name never changes on a language switch, and nothing compares a stored name against a catalog default. Where the server composes the name, the web sends the language: the chat copy request carries `titleLocale` so `numberedCopyTitle` in `server/chat-fork.ts` numbers within one language's label and strips any language's label (the helper's own fork and a retry copy send none and keep the Korean label; `titleLocale` is not part of the fork's idempotency digest), and the usage export carries `lang` for the `usageCsv` headers in `server/usage-report.ts`. Fixed download file names stay language-neutral.
- **Locale formatting**: `formatNumber` and `formatDate` reuse `Intl` formatters per locale and option set while keeping USD currency, KST usage rollups, backup time zones, ISO query ranges, raw numeric values, and Korean K/M abbreviations unchanged; invalid timestamps omit dates cleanly.

### API errors and external boundary handling

- **Structured error wire (`errorWire` in `server/app-errors.ts`, `readErrorWire` in `packages/contracts/src/errors/wire.ts`)**: An `AppError` answers `{ code, params? }` with a code from the `AppErrorCode` catalog and no `error` string; every other failure answers `{ error }` with English request-validation text the web never shows, and a route registered through `registerEndpoint` (`server/endpoint.ts`) answers input its schema rejects with `INVALID_REQUEST` and no params, keeping the English issue list only in the thrown message that a helper tool reports to the model; and no thrown message in `server/` or `core/` is Korean: `findKoreanServerErrors` in `scripts/check-i18n.mjs` fails `npm run quality` on Hangul inside a `throw`, `new …Error(…)` or `reject(…)` there. A `core` validator that the web may also run locally (themes, palettes, theme backgrounds, illustration presets, translation guides, Risu package images, the pinned-lore budget, the native Risu source and its illustration profiles, native preset toggle keys and structure, Risu content, chat overrides and openings) throws a `ValidationError` (`core/validation-error.ts`) with a catalog code, its params and English text for the model. The web shows it with `toUiMessage` in `web/api-errors.ts`; a `field` param is a JSON path such as `appCss`, which `fieldLabels` there turns into the editor's own label, and an unknown path shows as written. The server turns it into an `AppError` with `validationAppError` (`server/app-errors.ts`), whose message is `CODE: English text`, at the theme, palette, background, illustration-preset and package-store boundaries, so every `instanceof HttpError` branch behind them sees a 400 or 409, and `helperToolError` hands that message to the model with the code and params; a resource patch the helper sends that fails one of them returns as a patch validation failure (`validationFailure` in `server/helper-resource-editing.ts`) with that message, so the model can correct it. Only codes a user can act on are catalogued separately (the opening text limit, `PACKAGE_START_NOT_FOUND`); a structural failure of Risu content or an opening answers `RISU_CONTENT_INVALID` or `PACKAGE_START_INVALID` and keeps its reason, such as `PACKAGE_LORE_FOLDER_REFERENCE`, only in the English text, because every param would have to appear in each locale's sentence. `RisuPromptError` (`core/risu-prompt.ts`) stays outside the catalog because its `PROMPT_*` code is stored in job diagnostics; `risuPromptAppErrorCode` turns it into `RISU_PROMPT_TOO_LARGE` or `RISU_PROMPT_INVALID` in `asAppError` and in `toUiMessage`. A JSON field parses through `parseJsonInput` and a chosen file through `readJsonFile` (`web/json-input.ts`), which show `errors.invalidJson` or the caller's own message instead of the browser's `SyntaxError`, also when the file cannot be read. The web reads only `code` and passes `params` to the message unchecked because the server and web ship in one build. A param named `…Bytes` travels as a byte count and `messageValues` in `web/api-errors.ts` renders it in MiB; text limits travel as character counts. `asAppError` (`server/app-errors.ts`) is the one conversion of `core` errors into catalog codes, used by the app error handler, `shellBridgeFailure`, `helperToolError` and the prepared Risu import worker: a `ValidationError` answers its own code, status and params, a `NativeTransferError` its own code when that code is catalogued and `NATIVE_TRANSFER_FILE_INVALID` otherwise, a `ChatTranscriptError` one of the four transcript codes the web words separately or `CHAT_TRANSCRIPT_INVALID`, and an `AgentCollaborationError` `AGENT_COLLABORATION_INVALID`; the original text stays in the message as `CODE: detail` for the model. The worker posts `risuWorkerOutcome`'s `code`, `statusCode` and `params`, and `server/risu-import-prepared.ts` rebuilds the `AppError` with `appErrorFrom`, so size limits keep their `maxBytes`. Risu runtime and Lua session errors carry status 400, which the web reads as a definite refusal; `withRisuFailureCode` (`server/risu-failure-code.ts`) reads the leading `RISU_*` code of a failure: a script timeout answers `RISU_NATIVE_TIMEOUT` as a definite 400 on `/risu-action`, whose run is already recorded as failed, and the read-only `/presentation` answers every `RISU_*` failure, timeouts included, as a logged 500. `web/api-errors.ts` maps the catalog with `satisfies`, so a code without a message fails `tsc`, and `tests/error-contract.test.ts` holds each message to the code's `AppErrorParams` names in all four locales. `HelperToolError` carries model-facing `CODE: detail` diagnostics for helper tools and stays outside the catalog. A helper error the web helper panel can also receive is a catalog `AppError`, and `helperToolError` in `server/helper-runtime.ts` passes its `code` and `params` to the model; that function derives `retryMode` from the code and status alone, so a renamed code must keep matching its patterns there. Compaction failures are stored codes (`HELPER_COMPACTION_FAILURES` in `core/helper.ts`) that `web/helper-task-error.ts` renders, not the wire; so are the request image and file codes a run or helper task stores, which `web/request-image-errors.ts` and `web/request-file-errors.ts` read. Failure text stored in the database keeps its schema-15 form and is not the wire: a run or auxiliary job that stops on a missing model stores `MODEL_REQUIRED:<role>` (`storedModelRequired` in `server/app-errors.ts`), which `web/auxiliary-error.ts` reads, and an illustration job stores its bare code, which `illustrationErrorMessage` in `web/illustration-labels.ts` reads from `appErrorMessages` when the code is a param-free catalog code and from its own table only for codes the runner alone stores. `MANUSCRIPT_TRANSLATION_MISSING` sends the first 20 missing scene numbers as a comma-separated `scenes` string with the `total`, and the web renders the scene labels in the current language. The illustration generator connection tests answer `{ ok: false, code }` with status 200, because a failed test is the result the settings screen shows. The error wire imports no zod: `web/api.ts` is in the startup bundle and zod is not, which `tests/web-runtime-boundary.test.ts` enforces over the eager imports of `web/main.tsx` and `packages/contracts/src/index.ts`.
- **Wire contract and raw-data boundaries**: `ApiError.code` is the wire code and `ApiError.uiMessage` its catalog message; an uncoded failure, a DELETE conflict included, shows the generic message for its status, because an uncoded `error` is English text for the model. No HTTP error depends on matching Korean text, and internal logic inspects codes, statuses, and numbers rather than localized copy. Provider diagnostic logs render verbatim.
- **Service worker and manifest**: SW persists the locale at `settings/ui-language` in `uimori-presentation` IndexedDB and reads it per push event (defaulting to Korean) without adding caching, automatic resends, or forced reloads. Per-language static manifests keep app ID, name, start URL, and `/` scope fixed; browser/OS controls permission prompts, install menu language, manifest refresh, and SW activation.
- **Catalog keys stay reachable (`findUnusedMessages` in `scripts/check-i18n.mjs`, run by `npm run quality`)**: A key is used when it appears as a string literal in `web`, `core`, `server`, `scripts` or `tests`; when a template literal or `'prefix.' +` concatenation that starts with a key segment can produce it (`t(\`palettes.color.${key}\`)`). Its Korean value appearing in source does not count. Any other key fails the check and is removed from all four languages. A derivation the scan cannot see goes in `retainedMessagePrefixes` with its reason; today that is only `errors.auxiliary.`, whose `.details` keys `web/auxiliary-error.ts` builds by replacing `.message`. New keys take semantic names (`common.languageNotSaved`), not numbered ones such as `chatsettings.m67`; existing numbered keys keep their names.
- **Korean literals in `web/` (`koreanLiteralErrors` in `scripts/check-i18n.mjs`, run by `npm run quality`)**: A string literal, template text, JSX text or attribute value, or CSS declaration containing Hangul in `web/` outside `web/locales/` fails the check, because UI text there ignores the reader's language; comments and regular expressions are not counted. An internal key or sentinel takes a non-Korean value: an ungrouped prompt control's group is `''`, and the toggle document's root group has an empty name, which the editor never matches against named groups. `scripts/korean-literal-allowlist.json` keeps two sections: `permanent` names a file whose Korean text stays, with its count and reason, and a mismatch there is corrected by hand; `debt` holds the per-file count not yet converted, which may only go down, and `node scripts/check-i18n.mjs --shrink` lowers it and never touches `permanent`. What stays Korean follows the boundaries in [UI language](../I18N.md): a language's own name, the service worker's own notification table, a stored legacy pricing note compared against saved rows, model inputs (a new note's default author, the lore-context preview query), and the reading and story UI preview fixtures.
- **Verification**: Error wire handling is covered by `tests/api-errors.test.ts`. `check:i18n -- --candidates` lists every Korean literal, including model inputs, persisted defaults, and legacy errors, so blind bulk replacement is prohibited; runner commands live in [DEVELOPMENT](DEVELOPMENT.md#verification-runners).

### Automatic chat title generation contract

- **Scheduled language**: Automatic titles generate in the app's UI language at schedule time using an English prompt instruction; a scheduled task whose language is not a supported UI locale fails with `TITLE_LOCALE_INVALID` before any model request.

## Themes, built-in assets and verification

- **Built-in assets and color keys**: Built-in asset files live in `third_party/theme-assets` with hashes pinned in `BUILTIN_THEME_ASSET_FILES` (sample theme fixtures live in `fixtures/themes/`); cloning and saving copies them into user themes for self-contained export. Custom decorative art regenerates from SVG via `scripts/theme-art/<레이아웃>.mjs` (`scripts/theme-art/<layout>.mjs`), after which its hash in `BUILTIN_THEME_ASSET_FILES` must be updated. Color names omit the leading `--`; the canonical list is `THEME_COLOR_KEYS` (`packages/contracts/src/domains/appearance/theme-vocabulary.ts`, beside `storyUiStyles`).

### Built-in layouts and palette sources of truth

- **Sources of truth and user-theme preservation**: Built-in layouts and `BUILTIN_PALETTES` are the canonical sources of truth; cloned or imported user themes and their colors are never deleted or overwritten.
- **Deleted scopes**: Deleting a bot or chat drops its theme, palette, story UI, background and illustration preset choices (`removeThemeScope`, `removeIllustrationPresetScope`) and leaves the themes and recipes themselves. A choice for a bot that is hidden or already purged, or a chat that no longer exists, answers 409 `REVISION_CONFLICT` (`assertAppearanceTargetLive`), because a bot deletion with no choice of its own bumps no preference revision a stale tab could trip on.
- **Backup boundary and scope**: Theme JSON stores layout original colors and excludes separate palettes and scope bindings (preserved in workspace SQLite backups), and theme edits/deletions never alter manuscripts or model inputs. Expression panels, BGM, TTS, and input translation are out of scope; verification commands live in [DEVELOPMENT](DEVELOPMENT.md#builds-and-evidence) and [DEVELOPMENT](DEVELOPMENT.md#verification-runners).

## Usage report and backfill

- **Lightweight `attempts` ledger**: Stores only call timestamps, purposes, test flags, and compact numeric estimate columns; usage queries never read manuscripts or prompt JSON, and deletion cleanup leaves numeric columns intact without loading or parsing request/response bodies in JS.
- **Deferred settlement and classification ownership**: Minimal frozen pricing metadata is kept only while an in-flight call awaits late settlement. Collaborative `agentId` and helper `purpose` are classified by the host; model output never alters billing classification.
- **Backfill (`backfillUnpricedCalls`)**: Estimates only unpriced historical calls lacking provider-reported cost so recorded prices are never rewritten retroactively; usage totals recompute from call records immediately while saved task totals stay unchanged. Pricing tool schemas live in `HELPER_PRICING_TOOLS`, and operational pricing/reporting rules (`시각 미확인`, search fees) live in [USAGE-REPORT](../USAGE-REPORT.md#추가-집계-규칙과-단가-소급-적용) and [HELPER-TOOLS](HELPER-TOOLS.md#web-search-and-model-pricing).
- **Read-only query boundary (`usageRoutes`)**: Auth-gated read-only queries never trigger model calls, price re-fetches, or scheduled jobs. Cross-cutting pricing and usage display regressions are verified by `tests/pricing-store.test.ts`, `tests/usage-display.test.ts` and `PWUI04` in `tests/personal-features-browser.spec.ts`.

## HTTP compression, private ETag and maintenance mode

- **Compression (`registerResponseCompression`)**: Hashed `/assets/*` serve 1-year `immutable` with prebuilt `.br`/`.gz` copies (`vite.config.ts`), while `index.html`, service worker, and manifests retain existing headers without precompressed copies. JSON and text API responses of at least `COMPRESSION_THRESHOLD_BYTES` (1 KiB) compress with Brotli (`BROTLI_QUALITY = 4`) or gzip; SSE, images, fonts, and archives stay uncompressed.
- **Private ETag (`revalidatePrivateJson`)**: Attaches `ETag` and `Cache-Control: private, no-cache` on authenticated `GET` responses of endpoints marked `cache: 'revalidate'` and of the unconverted routes in `REVALIDATED_ROUTES`, returning `304` when unchanged.
- **Maintenance boot boundary (`maintenanceRoutes`)**: `UIMORI_MAINTENANCE=1` permits DB entry and reads without task recovery or workers and cannot be opened via API (`409 MAINTENANCE_BOOT`). Because SQLite is not opened read-only, always verify against a DB copy rather than the sole production DB; operational procedures live in [SELF-HOST](../SELF-HOST.md#유지보수-모드), [UPDATES](../UPDATES.md#유지보수-모드), and [ORACLE-RELEASE](ORACLE-RELEASE.md).
