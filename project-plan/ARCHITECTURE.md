# 아키텍처 계약 v0.6.1

제안된 이름은 구현을 강제하는 클래스 목록이 아니다. 아래 경계와 동작을 유지하면 더 단순한 표현으로 구현할 수 있다.

## 1. 배치와 코드 경계

TypeScript, React/Vite, Node/Fastify, 서버 로컬 SQLite WAL을 사용한 모듈형 모놀리스가 출발안이다. 런타임·패키지 버전은 Windows 실제 지원을 확인하고 lockfile로 고정한다. 첫 구조는 web/server/core 정도의 몇 개 경계로 시작하며 미래 도메인마다 별도 패키지를 만들지 않는다.

명령 HTTP + 이벤트 구독(SSE를 기본 후보로 삼되 재접속·인증 계약이 더 적합하면 동등한 전송으로 변경 가능). 브라우저는 DB 파일을 공유하지 않는다. 서버 한 개가 DB와 장기 작업을 소유한다. LLM 응답을 기다리는 동안 DB transaction/쓰기 lock을 유지하지 않는다. 긴 출력은 UI에 묶어서 전송하고 영속 기록은 완료/중요 경계와 적당한 checkpoint로 남긴다. 모든 토큰에 DB row를 만들거나 전체 대화 상태를 직렬화하지 않는다.

서버에는 작은 durable jobs 테이블/처리 루프를 두고 기본 한 프로세스가 소유한다. 큐/이벤트/worker는 구현 경계이지 Redis/Kafka/Temporal 도입 이유가 아니다. 재시작 때 queued/실행중/완료/불확실 작업을 구분한다. 원격 과금 요청을 무조건 다시 시작하지 않는다.

## 2. 콘텐츠와 실행

콘텐츠 패키지는 character/persona/world/style/skill/UI 자원 등을 버전 관리한다. 패키지 형식은 통일하되 자료·지시·실행 도구·권한은 의미가 다르다. 캐릭터와 페르소나는 같은 actor 정의를 역할별로 사용할 수 있다. 모든 NPC에 독립 에이전트를 붙이지 않는다.

PromptProgram(편집 가능한 텍스트+타입 있는 제어+명시적 조립 규칙), CreativePreset(제어 조합), ModelPreset(모델/생성설정), ProviderConnection(프로토콜/endpoint/credential ref), ExecutionPolicy(도구·예산·취소)를 분리한다.

채팅은 버전 있는 콘텐츠를 장착하고 채팅별 override를 가진다. 전역 값은 새 채팅의 기본값일 뿐 기존 실행을 몰래 바꾸지 않는다. Run 시작 시 설정·콘텐츠·읽기 범위·가격 근거를 snapshot으로 고정한다. 권한 폐기와 비밀키 폐기는 실행 경계에서 최신 정책으로 재확인한다. secret 원문은 snapshot에 저장하지 않는다.

역할별 context/profile은 필요한 계약·자료목록·tools·output schema를 제공한다. 저장소 개발용 AGENTS.md/.agents/skills와 앱 안에서 사용하는 창작/번역용 문서 패키지는 분리한다. 앱 리소스를 설치했다고 개발 에이전트의 권한이나 상시 지시가 바뀌지 않는다.

## 3. 작품·분기·작업의 최소 데이터 계약

- 작품/채팅: 사용자가 이어가는 단위. 봇은 재사용 콘텐츠이고 채팅 자체가 아니다.
- 서사 revision/node: 불변 입력·원고 또는 명시적 작가 설정 변경. 단일 부모의 tree로 시작한다. 과거 원문 편집은 새 revision/분기를 만들며 기존 후손을 몰래 재해석하지 않는다.
- 분기: 현재 이어갈 경로와 head revision. 화면에서 고른 후보는 device view이며 공유 head를 무조건 움직이지 않는다.
- Run / ModelAttempt: 고정된 입력으로 수행한 작업/실제 provider 호출. 실패와 과금 기록도 보존한다.
- DerivedArtifact / Job: 번역·상태 제안·기억 등 특정 원문과 의존 버전에서 만들어진 파생물.

독서 커서·임시 입력·토글 초안과 canonical story state를 구분한다. 같은 branch의 충돌은 expected revision으로 감지하고, idempotency key는 중복 명령을 막는다. 이것은 외부 API의 exactly-once를 보증하지 않는다.

형제 후보는 같은 parent/request snapshot에서 만들어진 독립 원고다. 후보 A의 사건은 B의 현재 사실이 아니다. 미선택 후보도 재진입할 수 있다. ‘버린 분기의 기억 제외’는 전역 삭제가 아니라 현재 ancestry에서 배제한다는 뜻이다.

## 4. 비동기 파생 작업의 공통 계약

원문을 먼저 저장하고 표시한다. translation, presentation.enrich, status.extract, memory.extract는 원문 revision에 연결된 별도 job으로 실행한다. 자동 실행 여부와 모델 선택은 채팅별 설정이며, disabled이면 비용이 들지 않는다. 기본값 제안: 본문 번역 자동, 상태창을 장착한 채팅만 보조 상태 처리; 다중 후보의 비선택 번역/기억은 지연 실행.

작업 의존성은 sourceRevision, sourceHash, branch lineage, parentStateRevision, relevantCanonRevision, instruction/ruleRevision, modelPresetRevision과 같은 값으로 식별한다. 실제 사용하지 않은 전역 값까지 넣어 불필요하게 무효화하지 않는다. 파생 작업 시작 시 계보와 입력 범위를 고정한다.

완료 transaction은 대상 원문의 적격성과 해당 의존성, job ownership/attempt generation을 재검사한다. 한 논리 effect는 유일 키로 중복 반영을 막는다. 재시도는 진단 attempt가 추가되는 것이지 상태값을 한 번 더 가산하는 동작이 아니다.

**사용자가 다른 화면/분기로 이동했다는 이유만으로 정상적인 이전 작업 결과를 버리지 않는다.** 원래 대상 revision이 유효하면 그곳에 저장한다. 현재 화면/head를 기준으로 저장 대상을 다시 선택하지 않는다. 원문 수정/명시적 retcon/규칙 변경으로 의존성이 달라졌다면 stale로 남기고 현재 사실에 자동 합류하지 않는다.

원문 완료/번역 완료/상태 준비/기억 인덱스 준비는 다른 상태다. 번역 실패는 원문 실패가 아니며, annotation 실패가 정상 본문을 지우지 않는다. 영구 실패는 기존 결과 보존+부분 상태+개별 재시도 UI로 처리한다. 같은 원문을 다시 생성해 해결하지 않는다.

**저장과 후속 예약의 원자성:** 정상 원문 확정, 해당 Run의 완료 기록, 그 원문에 대해 켜져 있고 적격한 후속 job의 예약 레코드는 같은 서버 로컬 SQLite의 짧은 트랜잭션으로 커밋한다. 모델 호출·작업 실행·이벤트 전송은 커밋 밖에서 한다. 실제 후속 처리는 여전히 원문 확정 뒤에 실행하므로 원고 읽기를 번역·상태 완료까지 지연시키지 않는다.

원문만 저장한 뒤 메모리의 callback으로 job을 만드는 구간을 남기지 않는다. 커밋 직후 worker 깨우기나 알림 전에 프로세스가 종료돼도 재시작한 worker가 저장된 미실행 예약을 발견할 수 있어야 한다. 중복 예약은 논리 job의 유일성으로 막고, 파생 결과 저장과 해당 job 완료 기록도 함께 커밋한다. 거절·차단·부분 결과에는 기존 적격성 정책을 적용한다. 이는 로컬 기록의 계약이지 이미 시작된 원격 유료 요청의 exactly-once 보장이 아니다.

## 5. 보조 모델 기반 상태창 — 이번에 추가한 핵심 결정

### 5.1 기본 처리

메인 모델은 원고에 집중한다. **허용된 상태/행위 제약과 기존 사실은 계속 메인 입력에 포함한다.** 상태 출력 의무를 분리한다고 장면 작성에 필요한 소지품·위치·규칙까지 숨기는 것은 아니다.

완성 원문 + 이전 state + 관련 canon/규칙을 보조 모델에 제공한다. 보조 모델은 근거가 있는 사건·상태 변화 **제안**을 구조화해 반환한다. 출력 schema·직전 상태·각 필드의 의미와 유효한 값·숫자의 변화/계산 규칙은 역할 입력으로 제공하고 추가 설명은 도구로 읽을 수 있게 한다. schema 검사만으로 의미가 참이라고 단정하지 않는다. 권한·범위·근거 식별·허용 field/enum·숫자 범위를 검사하고 결정적 reducer가 최종 상태를 계산한다. 그 결과를 별도 상태창 component로 표시한다. 보조 모델은 원고 문자열에 HTML을 직접 이어 붙이거나 UI에서 DB를 쓰지 않는다.

명확한 숫자·기계 규칙은 프로그램이 계산한다. 예: 기존 코인10, 명시된 지출3이면7. 지출이 원문에 없으면 모델에게 그럴듯한 숫자를 만들라고 하지 않는다. module이 정의한 사건→점수 규칙은 버전 관리하고 모델의 임의 수치와 구분한다.

### 5.2 세 종류를 구분

1. **표시용 annotation**: 장면 요약·분위기·해석. 읽기를 막지 않고, 다음 이야기의 정사나 상태로 자동 승격하지 않는다.
2. **서사 연속성 state**: 원문에 근거한 위치·관계·소지품 상태. source와 시점이 있고, 불확실하면 unknown/해석으로 남긴다.
3. **게임 규칙 authoritative state**: 다음 행동 가능 여부를 결정하는 수치·자원·조건. reducer와 검증된 상태 commit이 필요하다. 다음 턴이 의존하면 준비 완료까지 generation만 대기한다. 사용자는 원고 읽기·다른 채팅을 계속할 수 있다.

보조 모델은 출처에 없는 내면·동기·새 사건을 사실로 만들지 않는다. ‘Inner Voice’ 같은 창작 해설을 허용할 경우 별도 annotation이며 저작권 배분·시점 계약을 따른다. 이 annotation을 다시 서사 증거로 먹이지 않는다.

### 5.3 다음 턴과의 경쟁

권위 있는 상태가 필요한 후속 요청은 waiting_for_state로 등록하며 완료 후 dependency snapshot을 확정한다. 사용자가 화면을 켜두고 기다릴 필요는 없다. 실패하면 재시도/명시적 수동 state/모듈 비활성 등 선택을 표시하고, 이전 상태로 몰래 진행하지 않는다. 모듈 변경도 기록되는 변경이다.

장면 설명처럼 선택적인 annotation은 이 barrier를 만들지 않는다. memory index가 늦으면 원문 tail로 보완할 수 있으나, 이미 잘못된 숫자로 진행하면 안 되는 authoritative state와 동일하게 취급하지 않는다.

### 5.4 후처리가 해결할 수 없는 것

원문 자체가 명시된 기계 규칙을 위반했다면 후처리 상태 숫자를 바꿔서 ‘정상’으로 수리하지 않는다. 원고/상태 불일치를 표시한다. 엄격한 게임 동작에서는 사전 규칙 검사 또는 생성 중 도구 사용이 필요할 수 있다. 모든 RP를 게임으로 만들지 말고 해당 모듈만 강한 규칙을 적용한다.

보조 상태 결과를 나중에 다시 계산할 때 기존 후속 분기의 기준이 자동으로 바뀌면 안 된다. 재계산 결과는 새 proposal/revision이며 명시적 적용에 필요한 후손 재검증/분기 정책을 사용한다.

### 5.5 비용과 지연

보조 모델은 추가 입력/출력/시간이 든다. 싸고 빠른 상태 추출기를 쓰는 것이 항상 더 싸거나 정확하다고 미리 결론 내리지 않는다. raw narrative 장문을 status/memory/translation에 각각 보낼 때의 전체 비용을 기록한다. 호환되는 상태·기억 추출은 공통 사건 추출 결과 재사용을 나중에 평가할 수 있지만 초기에는 다수 critic/rewriter 호출을 강제하지 않는다.

번역은 원문+시점 맥락으로 시작할 수 있으면 status와 병렬로 진행한다. 방금 바뀐 말높임 등의 확정 정보가 필수인 특정 작업만 해당 상태에 의존하게 한다. 모든 번역을 느린 보조 상태 뒤에 무조건 직렬화하지 않는다.

## 6. 모델 주도 자료 탐색과 역할별 작업 공간

### 6.1 기본값: 작은 출발 맥락 + 자율적 추가 조회

메인 모델은 창작에 필요한 로어·과거 사건·창작 스킬을 직접 발견/조회할 수 있다. 별도 selector가 고른 top-k만 볼 수 있는 폐쇄형 RAG로 만들지 않는다. 같은 허용 scope 안에서 목록 탐색, 검색 확장, 연관 문서 추적, 부분/전체 읽기가 가능해야 한다. prefetch는 선택적인 힌트·지연 최적화일 뿐 whitelist나 사실 채택 결정자가 아니다. 인물 관련성을 단순 문자열 매칭으로 확정하지 않는다.

매 턴 별도 planner/selector/critic 호출을 강제하지 않는다. 모델이 정보가 충분하다고 판단하면 바로 본문을 쓰고, 필요할 때 반복 조회·검토한다. 호출/시간/context/금액에는 사용자가 선택한 예산과 provider 한도를 적용하되 '로어는 최대3개', '항상 한 번만 검색' 같은 고정 의미 제약을 core에 박지 않는다. 초과/누락은 명시적으로 진단하고 무한 자동 확장은 하지 않는다.

### 6.2 로딩 방식과 의미적 권위를 분리

역할별 입력은 다음 세 층으로 구성한다. 메인만 이 구조를 갖는 것이 아니다.

- **상시 계약·현재 작업:** 역할, 선택된 창작/번역/후처리 계약, 현재 요청, 최소 인물·장면·불변 제약, 출력 스키마와 승인된 도구의 기본 사용 계약. 불변 규칙은 짧은 핵심과 상세 참조를 나눌 수 있다. '상시'는 현재 역할/채팅/작업에서의 의미이지 전 라이브러리 주입이 아니다.
- **발견 가능한 목록:** 이름·내용 설명·범주·위치/안정 ID·버전·관련 항목. 크면 검색 가능한 목차로 줄이며 생략된 항목도 같은 허용 scope에서 찾아갈 길을 남긴다. 설명 하나를 모든 항목의 긴 본문으로 대체하지 않는다.
- **요청한 본문/구간:** 모델이 선택해 읽은 lore, skill, memory, template, asset metadata. 제목만 열어봤다고 본문까지 읽었다고 취급하지 않는다. 반환이 잘리면 continuation 정보와 잘림을 표시한다.

로어는 세계·인물의 근거, skill은 작업 방법, tool은 자료 접근/계산/산출물 제안의 실행 인터페이스다. 같은 패키지/검색 API로 배포·발견할 수 있어도 권위는 같지 않다. **필요할 때 읽는다고 따를지 임의 선택 가능한 설정이 되는 것은 아니다.** 로딩 선택은 이미 확정된 사실을 어길 권한이 아니며 상시 로딩 또한 자료를 system 명령으로 승격하지 않는다. 범위·버전·source kind는 본문 밖의 메타데이터로 보존한다.

제외된 모듈/다른 채팅/다른 branch의 비공개 자료는 검색 목록·본문·건수에서도 읽기 scope를 넘지 않는다. 모델이 읽은 스킬은 새로운 권한을 만들지 않는다. 앱이 이미 허용한 로컬 읽기를 매번 사용자에게 재승인받지는 않는다.

### 6.3 소수의 직관적인 도구와 실제 context 전달

예시 인터페이스는 `knowledge.search/read`, `skills.list/load`, `assets.search/inspect`다. 이름이나 클래스 수를 강제하지 않는다. 리소스 ID와 read 결과는 실제 source revision·range·reference를 가진다. 캐릭터마다 전용 도구 수백 개를 만드는 대신 소수의 공통 도구와 자료를 사용한다.

모델의 tool call을 실행하고 결과를 다음 추론 입력에 넣는 것은 **하네스가 구현할 책임**이다. SKILL.md 파일이 존재하거나 DB에 읽음 표시가 있다는 이유만으로 API 모델이 내용을 아는 것은 아니다. 추가 조회는 지원되는 모델 요청/도구 경계에서 처리하며 진행중인 HTTP 요청의 토큰을 몰래 수정할 수 있다고 가정하지 않는다. protocol call/result 짝과 opaque provider 상태를 유지한다.

장면 working set은 provenance를 가진 본문/요약의 집합이다. 모델은 허용 범위에서 참조 유지·추가 조회를 선택할 수 있으며, 컨텍스트 정리 뒤에도 필요한 내용이 실제 입력에 있는지 관찰한다. 원문은 보존하고 접두부 캐싱은 의미·역할을 손상하지 않는 범위에서 최적화한다. 자동 요약이 정사를 몰래 덮지 않는다.

### 6.4 역할별 작업 환경

메인은 고정 창작 계약/현재 장면과 lore·memory·craft 자료 읽기를 가진다. 기본 메인 입력에는 이미지 전체 목록, 파일명 규칙, 상태 HTML·CSS, 수치 출력 양식, 번역 프로토콜을 넣지 않는다. 단, 장면을 제약하는 사실·외모·행동 규칙은 메인도 알 수 있어야 한다.

이미지 역할은 해당 원문과 표현 지침, asset 목록/검색/preview 도구를 받는다. 상태 역할은 원문·직전 상태·상태 정의/계산 규칙·출력 schema와 scoped 지식 조회를 받는다. 번역 역할은 원문·번역 계약·명칭집과 시점별 조회를 받는다. 이미지 선택이나 상태 표현의 적절한 방법은 보조 모델이 결정하고 실제 저장/표시는 host가 계약에 맞게 수행한다.

역할은 모델 ID·프로세스 수·항상 켜지는 에이전트 수를 의미하지 않는다. 동일한 runner의 별도 context/task profile로 구현하고 disabled 작업은 호출하지 않는다. 미래에 읽기 조사 subtask를 위임할 수는 있지만 lead가 근거 원문에 접근할 수 있어야 하며, 초기 제품에 항상 별도 연구 에이전트나 재귀적 팀 생성을 요구하지 않는다.

### 6.5 기억과 창작 여지

원문은 보존한다. author-canon은 작가 선언 자체가 출처이며 transcript를 발명하지 않는다. observed-story, derived-summary, character belief/hypothesis를 구분한다. 기억은 scope/시점/ancestry와 index watermark를 갖고 필요하면 원문으로 돌아간다. watermark는 해당 분기에서 연속으로 처리된 마지막 원문 revision을 가리킨다. 그 이후의 아직 처리되지 않은 원문 구간을 recent tail로 보완하고, 더 오래된 원문은 필요할 때 검색·읽기로 회수한다. 미래 분기/다른 후보는 현재 사실이 아니다.

근거를 요구하는 것은 기존 사실/추출의 정확성을 지키기 위한 것이며, 작가가 위임한 새 인물·국소 배경·장면 전개까지 '검색 결과 없음'으로 금지하는 것이 아니다. 메인이 권한 안에서 창작한 본문은 해당 branch의 새로운 이야기 근거가 될 수 있다. 후처리는 원문의 새 사실을 반영하되 없는 과거·정체·내면을 몰래 만들어 정사로 올리지 않는다.

compaction은 모델 입력 최적화이지 DB 삭제가 아니다. 공급자 opaque state는 보조적인 전송 자료이며 portable story memory의 유일한 저장소가 아니다.

## 7. 번역

Hermēneía 핵심은 ‘한국어 표현은 재구성하되 사실·주체·시점·불확실성·장르 기능을 바꾸지 않는다’이다. 자동 context packet은 인물, 관계·호칭, 이름/용어, 현재 장면, 관련 앞뒤 원문을 준비한다. 전체 lore를 모두 복사하지 않으며 생성 모델을 매번 다시 호출해 번역 지침을 만들지도 않는다.

번역 기준 시점은 대상 원문이다. 미래 관계나 정체로 과거 대사를 수정하지 않는다. 원문이 유지한 오해와 모호함도 보존한다. translation context는 원문 사실 수정 권한이 아니다. 키·enum·숫자·asset ID·code span은 보호하고 인간용 문장만 번역한다.

원문+의존 맥락+용어집+번역 지시/모델 revision에 연결된 파생 결과를 보존한다. source와 번역을 다음 서사 입력에 중복 삽입하거나 번역 문장을 새 사건으로 추출하지 않는다. 분할 번역은 문맥 묶음으로 하고 block coverage/순서/중복과 보호 span을 검사한다. coverage 통과가 의미 완전성 보증은 아니다. 번역 내부의 재문단화가 가능하므로 원문/번역 앵커가 언제나1:1이라는 가정도 피한다.

원문 수정으로 old translation이 생겨도 지우지 말고 이전 revision 결과로 표시한다. 읽기용 번역을 직접 편집하는 것은 원작 canon 수정이 아니다. 원작 수정은 별도 명령이다.

## 8. provider·전송·비용

Connection, protocol adapter, model catalog/capabilities, task-specific preset을 분리한다. endpoint가 다르면 같은 model ID도 같은 연결이 아니다. remote catalog는 데이터만 갱신하고 키/권한/preset을 덮지 않는다. unknown capability/price는 unknown으로 유지한다. 모델 문자열 정규식으로 모든 기능을 확정하지 않는다.

기본 Adapter 계약은 text/tool call/tool result/usage/error/refusal/opaque provider state를 구분한다. 공통 문자열 chat으로 평탄화하지 않는다. 독특한 기능은 typed provider extension으로 제한해 전달하며 compatibility 표를 유지한다. 공식 SDK나 기존 client는 사용하되 도메인을 SDK 내부 타입에 종속시키지 않는다. 실제 모델 이름·API key/명령·parameter는 구현 시 공식 자료/선택 연결에서 확인한다.

첫 실사용 연결은 사용자가 선택한 본문 경로와 번역 경로만 우선한다. endpoints는 current config에서 읽고, 미확인이면 mock/fixture 구현은 계속하되 live 지원 주장은 남긴다. 모든 provider를 한 번에 지원하지 않는다.

캐시는 안정 구간·동적 제어·tool schema 변경의 영향을 관찰한다. Phēmē source의 특정 relay TTL/explicit breakpoint를 모든 공식 API 계약으로 복사하지 않는다. cache key와 실제 cache hit/청구량은 다르다. 각 요청/attempt의 raw usage와 price revision을 보존하고 추론 토큰 포함 관계/캐시 쓰기/읽기를 중복 없이 계산한다.

budget은 전체 사용자 작업, 후보 그룹, 각 child 작업에 예약/집계한다. 보조 상태도 포함한다. 확인되지 않은 사용량/가격은0이 아니다. 알려진 근거로 상한이 산정되지 않으면 경고/확인 정책을 적용하고 임의 무료 표기를 하지 않는다. 이미 발생한 원격 비용의 환급이나 앱 취소로 정확한 하드 차단을 보증하지 않는다.

부분 출력 후 실패/서버 재시작/외부 도구 성공 여부 불명확은 자동 replay하지 않는다. 한도 내 명시된 안전한 기술적 retry만 사용한다. policy refusal을 순환 provider 재시도나 우회 프롬프트로 바꾸지 않는다.

## 9. 에셋·확장·입력 변환

### 9.1 이미지 선택은 보조 표현 작업

파일 에셋은 hash/manifest/ref로 분기와 공유하고 목록/thumbnail/실물 로딩을 분리한다. asset metadata에는 가능한 범위의 actor/복장/표정/포즈/장소/캡션/대체 설명/허용 쓰임을 둔다. 불분명한 파일명만으로 시각 의미를 확정하지 않는다. 작성자 설명을 우선하고, 필요하면 허용된 이미지 이해 모델의 사전 메타데이터 작성 또는 선택된 소수 preview 확인을 사용한다. 이미지 capability가 없는 모델에 bytes를 전달하고 봤다고 가정하지 않는다.

보조 모델은 완성 원문과 compact catalog/search/inspect 경로를 보고 이미지 선택·생략·배치를 결정한다. 이미지가 없거나 맞지 않으면 이미지 없음도 정상 결과다. 모든 이미지 bytes/base64 또는 수천 항목의 긴 목록을 매번 메인/보조 입력에 넣지 않는다. 의복/인물 관련성 같은 필터와 실제 존재하는 조합은 시스템이 검사한다. 분위기 적합성은 의미 평가 대상이다.

결과는 예를 들어 `sourceRevision, blockAnchor, assetRef, presentationIntent`를 갖는 작은 **표현 annotation**이다. 원문 전체를 재작성해서 img tag를 삽입하는 것이 기본이 아니다. host가 원고/번역의 블록과 annotation을 조합하여 표시한다. anchor/asset 존재, 권한·버전·중복·최대 표시 정책을 검사한다. 번역 재문단화는 원문↔번역 anchor mapping으로 처리하고 문장 1:1을 강제하지 않는다.

한 긴 원고 안에서 의상/장소/인물이 변하면 해당 블록의 scene context에 맞춘다. 마지막 상태 하나를 모든 이미지에 적용하지 않는다. 이미지에만 보이는 표정·복장이 원문 사건이나 다음 canon을 역으로 바꾸지 않는다. 이미지 생략/오류/재시도는 본문·번역·state를 바꾸지 않는다. rendered HTML을 다음 본문 모델 입력으로 재순환시키지 않는다.

초기에는 원문 완료 뒤 enrichment를 실행한다. 나중에 완결된 블록 단위 처리를 도입할 수 있으나 모든 토큰마다 보조 모델을 재호출하지 않는다. 이미지/상태 역할을 같은 호출로 묶을지는 공통 context·비용·실패 격리를 측정한 뒤 결정한다. 필요한 역할만 실행하고 UI는 가용 산출물부터 표시한다.

### 9.2 상태·후처리와 원고 보존

상태창은 native component가 structured artifact를 렌더한다. HTML 정화·표시 scope와 기계 상태 reducer를 분리한다. 정규식은 제한된 변환 기능이며 권한 있는 상태 변경의 암묵적 통로가 아니다. 위험한 정규식은 끊을 수 있는 격리 실행·입력/시간 제한이 필요하다. Worker만으로 보안 sandbox를 주장하지 않는다.

장면 버튼은 chat/branch에 예약된 command다. 성공 원문 반영 시 소비하며 실패/거절/중복/취소를 명시한다. 원본 first message·lore·asset은 선택적 일회성 변환으로 옮길 수 있다. Lua/CBS의 실행 호환과 구분하고 미지원 변환은 보고한다.

## 10. 실제 사용 전 보안·복구

M0은 loopback/local 합성 데이터로 제한한다. 외부에서 폰으로 쓰기 전 단일 사용자라도 인증된 세션, HTTPS/안전한 사설 접속, chat/asset/event 권한 검사, CSRF/Origin·업로드 경계, 비밀키 서버 보관을 갖춘다. ‘private service’라는 이름만으로 보안 검증을 생략하지 않는다.

임의 URL의 remote catalog/tool/asset이 auth header를 다른 host에 전달하거나 내부 주소로 접근하지 않게 연결 권한/redirect/egress를 검증한다. 사용자 지정 로컬 endpoint가 필요한 경우 해당 목적지에만 명시적 허용을 둔다. 라이브러리 업데이트로 전역 허용을 늘리지 않는다.

개인 데이터 저장 위치와 dev/test 위치는 다르다. 업데이트 전 일관된 DB+asset 백업, 새 디렉터리 복원, 버전 불일치 실패, export/import을 실제 시험한다. SQLite WAL 사용 중 DB 파일 하나를 임의 복사한 것을 완전 백업이라고 하지 않는다. 바이너리 downgrade와 데이터 복원은 다르고 복원의 시점 손실을 알린다. 공개 다중 사용자 서비스는 후속 별도 검토다.
