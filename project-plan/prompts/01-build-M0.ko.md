# Codex 첫 작업 — M0 구현과 검증

> 최초 M0 구축용 지시문이에요. 현재 저장소는 M0 이후 기능이 구현돼 있으므로 그대로 재실행하지 않고 [CURRENT](../CURRENT.md)와 사용자가 요청한 범위를 확인해요. 기존 작업의 후속 지시는 [03-continue](03-continue.ko.md)를 사용해요.

`project-plan/README.md`를 시작점으로 PROJECT, ARCHITECTURE, VERIFICATION, MILESTONES의 M0와 ACCEPTANCE의 F01–F06을 읽어줘. 이 대화의 과거 기록이나 첨부 원문이 네 환경에 자동으로 있다고 가정하지 마. 계획을 다시 작성하는 데서 끝내지 말고, **작은 실제 앱과 검증 루프를 구현·실행·수정해서 M0를 끝내줘.**

목표 제품은 모바일 장문 RP·소설 생성, 한국어 번역, 보조 상태창, 분기·기억을 지원하는 독립 하네스야. 이번 범위는 M0이며, 실제 유료 모델/공개 배포/장기기억 전체/원본 봇 실행 호환까지 구현하라는 뜻은 아니야.

## 시작과 자율성

먼저 git 상태와 기존 사용자 변경, 적용되는 AGENTS/override/skills, Node·패키지 매니저·SQLite·브라우저·shell·localhost·네트워크 권한을 실제로 확인해. 개발 대상은 Windows11 로컬 Codex이며 WSL/Docker/bash를 전제하지 마.

빈 폴더면 TypeScript·React/Vite·Node/Fastify·파일 SQLite 기반으로 초기화해. 기존 앱이 있으면 현재 구조를 먼저 확인하고 불필요한 재작성은 피하며 차이를 기록해. 로컬 Git 초기화와 이번 작업 파일에 한정한 로컬 커밋은 허용하지만 사용자 신원/전역 Git 설정을 발명하거나 원격 push·공개하지 마.

허용된 범위의 일반 구현·의존성 준비·테스트·격리 정리는 스스로 진행해. 합리적이고 되돌릴 수 있는 선택은 기록하고 진행하며 반복 승인받지 마. 새 권한, 실제 사용자 데이터 변경, 추가 유료 호출, 외부 공개는 기존 승인 경계를 지켜. 특정 검사가 막혔다고 나머지 가능한 작업을 모두 중단하지 마.

## 이번에 연결할 제품 경로

1. 얇은 반응형 UI → 실제 HTTP/이벤트 → 실제 SQLite → 서버 소유 Run → 원문 저장.
2. 서로 다른 채팅/설정/원문 revision의 격리. 중복 요청과 오래된 revision의 충돌 감지. 탭을 닫아도 서버 작업은 계속되고 재접속은 같은 run을 읽을 것.
3. 고정 계약·발견 가능한 목록·실제 read 결과를 분리한 최소 역할 context를 연결해. 도구 없이 끝나는 scripted mock과 실제 로컬 자료를 search/read하는 scripted mock으로 확인하고 skill 로딩이 권한을 늘리지 않게 해. 메인 모델이 prefetch 바깥의 적법한 자료에도 접근할 수 있는 경로를 남기고 모든 요청에 별도 selector/planner를 강제하지 마.
4. 원문 뒤 **모의 번역과 모의 표시용 상태**를 별도 job/result로 붙여줘. 원문 확정·Run 완료·적격한 후속 job 예약을 같은 짧은 DB 트랜잭션에 기록하고 실제 작업은 커밋 뒤 실행해. 커밋 직후 프로세스가 종료돼도 재시작 시 미실행 예약을 발견하고 원문을 다시 생성하지 않는지 확인해. 메인 본문에 상태 HTML/JSON을 억지로 섞지 마. 지연·실패·중복·다른 화면 이동에도 원래 source에 결과를 붙이고 본문을 잃지 않을 것. 이것을 실모델 번역/상태 추출 검증이라고 표현하지 마.

메인의 tool 사용은 창작을 위한 조사야. 메인에 이미지 catalog·상태창 HTML·번역 절차를 모두 넣어둔 채 출력만 분리하는 방식은 피하자. M0의 보조 결과는 명시된 모의 번역/표시 상태만 연결하고, 실제 이미지 선택은 M1에서 구현해.

공통 계약은 작게 두고, 미래 기능의 빈 framework나 모든 acceptance test stub은 만들지 마. 실제 데이터 경계를 유지하면서 구현을 단순화할 자유가 있어. 사용자 불변 조건과 검증 기준을 편의상 낮추지는 마.

## 완료 검증

F01–F06의 관찰값을 실제 테스트에 연결해. 준비→앱 ready→관련 검사/브라우저 상호작용→실패 진단→정리를 재현 가능하게 만들어줘. Vitest/Playwright 등의 기존 reporter를 우선 쓰고 별도 거대 검증 프레임워크는 피하자.

필수 검사 실패·0개 선택·skip/report 누락·오래된 다른 서버·timeout을 격리된 시험으로 넣고, 검증 명령이 성공으로 숨기지 않는지도 확인해. 실제 파일 DB와 두 브라우저 context/동일 context의 두 탭을 사용하고, 전체 제품 경로를 mock으로 대체하지 마.

변경에 맞는 검사를 통과한 뒤에는 새 변경·실패·미해결 우려가 있을 때만 범위를 넓히거나 반복해. 의미 없는 테스트와 검토 반복으로 완료를 미루지 마. 가능하면 별도 검토 pass로 저장/경합/false oracle/비밀노출/기준 약화를 확인하고, 최종 통합 코드에서 필요한 검사를 다시 실행해.

기본 데이터는 합성이며 실제 소설·키는 쓰지 마. 원본 참고 자료가 없어도 M0는 진행할 수 있어.

## 최종 전달

실제로 쓴 실행·검증·정리 명령, 앱을 열고 확인하는 방법, code/build 기준, F01–F06 결과와 증거, 실패·차단·미실행 범위를 알려줘. CURRENT.md와 짧은 AGENTS에는 확인한 사실과 명령만 남겨줘. 중단될 경우에는 재현 가능한 상태와 가장 작은 다음 작업을 기록해.

M0가 검증되면 그 결과를 전달하고 마무리해. M1이나 유료 호출을 자동 시작하지 마. 완료 기준은 파일/문서가 생긴 것이 아니라 **다음 변경도 실제 앱에서 재현·검증·진단할 수 있는 상태**야.
