## 확인한 실행 흐름

아래 `Lua 28:72` 표기는 전용 Lua 표면의 **0부터 시작하는 섹션 index 28, 섹션 본문의 LF 기준 72번째 줄**이에요. 섹션은 편집 구분일 뿐 독립 Lua 파일이 아니에요. 예를 들어 `main()`은 28번에서 시작해 29번에서 끝나요.

1. **사용자 입력·수동 버튼.** `onButtonClick`에서 선택지를 받으며, `PerformDiceRoll~…` 분기는 d20과 조건별 추가 추첨·보너스·난이도·치명 판정을 계산해 사용자 메시지로 추가해요. 토큰 버튼은 과거 주사위 결과 메시지를 찾아 수치를 바꾸거나 다시 굴려 `setChat`으로 덮어써요. 스킬 투자·특성 취득·시작 상태·시스템 ON/OFF도 수동 함수예요. 근거: Lua 5:74, 6:18–63, 7:14–80, 12:1–460, 19:2·135, 21, 33–39.
2. **메인 응답의 저장 전/후 처리.** `listenEdit("editOutput")`가 완료 태그를 읽어 퀘스트 변수를 변경해요. `onOutput`은 이미지 이름과 중복 상태 표시를 정리한 뒤 `main()`을 호출해요. 근거: Lua 32:45–95. 실제 호출 시점은 위 Risu 안내의 저장 전 edit-output, 저장 및 `runVar` 이후 onOutput 구분을 따라 해석했어요.
3. **초기화·복원.** 매 `main()` 시작 때 최근 저장 seed를 이력에서 찾아 상태를 복원하고 임시 변경을 덧씌워요. 전역 `toggle_choice`를 읽고 채팅 변수·구조화 상태를 동기화해요. 근거: Lua 24:210–248, 26:2–207. 외부 프리셋 값은 이번 파일만으로 확정할 수 없어요.
4. **후처리 보조 호출.** 기본 통합 모드에서는 상태·태그/호감도를 한 번에 요청하고, 분리 모드에서는 조건에 따라 두 번 요청해요. 스킬 판정이 있으면 선택지 생성, 이미지 보조가 켜져 있으면 별도의 이미지 배치 요청이 추가돼요. 근거: Lua 28:47–106, 144–155, 224–235. 이미지 요청은 새 이미지를 만드는 호출이 아니라 **기존 이미지 명령을 문단 뒤에 배치하는 계획**이에요.
5. **상태 계산.** 보조 출력의 감정·휴식·훈련·퀘스트·인벤토리 태그와 메인 출력의 퀘스트 완료/실패를 파싱해 자원·보상·경험치·레벨을 순차 갱신해요. 이전 사용자 메시지의 판정 결과도 읽어요. 근거: Lua 4:48–182, 17:119–192, 18, 20, 28:120–222.
6. **주기적 NPC 상태.** 옵션을 켠 상태에서 8회마다 NPC 상태, 15회마다 장기 NPC 요약을 보조 모델로 요청하고 저장해요. 두 카운터는 독립적이며 재호출·복원에도 영향을 받아 단순한 달력 주기가 아니에요. 근거: Lua 29:1–57. 상태 snapshot은 채팅 변수로, 장기 요약은 구조화 상태로 보존돼요.
7. **메시지 완성·표시.** 본문·알림·보조 결과·선택지·seed를 결합해 마지막 메시지를 다시 저장하고, `editDisplay`와 정규식/CBS가 버튼·패널·이미지 표시를 만들어요. 상태/퀘스트/선택지/이미지 재생성 버튼도 이전 메시지를 수정해요. 근거: Lua 29:59–67, 30–32, 5, 22:651–735, 36, 37:1–110.

`callLLMWithRetry`는 `LLM`/`axLLM`을 선택하고 **한 호출 지점당 최대 5회 시도**해요. 주석의 “5번 재시도”와 달리 루프는 `1..5`이므로 최초 호출을 포함한 5회예요. 응답의 `success`로 성공을 판정하며 모든 결과 형식 검증 실패를 재시도하는 구조는 아니에요. 여러 호출 지점을 합친 호출 상한·durable attempt·불확실 전송 처리의 동등성을 이 함수에서 확인할 수 없어요. 근거: Lua 22:20–70. Uimori의 작업별 호출 한도·attempt·취소 규칙으로 별도 설계해야 해요.

## 후속 확장 검토의 최소 단위

다음은 **제품 변경안의 검토 범위**이며 이번에 구현·승인된 새 API가 아니에요.

1. **패키지 사후 처리 선언.** 원문 완료 이벤트에 어떤 역할·지침·입력·출력 schema를 쓸지 명시하고, 호출 간 선행 조건과 N회 간격을 데이터로 표현할 수 있는지 검토해요. Run/source/hash·패키지 revision·당시 모델·전체 호출 예산·전송 전 attempt·취소·불확실 실행 방지는 호스트가 계속 소유해야 해요. 기존 status/image/state 실행기와 중복되는 부분을 먼저 분리해요.
2. **구조화 출력 이벤트와 결정적 상태 전이.** 모델은 검증된 사건/선택 데이터만 내고, 보상·레벨·자원 계산은 호스트가 선언된 식으로 처리하는 계약이 필요해요. JSON 또는 고정 구분자 입력으로 바꾸고, 파싱·계산·게시 실패를 하나의 원자적 결과로 처리할지 정해요. 임의 Lua 패턴 파서나 범용 스크립트 hook 추가를 전제하지 않아요.
3. **source에 귀속되는 선택·상태 표시.** 공통 카드/목록/게이지·행동 참조가 실제로 필요한지 검토해요. 모델이 만든 버튼 payload는 source/hash와 상태 revision에 결합된 ID로 검증해야 해요. 이미 생성한 본문을 수정하는 대신 미확정 선택·별도 annotation을 갱신하는 사용 흐름과 원본의 차이를 사용자에게 보여줘야 해요.
4. **확장 없이 가능한 부분 제작.** 기본 상태·옵션·대표 d20/토큰·퀘스트 보상·지침 조건부터 개인 산출물로 작성하고 합성 입력으로 검증할 수 있어요. 실제 카드 전체 제작은 위 손실을 수용할지 정한 뒤 진행해요. 에셋 목록 도구 오류는 RisuToki의 별도 수정/지원되는 추출 경로가 마련돼야 해요.

원본이 이미 가진 상태·표시·권한 차이를 없애기 위해 임의 코드 실행이나 과거 원문 쓰기를 허용하는 것은 이번 조사에서 채택하지 않았어요. 특히 **사후 보조 모델의 자유 텍스트를 정사 사실로 자동 저장하는 정책**은 창작 도구의 기존 정사·출처 계약과 함께 판단해야 해요.

### 사용자 제안 후속안 · 기존 출력 후 하네스 확장

사용자는 “출력 후 보조모델은 지금 이미지 삽입 같은 사후처리 하네스에 더 다양한 기능을 제공하도록 하면 해결될 것 같다”는 방향을 제안했어요. **아래는 그 제안을 현재 코드에 대입한 후속 설계안이며, 새 실행기·API·저장 정책의 구현 승인이나 구현 완료를 뜻하지 않아요.** Lua 22·28·29의 사후 분석·상태 계산·주기적 NPC 정리는 이 방향으로 다룰 수 있어요. 저장 메시지 덮어쓰기와 전투판·선택 버튼 등 전용 UI는 별도 계약으로 남아요.

**재사용할 기반.** 등록 이미지를 고르는 `image` 역할은 [product-auxiliary.ts](../server/product-auxiliary.ts)의 `runAuxiliaryJob`에서 원문 ID/hash를 확인하고 owner·generation으로 작업을 claim/완료해요. [auxiliary.ts](../core/auxiliary.ts)는 원문 block anchor와 구조화 결과를 검증하며, 표시 상태는 정사·다음 턴 사실로 승격하지 않아요. 상태 모델은 [story-runner.ts](../server/story-runner.ts)의 `runStoryJob`에서 source/config/module revision과 이전 상태를 검증하고, 모델이 제출한 evidence가 있는 연산을 호스트가 적용해요. [story-store.ts](../server/story-store.ts)는 부모 상태와 source 계보를 확인하고 authoritative 상태가 없으면 다음 본문을 대기시켜요. 새 이미지를 만드는 [삽화 큐](../docs/ILLUSTRATIONS.md)는 이미지 배치와 별개지만, 예약 snapshot·취소 generation·원문시점 결과 표시의 참고가 돼요. 이 세 경로를 무조건 같은 큐로 합칠 필요는 없어요.

**최소 선언 범위.** 패키지 안에 제한된 사후 단계 목록을 두고 `단계 ID·지침·허용 입력·출력 schema·실행 조건·선행 단계·반영 대상`을 명시하는 안이에요. 이름은 논의용이며 현재 native JSON 필드가 아니에요. 허용 입력은 완료한 source의 허가된 구간, 당시 옵션·패키지·상태, 검증된 선행 단계 결과로 좁혀요. 조건은 기존 식 평가기를 사용하고 순환 의존은 거부해요. 8/15회 주기는 성공한 본문 source의 분기별 누적 순번에 고정하는 안부터 검토해요. 재시도 attempt·후보·포크 복사·transcript 가져오기를 새 발생으로 세지 않고, 같은 source에서 두 주기가 겹치면 서로 다른 단계만 한 번씩 예약해요. 패키지명에 따른 분기나 일반 Lua·JavaScript·RPC hook은 필요하지 않아요.

**모델 제안과 호스트 반영을 나눠요.** 예를 들어 `사건 추출 → 보상 계산 → 표시 결과`에서 보조 모델은 사건 종류·대상·근거 span을 구조화 데이터로 제출해요. 호스트는 등록된 사건/schema·근거·중복 여부를 검사한 뒤, 고정한 이전 상태와 선언된 계산식으로 자원·보상·레벨을 결정해요. 기존 state reducer와 [패키지 행동 계산](../docs/PACKAGE-BEHAVIOR.md)의 제한된 식·journal을 재사용할 수 있지만, 보조 출력에서 이 계산으로 연결하는 호스트 경로는 새 설계가 필요해요. 모델에 기존 `model` 행동 권한을 그대로 주거나 자유 텍스트를 정사로 저장하지 않아요. 호출 중 DB 트랜잭션을 열어 두지 않고, 검증된 제안·선행 결과를 보관한 후 상태 변경과 operation 영수증을 짧은 트랜잭션으로 함께 게시해요.

**동시 실행과 실패의 경계.** 예약에는 source ID/hash·분기·정의 revision·모델/지침·입력/출력 schema·조건 판정·부모 결과 ID/hash·기준 상태 revision·전체 호출 한도를 고정해요. 선행 작업이 완료돼도 현재 상태가 기준 revision과 다르면 최신값에 조용히 재계산하지 않고 충돌/복구 대상으로 남겨요. 상태를 공유하는 단계는 부모 순서를 따르고, 같은 source·단계·정의의 재접수는 최초 영수증을 돌려줘요. 모델이 call ID를 바꿔도 같은 근거의 완료 사건에 보상을 다시 지급하지 않아야 해요. authoritative 묶음은 모든 단계가 검증되기 전 임시 결과로 유지하고 실패 시 다음 본문을 막는 안이에요. 표시 전용 단계의 실패는 완료 원문과 성공한 독립 표시 결과를 보존해요. 전송 전 attempt, 매 전송의 최신 연결 권한 검사, owner/generation, 취소와 재시작 후 불확실 전송 재생 금지는 기존 계약을 유지해요. 이후 설정 변경은 예약 snapshot을 바꾸지 않아요.

| 후속 설계 검증 사례 | 관찰할 결과 |
| --- | --- |

| 8회·15회·120회 경계, 후보·포크·가져오기, 예약 후 모델 변경 | 정의한 source 순번으로 각 단계 1회, 범위 밖 발생 제외, 당시 모델·지침 snapshot 유지 |
| 이미지 선택에 없는 ID·다른 문단 anchor, 원문/번역 수정 | 등록 catalog와 해당 source anchor만 수락, 잘못된 본문에 결과 재배치 금지 |

우선 하나의 합성 패키지로 **사건 추출 1단계와 결정적 상태 전이 1단계**, 독립 표시 결과를 검증하는 범위가 적절해요. 이 범위를 확정하기 전에 authoritative 결과를 자동 게시할 조건과 사용자 검토가 필요한 사건의 범위를 결정해야 해요. NPC 요약이 일반 문맥 요약인지 별도 상태인지, 원본 자유 태그를 어떤 구조화 사건으로 바꿀지도 자료별 대응/손실 보고에서 명시해요. 게이지·버튼 표시와 과거 본문 교체는 이 단계에 함께 넣지 않아요.

## 검증 결과와 다음 검증 사례

**실시한 검증은 정적 구조 조회, 선택한 원본 실행 경로와 현재 Uimori 코드의 대조, 재조회 시 원본 metadata/항목 hash 일치 확인이에요.** Lua 컴파일/실행, 전체 HTML 렌더링, 원본 모델 응답, native 데이터 검증, Uimori DB 등록·동작 테스트는 실행하지 않았어요. 따라서 원본 호환 PASS·창작 품질 PASS·native 이식 완료로 집계하지 않아요.
