> 2026-09-07 후속 구현: CBS 조사 뒤 읽기 문맥·계산/목록/날짜·상태 액션·출력 파서·기록된 난수·구조화 폼과 분기/보관을 추가했어요. 현재 API는 [PACKAGE-BEHAVIOR](../docs/PACKAGE-BEHAVIOR.md), 검증 결과는 [PACKAGE-BEHAVIOR-RESULTS](PACKAGE-BEHAVIOR-RESULTS.md)를 기준으로 봐요. 아래 문서는 전체 장기 설계이며 자동 hooks/임의 보조 jobs/전용 view DSL·원본 카드 전체 포팅까지 완료했다는 뜻은 아니에요.

기준일: 2026-09-07. Phēmē·Veil 분석에 이어 사용자가 지정한 Merry Sisters, Alternate Hunters, Cheongwon High School을 정적으로 조사해 만든 **후속 설계안**이에요. 이 문서는 구현 완료나 원본 봇의 실행 호환을 뜻하지 않아요. 이번 작업은 원본 구조 조회와 계획 작성이며 앱 코드·사용자 DB·원본 파일을 바꾸거나 모델을 호출하지 않았어요.

## 결론과 제작 방식

현재 공통 패키지에 **상태·액션·출력 파서·보조 작업·화면 구성**을 더하는 방향을 제안해요. 프롬프트 조건 문법만 확장하면 메리의 RPG 로직과 청원고의 시간표를 표현하려고 별도의 프로그래밍 언어를 만들게 돼요. 프롬프트 조립과 패키지 동작은 서로 다른 계약으로 유지해요.

- 프롬프트는 기존 role/순서/history/cache/조건 AST를 유지해요. TypeScript 제작 API와 선택형 문법은 같은 AST를 생성해요.
- 일반 패키지는 선언형 데이터와 폼만으로 만들 수 있게 해요. 상태 필드, 버튼, 파서, 간단한 계산, 작업 요청과 화면 구성을 공통 형식으로 기술해요.
- 복잡한 알고리즘의 제작 방식으로는 **TypeScript API를 우선 후보**로 두되, 제작 때 데이터로 변환하는 부분과 실행 때 계산이 필요한 함수를 구분해요. 아직 임의 JavaScript 런타임 도입을 확정하지 않아요.
- 메리의 자원 소비/조건부 효과, 청원고의 시간표 배정, 여러 인물의 상태 갱신을 작은 비교 구현으로 만든 뒤 AST만으로 처리할지 제한된 순수 함수 실행을 추가할지 결정해요. 전체 Lua를 양쪽으로 재작성하는 비교는 하지 않아요.

TypeScript를 제작 도구로 쓴다는 결정만으로 실행 중의 `if`, 반복, 비동기 호출까지 지원되는 것은 아니에요. 제한 함수 후보도 DB·네트워크·시각·난수를 직접 읽지 않고 호스트가 제공한 입력으로 제안만 반환해야 해요. 실제 격리 엔진과 제한은 비교 단계에서 검증해요.

### 상태와 변경의 출처

상태의 주인은 라이브러리 파일이 아니라 **채팅 분기의 패키지 장착 인스턴스**예요. 안정적인 instance ID에 package/behavior/schema revision을 연결해요. 현재 옵션 키 `id@revision:role`을 진행 상태의 영속 ID로 그대로 사용하면 개정 때 상태가 끊기므로 별도 migration이 필요해요. 같은 패키지를 bot/persona/module로 붙여도 상태가 암묵적으로 공유되지는 않아요.

변경은 다음 출처를 구분하고 허용 필드·기준 state revision·입력 hash를 검증해요.

1. 사용자 action: 초기 설정, 일정 추가, 능력치 투자, 리롤 등.
2. 원문 파싱: Veil STATUS/LEDGER처럼 지정된 형식에서 얻은 값.
3. 보조 작업 결과: 고정 source와 문맥에서 추출한 상태/이벤트.
4. 호스트가 기록한 추첨 및 결정적 규칙: 주사위·보상·배율·시간표.

모델의 서술에서 수치 변화를 해석하는 일과 명시적인 상태 프로토콜 값을 읽는 일은 다른 권한이에요. 절대값 파서도 source hash/부모 state revision/필드 범위를 갖고, 이후 사용자 행동을 늦은 결과로 덮어쓰지 못해요. 충돌 결과는 stale로 남기고 활성 상태에 적용하지 않는 것을 기본으로 해요. 자동 병합이나 유료 재계산은 별도 명시된 정책이 있을 때만 해요.

파서의 필수 필드는 지정한 그룹 단위로 모두 검증한 뒤 원자적으로 적용해요. 깨진 STATUS 일부만 반영하거나 오류를 빈 성공으로 처리하지 않아요. 원문은 계속 읽을 수 있고, 다음 생성에 반드시 필요한 상태만 다음 턴을 대기시켜요. 사용자는 원문/파싱 결과를 검토하고 명시적으로 복구할 수 있어야 해요.

### 턴·난수·취소·재생성

호스트가 부모 상태를 확정하고 턴 입력을 예약한 뒤 필요한 추첨을 기록해요. 프롬프트 미리보기와 화면 재표시는 추첨·자원 소비·턴 카운터를 진행시키지 않아요. 같은 예약의 재접속/안전한 전송 재시도는 같은 추첨을 사용하고, 명시적 리롤은 별도 action으로 기록해요.

action 중복 키에는 분기/instance/action ID뿐 아니라 payload hash와 behavior revision을 포함해요. CAS, 자원 소비, 결과, 후속 작업 예약을 한 트랜잭션에 저장해 **로컬 반영 1회**를 보장해요. 외부 모델 실행은 응답 유실 시 불확실할 수 있으므로 똑같은 의미의 실행 1회를 보증하지 않아요. 기존 전송 전 attempt journal과 불확실 실행 자동 재생 금지를 유지해요.

주기 작업의 턴은 분기에서 확정한 메인 응답의 논리적 위치로 정의해요. 버튼 클릭·보조 호출·화면 표시·취소는 턴 수에 더하지 않아요. 같은 위치의 응답 재생성은 동일 부모 상태에서 새 결과를 계산하며 새 버전의 파생물만 채택해요. 과거 상태에 delta를 역으로 빼는 방식은 사용하지 않아요. 재생성 시 추첨 유지가 기본이고 새 추첨은 사용자가 구분해서 실행해요.

포크는 분기점까지의 상태·추첨·진행 중 작업의 유효성 정보를 함께 보존하고, 이후 action/추첨은 새 분기 범위에서 독립적으로 기록해요. 8턴/15턴 작업은 해당 턴의 채택된 source 버전에 한 번만 예약해요. 패키지 개정은 명시적 상태 migration을 거치며 과거 Run 정의를 바꾸지 않아요.

### 메인과 보조 역할, 원문 보존

상태 추출·이미지 선택·번역·요약은 각각 필요한 원문/상태/자료만 받는 호스트 작업으로 실행해요. 패키지는 요청 계획을 선언하고 실제 모델·권한·호출 수·취소·비용 처리는 기존 호스트가 소유해요. 작업 의존성은 순환과 무한 연쇄를 거부하고 턴 전체 상한을 가져요. 메리의 최대 5회 호출 루프를 그대로 이식하지 않아요.

선택지나 배경 NPC의 새 행동처럼 **새로운 내용을 창작하는 작업**은 단순 상태 추출로 위장하지 않아요. 명시적인 창작 역할과 canon 반영 규칙을 갖고, 독자에게 보이는지·세계에서 확정됐는지·인물이 아는지를 구분해요. 메인의 창작 자율성과 필요한 로어/기억 조회 권한은 유지해요.

원본의 `setChat` 재작성은 저장된 응답에 붙는 상태/선택지/이미지/알림 파생물로 옮겨요. 일반적인 표시 정규식은 원문 의미나 기억의 입력을 바꾸지 않아요. 요청에서 기계 블록을 감출 때는 검증한 source span을 이용하고, 어떤 projection으로 어떤 role 입력을 만들었는지 snapshot에 남겨요. 변환 순서는 명시적이며 여러 패키지의 상태나 숨김 구간을 서로 침범하지 못하게 해요.

## 구현 순서와 완료 기준

| 단계 | 결과물 | 종료 기준 |
| --- | --- | --- |
| B0 · 계약/비교 | 작은 데이터명세와 TS 함수 후보, 메리 판정·청원고 시간표의 중립 합성 예제 | 같은 입력/추첨의 결과·오류·재실행 비교. 작성 복잡도/추적성/실행 제한을 근거로 제작·실행 방식 결정 |
| B1 · 상태/action 저장 | instance/schema migration, action journal, recorded draw, 원자적 효과/예약 | 중복 클릭·CAS 충돌·자원 부족·재접속·취소·포크·개정에서 중복 소비/상태 유실 없음 |
| B2 · 생성/파싱/job 연결 | prepare-main/after-main, typed parser, 문맥 선택, 역할별 job/의존성 | Veil 형태의 상태→추첨→입력→응답→파싱→다음 입력이 한 경로로 통과. stale/깨진 상태는 미반영 |
| B3 · 공통 UI | setup/action forms, 상태/퀘스트/선택지/표/달력, 에셋·오디오 참조 | desktop/390px 키보드·스크롤·대기/오류 표시. 다시 그리거나 화면을 열어도 상태/모델 호출이 늘지 않음 |
| B4 · 대용량 가져오기 | 파일 업로드·에셋 manifest/분리 저장·미지원 동작 보고·취소 정리 | 메리/Alternate 크기의 합성 ZIP에서 메모리/크기/중복/경로/CRC 검사. 에셋 전체를 JSON/base64나 모델 입력에 적재하지 않음 |
| B5 · 표본별 변환 검증 | 개별 동작 대응표, 실제 로컬 패키지, 합성 회귀·화면 확인 | Phēmē 유지, Veil 순환, Alternate 보조 상태, 청원고 일정/시간표, 마지막으로 메리 RPG/보조 작업/복원까지 단계별 확인 |

B1–B3와 B4는 계약이 정해지면 독립 구현할 수 있어요. B5의 큰 파일 수입과 전체 패키지 검증은 B4를 기다려요. 먼저 작은 Veil 순환을 연결한 뒤 다른 사례를 더하고, 메리의 기능을 일부만 옮긴 상태를 전체 이식 완료라고 표시하지 않아요.

실제 카드의 전수 동작 대응표에는 각 기능을 `지원 / 의미를 보존해 재설계 / 제외 / 미확인`으로 표시하고 이유를 적어요. 원본 제작자가 넣은 보호·시작 조건·상태/지식 구분을 추정으로 없애지 않아요. 미지원 기능 때문에 핵심 흐름이 끊기면 검토용 초안으로 남겨요. 원본 HTML/Lua의 동일 실행은 목표가 아니에요.

### 반드시 넣을 반례 검사

- 메리: 마지막 토큰의 동시 사용, 중복 퀘스트 보상, 리롤 후 재접속, 8/15턴 경계의 재생성, 다중 보조 작업 일부 실패.
- 청원고: 동일 응답 재생성의 호감도 이중 반영, 일정 삭제/시간표 변경 경합, 윤일·월 경계·고정 교시와 랜덤 배정.
- Alternate: 보조 작업 대기 중 새 응답·원문 수정·분기 전환이 발생해도 원래 source에만 귀속. 오래된 상태의 history projection이 raw 저장본을 바꾸지 않음.
- Veil: preview/전송 재시도에서 추첨 불변, STATUS/LEDGER 일부 손상 시 원자성, 부모 상태 대기와 후속 입력의 정확한 상태값.
- 공통: 여러 역할의 같은 패키지·여러 모듈의 ID 충돌, 개정/백업 roundtrip, 실행 시간/출력/목록/연쇄 호출 상한, 렌더러의 읽기 전용 성질.

## 범위와 다음 결정

권장 방향은 **TypeScript 제작 도구 + 공통 데이터 계약 + 필요가 검증된 계산 확장**이에요. CBS/Lua 전체 호환이나 새 범용 문법 설계는 선행 조건으로 두지 않아요. B0의 결과로 실행 방식만 확정하고 기존 Uimori의 저장·권한·불확실 실행 규칙은 계속 적용해요.

계획 작성 시점에는 이 계획의 구현/실행 PASS가 없었어요. 이후 공통 기능 구현·검증은 [PACKAGE-BEHAVIOR-RESULTS](PACKAGE-BEHAVIOR-RESULTS.md)에 별도로 기록했으며, B0–B5 전체나 원본 카드 전체의 완료를 뜻하지 않아요. 이전 개편의 799개 단위/51개 브라우저 통과는 그 당시 구현에만 해당해요. 실제 원본의 유료 모델 실행·문학적 동일성 평가·개인 자료의 공개 배포는 별도 범위이며, 계획 조사에서는 테스트 DB나 원본 파일로 실험하지 않았어요.
