# 최종 점검 v0.6.1

작성일: 2026-09-06. 대상: v0.6 ZIP의 문서·JSON·Codex 지시문. 제품 코드 검토나 앱 실행 결과가 아니다.

## 판정

기술 조합, 제품 목표, 모델 자율성, 역할 분리와 M0–M3 단계는 유지한다. 설계를 다시 시작하거나 기능을 더 추가할 이유는 찾지 못했다. 아래 세 부분만 보정한 뒤 M0를 구현하는 편이 낫다. 발견 사항은 미구현 제품의 실제 버그가 아니라 문서상 누락·오해 가능성이다.

## C1. 원문 저장과 후속 job 예약 사이의 영속성 경계

- 원본 위치: v0.6 ARCHITECTURE.md §4, 물리 37–45행; ACCEPTANCE.json F05; 첫 작업 지시 제품 경로4.
- 확인한 내용: 파생 작업의 독립 수명, 결과 커밋과 중복 방지는 있었지만 원문 확정과 job 예약을 함께 커밋하는 계약은 명시되어 있지 않았다.
- 가능한 잘못된 구현: 원문을 저장한 뒤 in-memory callback으로 번역/상태 작업을 예약한다. 둘 사이에서 서버가 죽으면 원문은 있지만 예약은 없다. job 테이블만 재시작해도 찾을 작업 자체가 없다.
- 보정: 정상 원문 확정·Run 완료·적격한 job 예약을 같은 짧은 SQLite 트랜잭션에 넣는다. 실제 모델 호출/worker 실행/알림은 밖에서 한다. 파생 결과와 job 완료 기록도 함께 커밋한다. 불확실한 원격 유료 요청은 자동 replay하지 않는다.
- 검증 목표: F05의 기존 장애 시나리오에서 트랜잭션 중간 실패와 커밋 직후 worker 알림 전 종료를 재현한다. 원문 재생성 없이 예약을 발견하고 결과를 중복 반영하지 않아야 한다.
- 변경 대상: ARCHITECTURE, MILESTONES M0, VERIFICATION, ACCEPTANCE F05, 첫 작업 지시.
- 이는 새로운 큐 서비스나 분산 트랜잭션 프레임워크 요구가 아니다.

## C2. recent tail로 보완하는 watermark 방향

- 원본 위치: v0.6 ACCEPTANCE.json S05.
- 원본 문구: `memory watermark 이전 누락은 recent tail로 보완`.
- 문제: 연속 처리 완료 지점을 watermark로 쓰는 설계에서, 아직 기억 추출이 안 된 최신 구간은 그 이후다. 이전이라는 문구는 방금 발생한 사건을 입력에서 놓치는 구현을 허용할 수 있다.
- 보정: 해당 분기의 연속 처리 마지막 원문revision을 watermark로 정의한다. 이후 미처리 원문을 recent tail로 보완하고 더 오래된 원문은 검색·읽기로 회수한다. 모든 기억을 무제한 기본 입력에 넣으라는 뜻은 아니다.
- 변경 대상: ARCHITECTURE §6.5, ACCEPTANCE S05. M2 범위를 M0로 앞당기지 않는다.

## C3. 단계별 증거와 이어가기의 외부 차단 처리

- 원본 위치: v0.6 MILESTONES.md 물리31행, prompts/03-continue.ko.md 물리3–11행.
- 확인한 내용: M1 설명에서 Q01–Q05를 함께 언급하지만 Q04는 ACCEPTANCE에서 M2로 지정되어 있다. 이어가기 지시는 ‘막힌 현재 필수 항목부터 해결’과 ‘키 없이 로컬 구현 계속’을 동시에 말한다.
- 위험: 구현자가 M2 장기기억 평가를 M1 gate로 가져오거나, API 키가 없다는 동일한 차단을 반복하며 무관한 로컬 구현을 멈출 수 있다.
- 보정: M1 품질 범위는 Q01·Q02·Q03·Q05, Q04는 M2다. 로컬 결함은 먼저 고친다. 키·예산·기기만 부족한 주장은 BLOCKED로 유지하고 사용자 요청 범위의 독립적인 다음 로컬 흐름은 진행할 수 있다. 그 경우에도 전체 milestone/live 지원을 완료로 표시하지 않는다.
- 변경 대상: MILESTONES, 이어가기 지시. M0 완료 후 자동 M1 착수 금지는 그대로다.

## 그대로 유지한 판단

작은 모듈형 모놀리스, 채팅별 설정·불변 원문, 모델 주도 자료 탐색, 역할별 고정 계약/발견 목록/실제 읽기 결과, 보조 번역·이미지·표시 상태, scope·권한·비용 경계가 서로 양립한다. 메인 도구 사용을 없애거나 필수 연구팀을 새로 둘 이유는 없다. 기존의 UI 없는 테스트만으로 성공 처리하지 않는 검증 원칙과 짧은 AGENTS/CURRENT도 유지한다.

처음부터 모든 기능·future test stub·provider adapter를 만들라는 지시는 없다. first task는 M0에서 멈추고, 다음 지시로 한 사용자 흐름씩 진행한다. 문학적 품질·실제 로어 선택·현재 provider 단가는 구현 후 별도 근거가 필요하며 정적 계획으로 보장하지 않는다.

## 실제로 이번에 확인한 것

v0.6 ZIP 15개 파일을 읽고 문서 간 단계·지시·수용 기준을 대조했다. 36개 수용 ID와 89개 과거 ID 연결, 기존 해시, standalone/ZIP 안의 아키텍처·첫 지시문 일치를 재계산했다. v0.6.1은 같은 파일 목록과 수용 ID를 유지하며 구조 검사를 다시 수행한다. 세부 결과는 KIT_VALIDATION.json에 있다.

앱 코드·Windows 환경·브라우저·유료 모델·휴대폰 동작을 실행한 것이 아니다. SQLite/AGENTS/worktree/Windows 공식 문서는 관련 계약 참고로만 확인했다. 새 모델 전용 파라미터나 라이선스 조건을 추측해 추가하지 않았다.
